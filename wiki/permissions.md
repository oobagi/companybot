# Permissions

How agents get the go-ahead for actions that leave the building, or that act as you in an automation someone else wrote. Start strict, loosen as trust builds. This page owns action rules and approval invariants. How to add a tool: [Extending](extending.md#action-rules-and-approvals).

## What asks
- Every tool has a **risk** (`toolRisk`): `none` runs right away; `inside` runs right away except in a run that follows someone else's words (below), where it asks; `outside` asks first; `locked` always asks and never offers "Always allow".
- Default: connector tools not marked read-only are `outside` (unlabeled tools ask; a server's read-only label is its claim). A connector tool the server marks `destructiveHint` is `locked`, even if it also claims read-only (hints only ever tighten). Built-ins that change anything are `inside`, read-only ones `none`, unless they declare `risk`; so a new built-in asks in others' automations the first time it's used, with no mass pausing. Member invitations (including resend/cancel in the invitation group) and skill edits/creation declare `outside` (every agent follows skills); member removal, channel deletion, skill deletion/uninstall and automation deletion/uninstall declare `locked`. Archiving pages, records, fields or databases uses call-specific `locked` risk. Forgetting a memory, deleting a saved view and undoing a record change (which can archive it) are locked too. Ordinary writes and restores keep their existing risk. Future outside sends and calls declare `outside`; payments and bulk sends declare `locked`.
- `web.search` and `web.fetch` declare `none`: they change nothing and read nothing private, so they run without asking, in others' automations too (asking every time would make them unusable). What keeps them safe instead: search sends only the query to the provider, and `web.fetch` opens only links that existed before the model wrote anything (the person's messages this turn, the thread's parent if they wrote it, the message that started a turn resumed after an approval, or this turn's web results, compared with the query string), so injected text can't make it send data to a link of its choosing. Owners who don't want them remove the grant. They declare `sendsOut`, so they're still checked on every call. **Restricted egress:** outside the workspace is a wider audience than any chat, so once a turn has any restricted source (`turnIsRestricted`: #210's sources, checked against a place open to the whole workspace), including the chat it runs in (a private channel, a group DM) and a role-limited workspace connector it read (#234), each web call and connector call asks with its exact query, link or payload, `locked` (no Always). The gate is mandatory: an Unlocked lock, an Always rule or an automation grant doesn't lift it; a block or Never still wins. Two exceptions: #210's own-data rule (in the asker's own 1:1 agent DM, their one-person data doesn't count; anyone else's restricted place still does), and a **read-only** call to the same workspace connector install the data came from (read-only on both sides by one rule, core `readsOnly`: the live tool says read-only and isn't destructive, and the server's last listing agrees; an unlisted or destructive tool counts as a write, and the same rule decides which connector calls are claimed by call id). A write or send through that connector (`crm.send_email` can reach anyone) asks like any other.
- `pages.write` is `inside`, like record writes (#215): creating, replacing, moving and restoring pages act as the person, so rules, Never, owner locks and others' automations reach them. Archiving (`trash: true`) stays `locked`.
- `web.save` declares `none` too: same links and allowance as `web.fetch`, and the file only lands on the reply. Using it elsewhere asks as that tool does.
- `images.generate` declares `inside`: nothing leaves the workspace (AI Gateway is our inference provider, like a model call), but it spends the workspace's money and can read pictures from the person's private chats as edit input, so it runs right away in your own chats and asks in runs following someone else's words. The monthly image budget (Settings → General) caps the spend; locks and Never rules work as for any built-in.
- Personal connector read-only tools declare `inside`: foreign automation runs ask on first use; normal chats and workspace-shared connector reads keep their existing behavior. Destructive hints still lock.
- **What counts as acting as you (`inside`):** reading what only you see (`chat.read`/`chat.search` reach your private channels and DMs; `memory.search` your personal memories) agent Activity (`records.history` with `source: agents`), other agents’ accessible memories, and anything done as you (posting, DMs, channels, records, pages, memory, automations, installs, workspace settings). **Not counted (`none`):** reads of shared workspace data (records, databases, views, pages, the automation list, skills), the clock, widgets, and reacting to the message being answered. Public-channel reads count because the same tool reaches private ones; we'd rather ask once than guess per call.
- Internal message delivery, channel changes, installs, automation edits/pause/resume and non-security workspace settings follow the acting person's normal rights and run immediately, outside others' automations. An agent delivery names the agent and person, does not mark the person's destination read, and never triggers another agent or automation. Resuming or subscribing never grants Always consent.
- Internal changes (record edits, database management, shared sorting and filtering) run right away and are logged. Records have undo; database and saved-view changes do not. Creating, renaming and deleting databases takes `fields.edit`; archiving keeps content in Archive indefinitely, and deleting forever takes `trash.manage`, never agents; shared views take `records.edit`. Both the app and agents use the same server checks.

- **Agents handing off act for the same person.** A turn another agent started (an @mention handoff, the dispatcher's pick, or `chat.ask_agent`) acts as the chain's person (`agentTurns.actorId`), with their roles, connections and rules, and asks exactly what that person's own turn would. Only a person's message starts a chain: wakes and automation runs never hand off, so a webhook can't set agents on each other. An ask stays in the asker's chat, out of its timeline: whoever can see that chat can open it read-only, as with an @mention's thread, and the asked agent follows that chat's memory rules. Continue on a paused chain is theirs alone (`chains.decide`), like an approval.

## Rules
- Grouped tools use an action union but one approval identity per tool. `chat.manage` and `channels.manage` use call-specific risk: `delete` is locked while its other actions run immediately. Separate outside invitations from locked removals; an Always rule for invitations must never authorize a removal. The exact nested request is hashed and shown on the card.
- The parity registry (`parity.ts`, tested against every public mutation) maps agent actions and human-only reasons. Role changes, owner invites, agent grants/self-modification, credentials, consent policy and account erasure stay direct human decisions. The registry has no deferred entries. Connector lifecycle/credentials, webhook-secret rotation, restoring an agent, skill or automation from Trash, and config restores remain direct human authority decisions. Agents may create tool-free agents and edit another agent's instructions/model, with owner rights; `agents.manage` delete (to Trash) and instruction/model changes are `locked` (call-specific risk), since they change what another agent does for everyone.
- **Per person, per action.** An action is one tool on one connector install (`crm.send_sms`), or a built-in. A rule (`permissionRules`) is Always or Never; no rule = Ask. Agents act as whoever asked, so a rule only applies to that person's calls and never reaches anyone else's accounts.
- **Action locks** (`permissionLocks`, `actions.lock` switch): Always ask, Blocked, or (for `locked` tools) Unlocked. Apply to everyone, reads included.
- **Strictest wins** (`permissionFor`): owner block → person's Never → owner/default lock (ask, no Always) → no risk, or `inside` in your own run (run) → person's Always (never for `inside`) → automation grant → ask.
- **Checked fresh at every call** (`permissions.check`, via the AI SDK's `toolApproval`). Nothing is cached in a session, so revoking or locking applies to the very next call. A call approved on the card is re-checked before it runs: a block or Never set since wins.
- Rules key on the person and the action only, never on a snapshot of content, so unrelated changes can't void or block them (the "approvals broke silently" lesson).
- **Approvals name ids, not names** (#215). Every built-in that changes something takes the id of what it changes and of where it goes (pages and parents, records, linked records, chats or `"here"`, agents, skills, automations, memories, messages); databases and fields by key, teammates by id, email or `"me"`. Names resolve only in read and find tools. So renaming the approved page and giving a new one its old title can't redirect an approved archive.
- **Approvals bind what they depend on.** A tool's `binds(input)` names what its effect depends on (an overwritten or archived page, a restored version, an archived record, a changed memory, an edited or deleted message, a deleted agent, skill or automation). Record writes also bind what their keys and labels mean (`recordRefs`): the database and field ids behind keys, the option ids behind choice labels, and, for archiving a field or database, its newest live and archived record changes, so a field remade with the same key, a choice label moved to another option, or a record added since stops it. `approvals.request` stores those revisions (`bound`) and hashes them with the call; `claim` refuses if any changed, and the effect's own transaction checks again (`withReceipt`), so an edit in between can't slip through: "What this changes was edited after it was approved, so it didn't run." Appends, renames and creates bind nothing else, so unrelated edits don't void them.
- **Every call has an operation key** (`Op`): the approval id for an approved call, else the model's call id (`ToolContext.forCall`). A built-in's write commits with a receipt under that key (`toolReceipts`, or the approval's own result and Activity line, `withReceipt`), so a retried step or duplicate delivery writes nothing twice. One call id holds one approval (`approvals.request` returns the same card). Built-ins whose effects take several steps (`untransacted`: `images.generate`, `web.save`) claim the key before downloading or spending anything (`approvals.startOp`) and settle it after (`finishOp`). Connector calls get an idempotency key (the call id) whenever their schema has `idempotency_key`/`idempotencyKey`, approved or not; on a held call it's in the input shown and hashed. A connector write without one is claimed by call id before it's sent (`ToolContext.calls`, `approvals.startCall`): a repeat gets the first call's stored result, or "may or may not have happened" if it never finished, and is never sent twice. Receipts are kept 30 days once done (`forgetReceipts`, hourly, in batches); a started one, whose outcome is unknown, stays until its turn is deleted. No receipt is written for a turn or workspace that's gone.
- **Unknown outcomes.** A connector or `untransacted` call cut off or failed in transit after approval may or may not have happened: it ends `failed` with `outcome: "unknown"` and "may or may not have happened. Check before trying again." A field, not a new status, so apps before 0.1.0-alpha.10 still show the error. A one-transaction built-in cut off ends plain `failed`: nothing changed.
- Uninstalling a connector deletes its rules and locks; removing a member deletes theirs. Reinstalling or rejoining starts strict. A custom connector (#257) whose server, account type or sign-in is edited starts strict the same way (it's uninstalled and reinstalled for the same roles); removing it is an uninstall. Only `connectors.manage` adds, edits or removes custom connectors, never agents (`parity.ts`). Its tools follow every rule here unchanged: unlabeled tools ask, `destructiveHint` locks, restricted egress and private-reply sources treat its install like any workspace connector install.

## Roles
What a person may do at all, before any of the above. Roles are workspace data (`roles` table); the switches are the keys in `core/src/permissions.ts`, each with a plain label and a Member default.
- **Owner** (built in) can do everything, can't be edited or deleted, and every workspace keeps one (`hasLiveOwner`). Owner-only things are never switches: resetting or deleting the workspace (`workspace.reset`, `workspace.delete`) and changing roles (`roles.manage`). Only owners give or take Owner, change an owner's roles, invite an owner or remove one.
- **Member** (built in) is what new people and invites get. Owners toggle its switches and can't delete it. It stores only their changes (`roles.switches`): each switch is `override ?? default`, so a new permission reaches every workspace's Member as its default, and so does a changed default.
- **Member defaults** (decided 2026-11-04): on for working the data and talking — records, pages, team memory, channels, `connectors.connect`, `sidebar.arrange`. Off for shaping the workspace: team skills (`skills.edit`; every agent follows them), team automations (`automations.edit`; they act for others) and databases and fields (`fields.edit`; schema), plus everything sensitive. Personal skills and automations stay open to everyone. Same as Slack (members post and make channels; workspace-wide config is admin), HubSpot ("Edit property settings" is a separate admin permission from editing records) and Airtable (Editors change records; only Creators change tables and fields). Owners turn any of these on for Member, or make a role for it.
- **Public** (built in): the role outsiders get. See [Public](#public) below.
- **Custom roles**: owners create, rename and delete them (`backend/convex/roles.ts`, max 30). They store what's on; anything absent (a new permission too) is off. Deleting one takes it off everyone and every connector; anyone left with none keeps only baseline access: shared reads, chat and personal items, until an owner assigns a role. A pending invite left with none gets Member (the cascade's `fallbackRoleId`), like one sent without a role; the confirmation counts pending invites (`roles.list` `invited`).
- A person holds one or more (`members.roles`) and gets the **union** of their switches (`accessFrom` → `Access { roles, owner, permissions }`; `can(access, p)`). `members.manage` hands out roles, with limits (decided 2026-11-04, after testers gave themselves a custom role and a security audit): someone who isn't an Owner gives or takes only Member and roles they have themselves (`canGrantRole`), invites included, and never changes their own roles. Holding the role, not just its switches, is the test: a role also opens places and connectors, so a switch-only check let a manager invite a second account into a role that opens a database they can't. The same holds for taking a role by other means: they remove a person, or cancel an invite, only if they could take every role it has (`requireGrantable`, agent tools included). On joining, an invite's roles are checked again against the inviter's roles at that moment (`joiningRoles`); one they can no longer give becomes Member, unless the inviter is an Owner. Invites with no `invitedBy` keep their roles. Owners are unrestricted. The alpha.9 `setRole` and `role` literals go through the same check (`checkRoles`).
- **No maker rights.** Making a channel, skill, field or team automation gives no extra power over it; the switch decides. Personal skills are visible and editable only to their maker, with no switch to create one. Sharing one with the team requires `skills.edit` and confirmation. Personal automations (audience `creator`) follow the same visibility rule (`canEditAutomation`), and making one needs no switch.
- **Connectors** pick which roles may use them (`connectorInstalls.roles`; owners always can, `canUseConnector`).
- **Agents** see the same tools for everyone; a built-in whose `permission` the acting person lacks is refused at call time by `permissions.check` (`{ type: "deny", by: "role" }`), and the model is told which roles have it (`deniedMessage`), so it can tell the person whom to ask.
- Adding a switch needs no migration; pick its Member default with care (see [Extending](extending.md#permissions)).
- **Mid-migration** (COMPAT, until `migrations.customRoles*` run on prod): every read of who holds what goes through `accessOf` (`lib.ts`), which reads an old `role` as the built-in role it became, even before the workspace has its roles; connector installs' old `"member"` reads as the Member role (`allowedRoles`). So access, the last-owner checks, leaving, erasing and old invites behave the same before, during and after.

## Public
The role for people outside the workspace (customers who email or text an agent, [Product → Inbox](product.md#inbox-email-and-texts-built)). It applies by itself whenever the asker isn't a member; no one can be given it, and it can't be deleted. **It's built from the same blocks as any role, never from hardcoded workflows** (decided 2026-11-07: no "create a lead" or "read FAQ pages" switches): data access is places' Who can access lists, and anything more is an ordinary automation on the Inbox events, run as its person.
- **Data: Who can access lists.** Owners add Public (`PUBLIC`, core `place-access.ts`) to a page's or database's list like any role ([Who can access](#who-can-access)). The reader is `PUBLIC_ACCESS`, through the same `levelIn`/`canAddIn`; **Everyone never includes Public** (`isFor`), so nothing is shared outside until someone adds it.
- **How agents talk with them is the agent's, not the role's** (moved 2026-11-08: Roles held "reply without staff approving", which isn't a permission). Each agent's config (core `agent-config.ts`, versioned like the rest) has `customerReplies` (`check`, the default: replies are drafts staff send; `send`: they go out at once) and `handOffTopics` (topics it never answers; it hands those to staff). Changed in the agent DM's Details panel or Settings → Agents (`agents.setCustomerHandling`, `agents.update`, both `agents.manage`); an agent changing another's is `locked` and its own is refused, like instructions. Taking a message and handing off are always on. Settings → Roles → Public only explains the role.
- **The hard ceiling, the only Public-specific rule** (`publicLevelProblem`, `publicPlaceLevels`): View on pages; View or Add on databases; nothing on channels; never Edit. Saving a list past it is refused (`cleanAccess` via `savedAccess`, for every kind of place), and a stored Edit for Public would give nothing anyway (`levelIn` skips it). Settings, members, roles, memory, connectors and automations have no place list for Public at all. Changing a list stays a direct human decision (`parity.ts`), so there's no agent sharing tool.
- **Its own runner.** A Public turn (`backend/convex/inboxAgent.ts`) isn't a chat turn: it has no actor, so it can't reach `runningTurn` or any member tool. The model gets only the Public tools (core `public-tools.ts`) and the agent's instructions; customer text, and everything tools return, is fenced or framed as data (`publicTurnPrompt`). Conversation tools: `reply`, `take_message` and `hand_off`, always. Data tools, only when something is shared (`sharedSummary`): `shared` (what's shared, with fields), `read_page`, `find_records`, `save_record` (only with Add). Each call rechecks the conversation (live workspace and agent, staff haven't taken it: `outsiderOf`), the ability, and the list (`backend/convex/publicPlaces.ts`).
- **What Public reads, mirroring members:** a standalone page whose ruling list (its own, else the ancestor it follows) has Public at View; sub-pages that follow it, not ones with their own list. Page blocks are titled per reader (`pageTitlesFor`), so a hidden sub-page is "Page". Databases at View: every live record. Stricter than members on purpose: only plain fields (never `user` or `link` fields: they'd name teammates and other records, `outsiderFields`), never record bodies (staff notes live there), and never a page or database with retained sources (`usedPlaces`). Sharing a place with Public is refused while it holds facts from a source Public can't open (`audienceFit`, like any widening).
- **Add as Public:** "you" is the conversation's contact (the lowercased email or E.164 phone). `save_record` creates records stamped `records.contact` (no `createdBy`), and changes or archives (cancels) only rows with that contact (`ownRecordFor`); `find_records` lists them through `records.by_contact`. Writes go through `recordOps` (`createRecordFor`, `updateRecordFor`, `archiveRecordFor`) with a `Writer` of `{ outsider }`: history stores `contact` and `agentId` with no `userId`, shown as "Companybot, for (555) 123-4567 by text" (`changedBy`, core `outsiderWords`). Only staff restore.
- **Forged senders change nothing.** Anyone can put someone else's address in an email's From. Replies only go to the real address, so a forger reads nothing; changing or cancelling their records also needs the latest email to pass the receiving server's own sender check (core `senderVerified`: the first `Authentication-Results`, DMARC pass or DKIM by the From domain; later ones came with the mail). A message that fails is stored `unverified`, and `Outsider.verified` is false until a passing one arrives. Texts come from the carrier, so they always count. Adding a new record is still allowed.
- **Outside replies ask first.** Unless the agent is set to send replies right away, its reply is a draft that staff edit and send (`inbox.sendDraft`). When an agent works Inbox for a member (`inbox.manage` start and reply) those are `outside` actions with the usual card. One reply per turn, at most 10 agent replies per conversation per hour (then it's handed to staff), and never to auto-replies, lists or our own addresses.
- **Inbox events** (`inbox.started` for a new conversation, `inbox.received` for every message; core `appEvents`) trigger ordinary automations from `inbox.receive`, never for auto-replies or our own addresses. The run follows someone else's words (an event), so it asks before `inside` actions like any event run, and acts as its person, never as Public. The event's data is customers' messages, so the trigger `needs` `inbox.use`: making or saving one checks it (`checkConfig`), and runs skip anyone without it (DMs, subscribers, the channel actor).

## Who can access
Each **channel**, **database**, **page**, **folder** and **file** has a list (`access` on `chats`, `recordTypes`, `pages`, `driveFiles`): **Everyone**, chosen roles or **Public** ([Public](#public); never on a channel, folder or file), each at **View** or **Edit** (shown as **Post** for channels), or **Add** in a database. Like Google Drive or Notion sharing, not Discord's override grid. Rules in `core/src/place-access.ts`; backend gates in `backend/convex/placeAccess.ts`.
- **Add** (databases only; generic, any role): create records, and see, change or archive only the ones you made (`madeBy`: `createdBy` is you, or for Public the contact), like editing your own Google Form response. It isn't on the View → Edit scale: `levelIn` (the reach into everything) ignores it and `canAddIn` checks it, so every existing reader treats an Add-only person as having no access, and only the paths written for Add honor it: the database's sidebar entry and fields (`recordTypes.list`, `canAdd`, `seesAll`), its list (`records.list` with `owner`, driven by `records.by_creator`), `records.get`, `requireRecord`'s own-record rule (reads, writes, archive, restore, undo, history), a record's body (`ownBody`), and the record tools (`typesFor` marks `onlyYours`, `findFor` lists theirs, `saveFor` creates). Search, links, Activity and Archive don't show them; fields, views and the database stay with Edit. Two roles add up: View from one and Add from another sees everything and adds. `widens` counts Add and Public as letting someone further in.
- **Not on the list: no access.** Checked by the shared readers, not their callers: `requireChat`/`chatByRef`/`canSee` (chats), `requireType`/`requireRecord`/`typeVisible` (databases and records, including `recordOut`), `requirePage`/`pageVisible` (pages). What's covered, by test (`tests/placeAccess.test.ts`, including one that runs every listing and agent listing tool as someone off the list): lists, sidebars and browse; `get`s; search (records, pages, messages); link chips (`resolveRefs` → `{ locked: true }`, no name); record Activity and history; page history and moves; Archive; alerts, unread counts and the workspace rail's badges; follow-ups; automation listings and their last runs (a watched or destination channel they can't see is "a channel", without its id; runs store channel ids, named per reader by `outcomeText`); saved views; links both ways (`records.linked`); a record's discussions; typing; agents' tool calls in Activity; the editor's page sync and its history (`pageSync`); and agents' reads and listings.
- **What still shows:** that something exists, never its name. A parent page's document keeps a hidden sub-page's block (its id only: "Page"); a visible database's link field to a hidden one says so (`linksHidden`) without that database's id (`fieldsShown`); page history says "Moved from a page you can't see"; a page in Archive under a hidden ancestor says so without naming it. Asking for a hidden place by id gets the refusal line below with "this page", "this database" or "this channel"; naming one exactly gets it with the name as typed, which confirms it exists. Words people typed stay as written (a message saying "#payroll"). Agent replies and tool lines follow the recorded sources too: see [Private replies](chat.md#private-replies).
- **Owners always have Edit.** Someone's level is the most any of their roles gives (`levelIn`).
- **No list is Everyone at Edit** (unset in storage), so nothing changes until someone restricts a place. Setting it back to that stores nothing again.
- **Pages, folders and files:** a sub-page, folder or file follows its nearest ancestor's list unless it sets its own (`pages.setAccess` / `driveFiles.setAccess` with `null` follows again; `fileStates` over `pageStates`). A record's page follows its database, and so do pages inside it (through it) unless one sets its own list; the access walk stops at the record's page (`pageStates`). **Moving or restoring a page never opens it to more people** (`keptAccess`): one following its old parent keeps that list if the new place's would let anyone further in (`widens`), including a page restored to the top level because its parent stays in Archive; moving somewhere stricter makes it stricter. A parent's document syncs whole to everyone who can see it, so page blocks hold only the sub-page's id, in every snapshot, step and restored version (`pageBlocks.ts`): titles resolve per reader as it's read (the app through `pages.get`, agents through `withPageTitles`). Titles older apps stored are stripped from every sync read and history version (`withoutPageTitles`) and from kept versions by `migrations.pageBlockTitles`.
- **Private channels** keep their member list; the access list applies on top. **#general** always keeps Everyone, at least at View.
- **Who changes a list:** the kind's switch (`channels.edit`, `fields.edit`, `pages.edit`) and Edit in the place. A change that would leave the person without Edit (Post) there is refused unless they're an Owner (`requireKeepsEdit`, core `losesOwnEdit`: "You'd lose edit access. Ask an Owner."), so a Member can't set #general to View or drop Everyone and lock the team out with no undo; a page, folder or file going back to its parent's list counts. The app disables those controls with the same rule. Role ids are checked against the workspace's roles (`savedAccess`): another workspace's or a deleted role is refused; naming Owner is dropped. Deleting a role takes it off every list (emptied, a list is Owners only). It's a direct human decision (`parity.ts`).
- **Writes need Edit (Post):** posting, editing your messages and reacting in a channel (deleting your own stays open); changing records, fields, views, the database itself and its pages; editing, moving, archiving and restoring pages, folders and files. An agent replies in a chat only for someone who can post there (`canReplyAs`), checked when a follow-up wakes, when its turn starts, on every tool call (`runningTurn`), on every stream write and the runner's stop checks (`updateReply`, `isStopping`, `steerWait`), and when any reply finishes (`finishReply`). Someone moved to View mid-reply stops it: nothing it writes after goes out, and it ends with "This person can no longer post in this chat." An automation posting to a channel acts for someone who can post there, and one watching a restricted channel posts only there or to the people who turn it on (`postingProblem`).
- **Refusals name who has access:** "Only Office and Owners can see Deals.", "Only Office and Owners can post in #news." (`placeDeniedMessage`, with role names, Owners last). The place's name goes only to someone who can see it, or back to someone who asked by that name (`requireAccess`'s `asked`); by id, it's "this database". The app hides places instead; agents look places up by name or id, so their tools find a hidden one and return that line, and the agent tells its person whom to ask.
- **Agents use the asker's access**, read fresh at every call through `runningTurn`, like roles. A follow-up's record is read through `recordOut` when its turn runs, so access lost while it waited ends the turn with the refusal.
- **Private replies (#201):** shared readers record restricted databases, pages and channels on the reply before returning results to the model. Workspace connector calls record their install id and use its live allowed roles; default Member access does not include people who hold only custom roles. Deleted installs become Owners-only: Owners keep access to saved work, including editing it and running their automations; a direct Owner change to a place’s access list can remove its deleted connector sources and reopen that place to roles. Live installs and other sources still constrain the change. Reinstalling alone does not reopen old sources to other roles. Reads of records record their database. Every viewer must still be able to view every source; sharing the reply explicitly releases it to its chat. See [Chat → Private replies](chat.md#private-replies).

## The card
- The held call shows **in the agent's reply**, where it made the call: "I'd like to send an email to dana@acme.com from your Gmail.", the exact input, then **Allow once / Always allow / Deny**. From an automation's run it names it: "Monday sales summary wants to post in #general as you.", and the button reads **Always for this automation**. A tool's `label` names who or where ("Remove ben@acme.com from the workspace", "Resend the invitation to ben@acme.com"). It stays in the timeline with the outcome ("Allowed once by Jaden"); what the call returned sits behind **Raw**, since the agent's reply says it in words.
- Actions are named the same everywhere (`actionLabel`): the MCP tool's title, else its name in words ("send_sms" → "Send SMS"). Phone numbers show laid out; what runs and what's hashed is the exact input. Tool lines under replies say what happened ("Sent SMS with Fake CRM", `toolLine`); a tool with `label` names what this call touched ("Saved Acme Roofing"). Labels are stored on the reply's tool part, never replayed to the model.
- **The top of the card is the agent's own words**: one or two sentences on what the call will do and why it wants to ("I'll archive Old pricing notes because it has outdated pricing."). When it holds a call, the runner asks the same model, with the turn's instructions and conversation (cached prefix), via `whyPrompt`; the text is stored on the `approval` part (`why`). Later turns replay the held call itself, with a "held for approval" result. It's the model's claim, so the exact input stays right under it, and an automation's card adds which automation made it. If writing it fails, the card shows the plain ask above.
- Under the buttons, in plain words, what "always" covers: "Always allow: agents can send email from your Gmail without asking you first. Only when acting for you." Settings uses the same text (`alwaysAllowText`), minus the pointer to Settings.
- "Always allow" saves the rule and runs the call. Not shown for locked actions or to anyone but the person the agent acts for. The server enforces it too: `decide({ always: true })` is refused wherever the action always asks (locked, or a workspace "ask" lock), and scoped to the automation if the run was one's.
- The runner must save the exact held call with its `risk` (`approvals.request`). Stored `risk` stays optional because no migration backfilled old rows; those rows cannot offer Always and use conservative risk checks.
- The lock is SHA-256 of canonical JSON of the tool id, exact input and bound revisions (`approvalHash`). The app returns the hash it showed; `decide` refuses any other; `claim` re-hashes before running. Only the acting person decides, while they can see the chat, within 24h. No role can decide for someone else. Compare nothing else: unrelated changes never void a call.
- **What the card shows** (`approvals.forReply`): the call's own action from its input (`ToolDef.action`, "Archive page"; `actionKeys` like `trash` it already says are left off) and its fields with every id named as this viewer may see it (`namedInput`: page, record, database and chat titles through the shared readers, else "a page you can't see"), never a hidden place's name. Bounded so a reply always loads: at most 50 cards per reply (`APPROVALS_PER_REPLY`; the app says when more aren't shown), 20 ids named per card and 200 per query, through one cache shared by the query's cards; a list past that ends "and N more", other ids stay unresolved. `input` stays the exact call for Raw and the hash.
- `approvals.decide` returns `{ decided: false }` when the call is no longer pending (lost a race to another device or click) instead of throwing, since the client logs every failed mutation; the card already shows the outcome. Expired and mismatched calls still refuse.
- `approvals.decide` queues a normal turn in the same place with `approvalId`. It runs the approved call first, then gives the agent its outcome through `buildTurnPrompt`. Replays note the held call without its outcome, staying byte-identical.
- Cards are `approval` message parts. `messages.list` returns them in `parts`.
- Blocked calls (Never or owner block) don't run; the model is told why, and the tool line shows failed.

## Automations
Modeled on Android runtime permissions and OAuth incremental consent: ask for what's needed in context, grants are per action, and saying no to one thing leaves the rest working.
- **Whose words a run follows** (`followsOthers`): yours if you made and last edited it, or it's a library one nobody edits, and its trigger is a schedule. Otherwise someone else's: another person made or last edited it, or a webhook or in-app event feeds it text from others. Only those runs ask before `inside` actions; outside actions keep the rules above either way.
- Foreign runs receive no prior conversation replay or summary, nor an unrelated thread parent. Only their trigger and replies in a thread rooted at that trigger are fed automatically; reading other history goes through the `inside`-gated chat tools, including after approval.
- **Turning one on** ("Turn on for me", resuming, or picking a channel) shows a short confirmation, with no permission list or grants. The first action needing consent asks when used. Cancel does nothing.
- **During a run, only the call waits.** Its card goes to the acting person's private DM with the agent, including channel/thread runs; the model is told it is waiting (`heldReason`) and carries on. Nothing pauses the automation as a whole. Allow once or Always runs it in a follow-up turn in the original place, preserving implicit targets; Deny runs nothing. Cards name the acting person, and only they can decide.
- **Always invariants.** An Always for an `inside` action exists only scoped to one automation (`setRule` refuses person-wide ones); a person-wide Always never reaches into someone else's automation. Grants key on the action, never the prompt, so a reworded prompt keeps them but can only use what was allowed. A held call remembers its automation (`approvals.automationInstallId`); if it's deleted, the card stops offering Always, never widening to a person-wide rule.
- A run belongs to an automation when its server-written trigger message was posted by it. The message preserves whether the original run followed others' words; later edits cannot turn it into trusted chat, and removing the automation blocks further permission-checked calls. Grants apply only to those runs; the same person chatting normally is still asked for outside actions, and never for `inside` ones.
- Turning it off for yourself, or deleting it, removes the grants.
- **Follow-ups inherit it.** A wakeup made in a run that followed someone else's words (a webhook, an in-app event, someone else's automation, or another such wake) is `foreign` (`automationScope` on the making turn), so its wake turn asks before `inside` actions like that run would. A webhook can't launder its text into a trusted turn months later. Wake turns hold calls like an automation's run (card in the actor's DM, the run goes on) and never offer Always.

## Where it shows up
1. **Chat:** the permission message with three buttons.
2. **Turning on an automation:** short confirmation → Turn on / Cancel; first-use cards offer Always for this automation.
3. **Workspace settings → Permissions → Yours:** your Always and Never rules and automation grants in this workspace, editable. They're stored per workspace (`permissionRules.workspaceId`), so they live in Workspace settings, not Account.
4. **Connector detail page → Actions:** each action Ask / Always / Never (same rules as #3). Listed from what the server last reported (`connectorTools`, updated each turn or with "Refresh list"); display only, calls are decided on the live tool.
5. **Workspace settings → Permissions → Action locks** (people with `actions.lock`).
6. **Activity:** each auto-allowed call says how ("Always allowed by Jaden, Oct 25"), links to the rule, or notes it was removed since.

## Code
- `core/src/action-rules.ts`: risk, per-person rules, workspace locks, `permissionFor` and denial reasons. Role switches stay in `core/src/permissions.ts` (see Roles above).
- `core/src/action-words.ts`: labels, asks, Always text and tool lines. The card and Settings use the same helpers.
- `core/src/approvals.ts`: exact-call hashes, status, expiry and who may decide.
- `backend/convex/permissions.ts`: stores rules and locks, checks calls, and grants automation actions. `connectorTools.ts` owns the last-listed connector metadata; settings read it, but calls use the live tool.
- The runner supplies `toolApprovalPolicy(usable, check)` as the AI SDK's `toolApproval`. Built-ins with no risk skip the check; connector reads are checked too. A rule-allowed call logs `allowed` (how, who, when, rule id).
- `core/src/public-role.ts`, `core/src/public-tools.ts`: the Public ceiling and its tools; `backend/convex/inboxAgent.ts` runs them. Tests: `backend/tests/inbox.test.ts`, `core/src/inbox.test.ts`.
- `backend/convex/approvals.ts`: holds, decides and claims calls. Tests: `backend/tests/permissions.test.ts` and `approvals.test.ts`; pure helpers have matching core tests.

## How others do it (Oct 2026)
- **Claude Code:** allow / ask / deny rules, checked deny → ask → allow; admin-managed rules can't be overridden; `/permissions` lists every rule and where it came from. [Docs](https://code.claude.com/docs/en/permissions)
- **ChatGPT workspace agents:** connector writes default to "Always ask"; builders can set some to "Never ask" or approve specific actions; admins can limit what connectors may be asked to do. [Help](https://help.openai.com/en/articles/20001143-workspace-agents-in-chatgpt)
- **Lindy:** a per-action "Ask for confirmation" toggle on anything with side effects; the agent pauses and emails you, and you approve in the app. Their advice: start with oversight and loosen as trust builds. [Docs](https://docs.lindy.ai/testing/human-in-the-loop.md)
- **Copilot Studio:** per-tool approval with approve / approve for this session / deny; admins classify connectors (business, non-business, blocked). [Summary](https://m365admin.handsontek.net/?p=23665)
- **Meta Muse:** permission prompts appear as chat messages from the agent, not tool boxes. Its "Allow Always" let it message Marketplace buyers on its own, including a seller's home address: he expected to still be asked at key steps. Lesson: say exactly what "always" covers and that you won't be asked again. [Write-up](https://redreamality.com/blog/meta-muse-allow-always-agent-permission-defaults/)
- **Android runtime permissions:** ask in context when a feature is used, explain why, offer "Only this time", and keep the app working when the person denies. [Docs](https://developer.android.com/training/permissions/requesting)
- **Google OAuth incremental authorization:** request scopes when they're needed; earlier grants carry over; people may grant some scopes and not others. [Docs](https://developers.google.com/identity/protocols/oauth2/web-server#incrementalAuth)
- **MCP tool hints:** clients usually auto-approve read-only tools and confirm destructive ones, but hints aren't guarantees; unlabeled tools should be treated as destructive. [Speakeasy](https://www.speakeasy.com/docs/mcp/build/gram-functions/tool-annotations)

What we take: Android's ask-when-used and keep-working-on-deny (one held call never stops an automation's run), OAuth's per-action grants that carry over, Claude Code's strictest-wins order and owner locks, Lindy's per-action toggle and "loosen as trust builds," MCP's untrusted hints, and Muse's in-chat prompts with plainer "always" wording. We skip "for this session" because Companybot has no sessions (one continuous conversation per agent).

## Phone sends

Staff calls use the same `inbox.use` and agent-number gate. `inbox.manage:call` and `end_call` are outside actions; microphone pickup is direct device consent. Call tokens reach one claimed room and microphone/data only. Media is closed on staff disconnect; the server rechecks membership, number and agent at most 10 seconds apart, including while a call is active. Public voice remains Soon.

SMS keeps the existing `agents.manage` number gate and `inbox.use` staff gate; agent-initiated starts and replies still use the existing outside-risk Inbox approval. Before its one provider attempt, dispatch checks the workspace, active agent, original number and staff sender's current Inbox permission. Automatic Public replies also stop on takeover or when automatic replies are disabled. A staff-approved draft acts for the person who approved it. Receipt callbacks only settle the bound attempt; they grant no customer or staff access. See [Phone](phone.md).
