# Chat

Channels, DMs (people and agents), threads, and reactions. One model for all of them. Tables: `chats`, `chatActivity`, `chatMembers`, `seatActivity`, `chatMessages`, `reactions`, `agentTurns`, `agentSessions` (`backend/convex/schema.ts`).

## Kinds
- **Channel** — named (`#sales`), public or private. Public: any member can read, and posting joins you. Private: members only; members add others. On top of either, a **Who can access** list (Everyone or roles, at View or Post; [Permissions](permissions.md#who-can-access)): off it, the channel doesn't exist for you (`canSee`); at View, it's read-only (`requirePost`: no posting, editing or reacting; the composer says who can post). Every workspace has `#general` (`isDefault`): everyone is in it, it can't be left or made private.
- **DM** — a fixed set of participants, found by `dmKey`. Person ↔ person, a group of people, or person ↔ agent (an **agent DM**). Each active agent shows in the sidebar as a DM even before the first message. **Close conversation** (Slack's pattern) hides a DM or group DM from your sidebar only (`chatMembers.closedAt`, `closeDm`) and keeps its history; it's back when a main-timeline message newer than that arrives (or one mentions you), or when you open it again (`openDm`, e.g. from New message). Agent DMs can't be closed: the row is how you reach the agent, and every active agent has one.
- **Side chat** — a separate conversation with an agent, under its agent DM (`parentId` = the DM; same `dmKey`, one level deep). Its own session and memory context, like a new chat in a chat app. The DM stays the primary chat: `openDm` and `agents[].dmId` return it, never a side chat. Named by `title`, set from the first line of the first message you send (`titleFrom`) and renamable; "New chat" until then. Archiving one moves it to Archive as kind `channel` (the Archive screen calls both "Chats"), with its messages; the DM itself can't be deleted.
- **Thread** — replies under a message (`threadId` = parent). The parent keeps `replyCount` and `lastReplyAt`. Threads are one level deep. In the app the open thread is part of the route (`/chat/<chat>/thread/<message>`), so the sidebar's thread row, Back/Forward and closing all agree.
- **Reaction** — one emoji from one person or agent on one message. Toggling again removes it. Any single emoji, checked by its structure (core `isEmoji`: one emoji sequence, so skin tones, ZWJ sequences, flags and keycaps count; text or two emoji don't), never against a list: the one rule for people and for an agent's reaction (its turn's decision, `reactOnce`). Stored in one form (`emojiOf`: fully qualified, the picker's), so "❤" and "❤️" are one reaction, not two rows. The quick row's 8 are only the desktop's suggestions.
- **Link previews** — the first 3 distinct http(s) links in a message (people's and agents') get a card under it: site, title, description, a small picture. Details below, under `linkPreviews.ts`.
- **Files** — up to 10 per message (`chatMessages.attachments`), like Slack's: pictures (PNG, JPEG, WebP, GIF), PDF, Word, Excel, PowerPoint, and text (plain, Markdown, CSV, JSON), up to 20 MB each. The same endpoint and kinds serve [Drive](drive.md) uploads. Upload and rules: `files.ts` under [Backend API](#backend-api-backendconvexchatsts-messagests-filests).

## When agents reply
- **Agent DM** (one person + one agent): every message the person sends, including automation runs posted as them.
- **Everywhere else:** only when @mentioned. (The main agent's welcome is fixed text, not a reply; see Onboarding.) Mentioning an agent in a channel adds it to the channel's members. In a DM, only agents already in it answer (a DM's participants are fixed).
- **Channels set to "When relevant"** (the default: `chats.replyMode` unset means "relevant", so every channel, new or old, starts there; "Mentions only" is stored as `"mentions"`; `replyModeOf` in core reads it, and DMs and side chats are always mentions): a person's message that @mentions no agent goes to the **reply router** (`backend/convex/router.ts`, prompt and schema in core `router.ts`). Anyone with `channels.edit` sets it (`updateChannel`, `channels.manage` `set_replies`). Group DMs stay mentions-only: they have no settings, and their agents are fixed anyway.
  - `messages.send` only schedules `router.decide` 1.5s out (`QUIET_WINDOW_MS`, the same quiet window a burst to an agent gets), off the send's critical path. When it runs it gives up if a newer person's message landed in the same place (chat + thread): that one decides, seeing this one, so a burst makes one call. A message that @mentions an agent schedules nothing; its agents answer as above and the rest stay quiet.
  - **One rule: the dispatcher wakes, the agent decides** (#172). The dispatcher is a wide net (recall), the agent is the final say (precision): the dispatcher sees only a few messages and a line per agent, the agent sees the whole conversation, its memory and what it said. So the dispatcher's prompt stays short and general ("could this be for the agent?"), with no special cases for nudges: the agent handles those from context. Same idea as "Inner Thoughts" (CHI 2025, arXiv 2501.00383): a cheap filter, then the participant with full context decides.
  - One call (`generateText` with `Output.object`, the AI SDK 7 form of `generateObject`) decides for each active agent in the channel (up to 10) one thing: wake it, `reply` (it could be for the agent: names it, asks or tells it something, asks something in its line of work, asks the room something it could answer, is addressed to everyone or all the agents, carries on what it said, or thanks or answers it), or `quiet` (plainly not for it), keyed `a1`, `a2`… so names are never matched. It sees the channel and topic, each agent's name and description, the people there, the thread's parent, the 8 messages before (`ROUTER_CONTEXT_MESSAGES`, agents' marked as theirs), the message, every text as a JSON string, and one line of state when an agent just answered this person ("Companybot (agent a1) answered Ada just above", `justAnswered`: the last agent message, after the person wrote, with only them since). Left-out agents stay quiet. **The dispatcher only wakes; the agent decides how to respond**: a post, a reaction or nothing, all through its answer (below). A "thanks!" wakes the agent, which reacts.
  - **Someone else.** When an agent just answered, Jev also gets a yes/no question, `someone_else`: does the newest message ask for someone other than it (another answer, a second opinion, a check of its answer)? `forSomeoneElse` multiplies that agent's chance of `reply` by 1 − that, so "anyone else?" or "can anyone validate that?" doesn't wake whoever just answered. The state line alone didn't move Jev (Companybot stayed at 0.72–0.98, ranked first, nor did a qualifier on the criterion); the boolean did (0.10–0.20, under the wake bar, 9/9). Like "who goes next"'s `ack`.
  - **Confidence, as words.** Jev returns `probabilities` per choice (`{"reply":0.88,"quiet":0.12}`). Its chance of `reply` is banded (`confidenceBand`): ≥ 0.85 "clearly for you", ≥ 0.6 "probably for you", else "might be for you". A language model gives none: "probably". **Wider net:** an agent Jev marks quiet but with `reply` ≥ 0.4 (`ROUTER_MIN_PROBABILITY`) is woken too, as "might". At most 10 "might" turns per channel per hour (`ROUTER_MIGHT_PER_HOUR`, counted on `agentTurns.by_chat_dispatch`); past that they're dropped, the decision still recorded.
  - **Reply** → `enqueueTurn` as the message's author, with `agentTurns.routed` and `dispatch` (`{ model, band, probability?, probabilities?, costUsd, after, then }`). `routed` changes only the prompt's context line (below); the turn runs, shows and ends like any other. **One message's picks run one after another, best fit first** (`dispatch.after` / `then`; `turns.ts` `waiting` holds a pick until the one before ends, `startThen` starts it, `startWaiting` is a fallback after `STALE_TURN_MS`), so each sees what the ones before posted: run at once, two agents answered the same room question every time.
  - **Why it's here** (`routedNote`, core `turn-input.ts`), the one line of the prompt that differs between turns: nobody @mentioned it and the band in words; what agents already posted on this message, each as "Companybot just said: …. If they asked something, answer it or build on it; don't start over." (picks run in turn, so a later one sees it); which agents went first (one answer is enough, unless the message asks each of them: everyone, a vote); then **where it stands** (`roomState`, read off the messages already in the prompt, no model call): the people's last 3 questions (messages with "?") and who first wrote after each, what the agent itself last said, and whether a person wrote after the message. A hop gets who named it instead, a handoff or ask its note, a DM "This is a DM with Ada.", an @mention "Ada @mentioned you."
  - **One answer, reaction first** (#177, #179). Every turn (an @mention, a DM, a pick, a hop, a handoff, an ask, an approval's follow-up, a wake) ends with the same required structured answer, the only way an agent posts or reacts in the chat it's answering: `{ emoji, new_point, to, message }` (core `postDecision`), in that order. `emoji`: its reaction, one emoji or null, decided first and on its own; `new_point` (≤ 15 words: what it'd add that nobody here has said, or empty; it gates nothing, it's there so the agent weighs what's new before it drafts); `to` (who should answer next: a person or agent here by name, or `"room"`; a person left something to answer or do is named, even when an agent is told too); `message` (Markdown; empty posts nothing). **The code rule** (core `responseOf`): it posts iff `message` isn't blank, and reacts iff `emoji` is one emoji (`isEmoji`), on the trigger message (`turns.finishReply` → `chatOps.reactOnce`: added, never toggled off; a wake has no trigger, so no reaction). Both, either or neither. No text is ever matched. Every prompt ends with the same note (`ANSWER_NOTE`): the fields, then when to write (answer what's for you; don't post what's answered, what's for someone else, people talking, or only an acknowledgment; a message for you that needs no words gets your reaction; nobody asked you: 1–3 sentences, one move). It's the AI SDK's `output: Output.object(...)` on the same `streamText` tool loop (`agent.ts`): tools run first, and only the final step must be the JSON, so a turn can look around before answering. The schema is the same in every turn (`to` is a plain string, matched to who's here in code), so it never changes the request's cached prefix. The answer is kept on the turn as made (`agentTurns.decision`), to debug what it chose. **Why reaction first:** with `respond` (post / react / nothing) after `new_point`, "thanks" in a 1:1 channel was ignored in production but passed the eval: the eval ran each step fresh, production replays the session, where earlier thanks showed as "(No reply.)" and the model copied it (3/4 said nothing). Reaction first plus reactions replayed (`[You reacted 👍]`, `replayOf`) plus "each time, even if you reacted to one like it before": 40/40. "Everyone give me a reaction" once got a 👋 reaction and a "👋" message from one agent, and "Give me a reaction" a 👀 on an earlier picture through `chat_manage`: there's no other way to react (no `chat_react`, no `chat_manage` `react`), so one turn makes one response of its own. A `chat_manage` send into the chat it's answering is a different thing: a post *for its person* ("post X here for me", #205), shown as “Companybot, for Dana”; the result says it's above the reply, so the reply doesn't repeat it. Why a required answer and not an optional post tool: an optional tool biases agents toward posting (tool-overuse; When2Speak 2026, CAPA 2026 "Speak for Me", Inner Thoughts CHI 2025: a required decision, made before drafting, works best).
  - **One display path.** Every reply starts as a hidden row (`quiet`: not in the timeline, unread or thread counts yet), so activity, approvals and files have somewhere to attach. **It shows the moment there's something to show** (`turns.ts` `show`, from `updateReply` and `finishReply`): its `message` starting to fill in, or an approval card. Then `quiet` is cleared, `publishedAt` set (it sorts there, below what it read) and it's counted (`countMessage`). **Streaming:** the runner reads the step's text through the output spec's own `parsePartialOutput` (what the SDK's `partialOutputStream` emits), in the same stream loop as the tool lines, and writes the partial `message` into the reply's stream (`replyStreams`) as it fills in; the JSON itself is never shown. When the answer is done, its message goes last, after the tool lines. Text before a tool call isn't shown: only `message` is, and only the current step's (a step that goes on to call tools drops its draft). No message: the reply stays hidden, though its stats and cost are recorded on it; a reaction alone is fine. **Invalid or missing answer** (no valid JSON at the end, and no card to decide on): "It didn't write a reply." where the reply would be, for every turn (`agent.ts` throws, `finishReply` shows the error). Tests: `answer.test.ts`.
  - **No claim check.** It once hid a pick's post when another agent posted there first, unseen. With replies streaming as they're written there's nothing left to hide at the end, and the case can't arise: one message's picks run one after another, each seeing what the others posted.
  - **`to`: talking to a coworker.** A shown reply whose `to` names another agent in the place wakes it next, as a hop on the post (`chains.handOff` → `passTo`, `dispatch.by` = the agent that named it, no dispatcher call): same chain, same limits (3 hops, 4 agent messages since a person wrote, rings, round trips), so a few turns at most before a person speaks. **Not if that agent is already answering there** (`answeringThere`): a turn of its own queued or running in the post's place or in the thread the hop would start (a pick waiting on the same message, a person's message to it). Its turn there answers, and the post is in its history next time. Before, Marlowe's "Companybot, go ahead and post the first hand" started a second Companybot turn in a thread while its pick on the person's "IDK you pick" ran at the top level: one agent, two answers at once, unaware of each other, contradicting each other (one dealt open hands, the other said it couldn't deal). Same for "who goes next" hops. An @mention is explicit work, so it isn't dropped: it waits (below). `to` a person: nobody is asked who goes next. `"room"`: as before.
  - The typing line shows every turn's step, or "Thinking…" (set when it starts), until its message starts; then it types like a person (any turn may say nothing, so none shows "typing" before that). What's shown is what hands off: `handOff` and "who goes next" read `shownReply` (the reply, unless it's hidden).
  - **Stats.** A dispatched turn's reply stats carry `dispatch` (`replyStats.dispatch`: model, band, probability, both probabilities, the decision call's cost, or `by` for a hop another agent named: "· via Companybot"). The line under the reply adds "· via dispatcher 84%"; its breakdown adds Picked by (Dispatcher (Jev)), Confidence ("84% reply · 16% quiet"; "—" from a language model; a hop's "90% go next") and Decision ("$0.00006, apart from this reply"). It's apart from This reply: the call is recorded once, as kind `router`, however many agents it woke, so Usage's Reply decisions still add up. @mention and DM replies have no `dispatch`, so no such rows.
  - Cost: kind `router` ("Reply decisions") in `usage`, for the message's author, with no agent (one call covers them all). About $0.00002–0.00006 a call on Jev, $0.0001 on Luna.   - **Model:** Jev (`typesafe-ai/jev-1.14.0`, `ROUTER_MODEL`), TypeSafe's decision model, by default: people with `workspace.manage` pick another in Settings → General → Agents in channels (`workspaces.routerModel`; `workspace.settings` offers `routerModels`: decision models first, then the gateway's language models). - The reply goes **where it was mentioned**: the main timeline, or the thread.
- **On its own, quietly:** a wakeup (a follow-up it set, [Architecture](architecture.md) → Wakeups) wakes it in the place it was set, acting for the same person, with no message posted. It ends with the same answer as any turn (above); with no message nothing shows.
- **Agents hand work to each other** by @mention, and ask each other privately: see [Agents working together](#agents-working-together). The reply router decides only on people's messages; after an agent's message, the dispatcher's "who goes next" question does.
- **One turn per agent per place** (chat + thread). Extra mentions queue in `agentTurns`; a person's message always posts. A turn stuck `running` over 5 minutes is failed and the queue moves on.
- **Stop** (#187): `turns.stop({ turnId })` ends a running turn early, for the person it runs for or anyone with `turns.stopAny` (off for Member by default). Convex can't kill a running action, so it's cooperative: the mutation only sets `agentTurns.stopping: { by, at }` (status stays `running`, so the queue still waits); the runner hears it on its next flush (`updateReply` returns `{ stopped }`, ~5×/s), a check on any stream part 1s after the last one (`isStopping`, so a long think that streams only reasoning still hears it; no timer), or after a step that called tools (a `stopWhen` condition). All of it is `turnStop` in `agent.ts`, one small helper; steering (#189, below) reuses its abort. While the model writes, it aborts `streamText` (`abortSignal`) at once. Once a step called a tool it doesn't abort: those calls finish (their results, activity lines and the step's cost are kept), and the run ends before the next step, so no later tool runs. Nothing already done is undone. `finishReply` then ends it like a failure without the error: the partial reply stays, `done` with `chatMessages.stoppedBy` ("Stopped by Ada" under it; replayed to the agent with "[Stopped by the person before you finished]"), usage saved, approvals settled, no handoff and no answer (a reply that was never shown stays hidden unless it holds a card to decide on; one already streaming keeps what it wrote, whatever the turn), an ask's asker hears "it was stopped", a wake's line says failed, and the next queued turn starts. A model call cut off mid-text may not report its cost (the AI SDK gives no usage on abort). It's a control only: a message saying "stop" is an ordinary message, never matched.
- **A burst gets one reply** (#188). A person's own message to an agent (its DM, an @mention: `agentTurns.person`) queues its turn `debouncing` and starts it only after a quiet window, 1.5s (`QUIET_WINDOW_MS`, core, the same one the dispatcher waits; `turns.startQueued` via `scheduler.runAfter`, no polling). A turn starts as **that person's newest queued turn there**, and `turns.mergeQueued` folds their older queued ones into it (`status: "done"`, `mergedInto`, no reply): its window (everything since the last reply started) holds all their messages, so each is answered once. Same for a burst sent while a reply runs: steering takes it in (below), else when it ends, one follow-up. Only the same person's: another person's message keeps its own turn (it acts with their permissions). Wakes, dispatcher picks and hops, handoffs, asks, approval follow-ups and automation runs aren't `person` turns: they start at once and never merge. During the window nothing shows on the typing line. Tests: `person()` (tests/person.ts) ends a sent message's window at once; `as.debounced()` leaves it to the timer (`bursts.test.ts`).
- **Your message steers the running turn** (#189; Grok Bot: "a direct message from you takes priority over background work and can redirect the current turn"). **Any** message a person sends in a place (chat + thread) reaches every agent reply running for them there, @mention or not: no mention is ever needed to redirect an agent that's replying to you. Their DM's agent and the agents they @mention get person turns as always; `turns.queueFollowUps` (from `messages.send`) queues a person turn for each other agent running a steerable turn for them there (same `actorId`). Every such turn, sent after the running turn's reply began, reaches that turn instead of waiting (`turns.steering`). Debouncing or not: the quiet window doesn't hold it back.
  - **At a step boundary** (`agentPrepareStep`'s async `steer`, every step but the first): `turns.steer` folds those queued turns into the running one (`status: "done"`, `mergedInto`, no reply), appends their messages to its stored `prompt` (core `steerNote`: "[Note from Companybot, not the person: Ada sent this while you were replying. It comes first…]" then their `[Ada (asker) …]` lines) and lists them on the turn (`agentTurns.steered`); the runner appends the same note as a user message. The AI SDK carries a step's messages into the next, so it's sent once, at the end: earlier messages are never rewritten and the cache holds. Their links join what `web.fetch` may open (`WebTurn.asked`).
  - **While it writes its answer** (a step with no tool call: no boundary left), the flush or the 1s stream-part check hears it (`updateReply` / `isStopping` return `steer`) and `turnStop` cuts the step off with #187's abort, `steered` rather than stopped. The runner drops that step's text (`parts.splice(stepStart)`, for every turn: a restart discards the partial, a stop keeps it), then **waits for the person to pause** (`turnStop.settle`): until their newest message there is `QUIET_WINDOW_MS` (1.5s) old (`turns.steerWait`), the same quiet window a burst gets. Then it takes all of them in at once (`turns.steer`) and starts a new `streamText` from what that step was sent plus the note: same turn, same reply, earlier steps (tool calls and results) kept, never redone; the step limit counts across runs (`agentStopAfter(done)`). So a burst ("help?" "with something?" "please?") is one restart, not one per message. Meanwhile the typing line says "Thinking…". A reply already shown stays shown while the new run streams; if that run ends with no message, it's hidden again. The wait is one `setTimeout` at a time, each at most `STOP_CHECK_MS` (1s), and it ends: no interval. Stop pressed meanwhile is heard on the next check and ends the turn (no restart; the message gets its own turn, as after any Stop); a turn failed as stale (`STALE_TURN_MS`) ends too. No count limit: a restart only redoes the writing step (cached, about $0.0003 on a small model), and it waits for the person to pause, so it restarts as long as they keep writing. The one limit is time, `STEER_WINDOW_MS` (60s into the reply), a safety net against something posting nonstop; past it the message gets the usual debounced follow-up. An answer asked before a restart is ignored (it can't cut off the new run). A cut-off step may not report its cost (as with Stop).
  - **The reply shows below what it read.** `turns.steer` moves a reply people already see below the messages it took in (`publishedAt` = now, chatOps `moveBelow`), at a step boundary or a restart, and moves its place's last activity with it (the chat's `lastMessageAt` on its `chatActivity` row, a thread's `lastReplyAt`; not counted again). A reply not shown yet is placed when it's shown (`show`). Before, a reply sorted where it began, above the messages it answered.
  - **Nothing answered twice, nothing lost.** The next turn's window is still "after the last reply began", minus that turn's `steered` messages; other people's messages in between stay in it. A message that arrives after the last boundary (a step that ended in text before it was heard) keeps its queued turn: the usual follow-up.
  - **Nothing hardcoded.** "stop", "never mind", "actually do X" are ordinary messages; the model decides. The guide's rule: a new message from the person who asked reaches you as a note and comes first; if it changes or calls off what they asked, say so in a short line and follow it, or stop; if not, carry on. No internal words reach the model: not "steer", "turn" or "dispatcher" (a test in core `turn-input.test.ts` checks the note, the guide and the routed prompts). Stop (above) stays the control that ends a turn without the model.
  - **Only the turn's own person**: another person's message acts with their access, so it keeps its own turn (or goes to the router). Steered (`turns.steerable`): any running turn acting for them that isn't a wake: their DM, an @mention, a dispatcher pick or a hop (it takes the message in and still ends with its answer, so "nvm" alone can mean it posts nothing, as for any turn), a handoff, an ask, an approval follow-up. Not steered: wake turns (incl. an ask's answer), automation runs, turns being stopped, stale ones. A queued follow-up that misses every boundary runs like the turn it was for: `routed` (with the pick's band, `costUsd: 0`, no `after`/`then`) after a pick or hop, so its prompt says nobody @mentioned it; but if it covers a direct ask too (an @mention merged in), `startNext` drops `routed`. It isn't a pick: `mightThisHour` skips `person` turns. An un-mentioned message still goes to the router for the other agents; `router.apply` skips agents it already reached (`hasTurnFor`), so none is woken twice. Pictures in a steering message are listed by file id but not sent as image parts. Tests: `steer.test.ts`.

## Private replies

**One rule:** a turn’s sources are everything it read, including its own chat when that chat is private or role-limited. A write may reach only an audience that can open every source, except in the asker’s own turn in their 1:1 DM with agents, where sources belonging only to that asker may be published. This includes their agent DM, personal memory, personal skills and personal connector data. Foreign automation runs and foreign wakeups never qualify, even in that DM; shared-chat turns also keep the full rule. To publish personal data widely, the person asks from their DM. These sources still count fully for context and for other people’s turns, and are shown on the reply wherever someone in the chat couldn’t open them. Group DMs, private channels (even with one member) and role-limited places keep the full rule. Shared readers (`requireType`/`requireRecord`/`typeVisible`, `requirePage`/`pageVisible`, `requireChat`/`canSee`) record restricted sources on `chatMessages.usedPlaces`. Agent reads run as mutations so the source is committed before the result returns to the model. Records record their database; pages resolve inherited access. Workspace connector calls (`connectors.forCall`) record the install id before use, with `allowedRoles` mapped to the same role audience as a database. This includes default Member access: a custom-role-only person must also have a role allowed by the install. Personal connector calls keep their existing one-person source. Reading a private reply or saved artifact carries its sources forward. Reading or copying a chat file records its chat before returning the file. File copies call that reader as a mutation. Claiming copied pictures into page or record bodies checks `writeSources` even if the body does not change; workspace, profile and agent pictures check the same shared audience. The origin chat stays in provenance; only that reply’s display label omits the chat it already appears in.

- **Posting isn't reading.** Opening a DM or posting in a chat (`chat.manage` `open_dm`/`send`, which check the chat with `requireChatToPost`) doesn't make it a source: nothing there reaches the model. The posted message still carries the turn's own sources. Only reads (`requireChat`, `canSee`, `chat.read`, search) record a chat. (#table-1: four DMs it dealt cards into made its channel reply “Only Jaden and Jaden and Jaden and Jaden can see this”, and every reply in its thread inherited that through the thread parent.)
- Each viewer must be able to open **every** recorded source now. Gaining a role later reveals earlier replies. Connector sources use the install’s current roles, so changing them also changes old replies and subsequent writes; a destination whose readers can all use the connector remains allowed. The visible reply says **🔒 Only Office and Owners can see this** (each person or place named once), and nothing at all when everyone who can see the chat can already open every source (`placeAudience`, the write fit check: your own DM, a channel limited to the same roles), so there's no lock and no Share there; hovering explains **Uses the Deals database** or **Uses the CRM connector**. For sources controlled by roles, the label and Share confirmation name the roles that can View every source, with Owners included; they do not claim that someone currently in the chat lacks access. Private-channel and DM sources also require membership: “Only people in #ops can see this”, or the matching roles in that channel when there is a role limit too. A viewer who cannot open the source sees “a private channel” or “a private conversation” instead of its name.
- Other viewers get only **🔒 Replied to Dana. Only Office and Owners can see this.** The server removes parts, attachments, previews, errors, stats and reactions before returning the row. Streaming, Activity, tool cards, approvals, typing steps, alerts, thread titles, record discussions and agent message search use the same audience. Server masking is a permanent security boundary for all clients, including alpha.9; it must never be removed as compatibility cleanup.
- Anyone who can see the reply and has Post in the destination can choose **Share to channel** once it finishes. The confirmation says **Only Office and Owners can see Deals. Share just the answer? Tool inputs, outputs and approval reasons stay private.** The message stores `sharedBy` and becomes visible to the chat, labeled **Shared by Dana**. Sharing releases only the shown answer. Activity (`forReply`, lists and pagination) and approval queries ignore `sharedBy` and check the original sources. Viewers without those sources get **Used 3 tools**, never tool labels, links, inputs, outputs or approval reasons. Source permissions and the private prompt stay private.
- This applies in all channels, DMs and side chats, including a one-person DM after the person loses access. The reply’s own chat is omitted only from its display label. Only the asker’s own turn in their 1:1 DM with agents may release their one-person data; cross-chat sends and edits retain all other restricted sources and are masked per viewer.
- Agents omit inaccessible replies and their stored prompts from session replay, channel history, thread context and dispatcher context.
- **No contagion in shared places** (decided 2026-11-04): anywhere but the asker's own 1:1 agent DM (`member.ownWrites`), replay leaves out replies, prompts and summaries whose sources don't fit everyone in the place (`placeAudience`, the same fit check as writes), and other agents' private replies in the new-messages window and reactions (the message the turn answers and its thread parent stay). So one private answer (a personal skill, a restricted database) doesn't make every later reply there private, and the model never sees that private history where others read the reply. Shared answers (`sharedBy`) still replay. In the asker's own DM, everything replays as before. Compacted summaries retain their source union (`summaryPlaces`); a viewer who cannot read one gets only the newest readable turns within `KEEP_TOKENS` (15,000 tokens). The fallback scans at most 200 turns or 4 MiB and leaves larger or older context out. Follow-ups and private agent asks carry sources through returned answers.
- All agent text writes use `writeSources` in `replySources.ts`: compare the destination’s roles and membership with every source. A refusal names the roles (and, for membership, the people in that chat); it does not offer an approval flow. This covers workspace/profile/agent names, instructions, channel topics, records, database/field metadata, views, page titles/bodies, team memory, skills and automation prompts. Reactions from the turn’s decision check the trigger message’s readers by the same rule and accept only one emoji. Invisible tag characters are allowed only in the three standardized subdivision flags: England, Scotland and Wales. Replies, tool cards, generated files and approvals carry the sources that narrow their audience on the server.
- Private artifacts keep `usedPlaces` across edits. The same `readArtifact`/`writeSources` helpers apply to personal memory, creator-only automations and destination places (pages, databases and channel metadata). Places retain a conservative union for their content and history; editing text never removes its sources. Reading or running an artifact passes those sources into the new turn. Losing a source hides the artifact; publishing it, changing place access or adding private-channel members must satisfy the saved sources too. Personal skills use these same helpers: loading one (`skills_load` → `skills.loadFor`) counts as a personal read, and changing Just me to Team checks the saved sources. Listing isn’t a read (#230): in the asker’s own agent DM the index lists their personal skills as before; elsewhere `installedSkills` leaves them out of the index (`unlisted`, id and name only, for a `/` mention they typed), so a channel reply stays public until a personal skill is actually loaded. Not listing beats listing untagged: a description could otherwise reach the channel in a public reply. No skill is auto-loaded; anything that ever injects a body must read through `readArtifact` too. Existing rows default to an empty source list; no migration is needed.
- Personal memory, personal skills, creator-only automation data and personal connector results carry a just-that-person source (their user id), so even workspace Owners cannot read another person’s facts. The label names that person, such as **Only Dana can see this**. A one-person DM also names its person; group DMs retain their membership audience. Connector metadata and tool results record this source before reaching the model.
- Stored prompts have their own `promptPlaces`. Sharing an answer never clears those sources. Replay includes a prompt only for a viewer who can open them all; steering adds its sources, and compaction includes prompt sources even when the answer was shared. Old prompts without provenance are omitted. Old summaries are untrusted until rebuilt by a compaction using the current source snapshot; a pre-deploy compaction’s text is discarded if it finishes later. The same bounded fallback applies, with no backfill.
- Deleted connector installs retain their install id with an Owners-only policy (an empty access list). Owners can still read and edit saved databases, channels and artifacts, run their saved automations, and explicitly share a reply; other roles lose access. Content writes compare the destination’s effective audience, including its saved sources, so a dead source does not prevent an Owner from editing that destination. A direct Owner access change can release deleted connector sources from that place’s `usedPlaces`, including inherited pages in a changed branch; all live installs and other sources must still fit the proposed audience. Non-Owners cannot release deleted sources. Original replies and other artifacts retain their provenance. Settings refusals explain the access change and identify the deleted connector when its label is available. Reinstalling the same connector makes a new install id and does not reopen the old source. Explicitly shared answer text stays shared; its tool details still follow the original sources. Existing replies with no recorded connector source cannot be retroactively classified.
- A non-Owner’s scheduled automation with a deleted connector source is skipped with a recorded failed outcome naming the connector and explaining Owners-only access. A metadata-only notice is posted in the maker’s agent DM, since source checks hide the automation itself; its prompt and source data are never copied into the notice. Workspace Owners’ automations can continue from their saved prompts.
- Source lookups are cached per query and viewer, with one shared page-state reader for all sources. Mutations read current access. Each write snapshots every source once with one page-state reader, loads destination members and roles once, then checks viewers in memory; deep page sources and large private chats do not multiply index reads. The 200-reply DM test uses distinct pages under a 31-ancestor chain and enforces Convex’s transaction limits. The app rail’s pins store local ids; record-title queries use the same database visibility reader.
- A message-posted automation copying an event into a DM stamps the watched channel’s sources on the trigger message. Its reply inherits them, so removal from the watched channel also hides the copied event and reply.
- Agent-written messages do not trigger `message.posted` (the existing loop prevention rule). No chat export endpoint exists; any future export must use the same viewer check.

Replies written before source tracking was deployed stay public: they have no recorded sources to check. On deployment, turns already running fail once when they call an internal read as a query; subsequent turns use the new mutation calls.

## Agents working together
Agents work together like people do, with the chat's own parts: @mentions, threads, DMs. No lead agent: the dispatcher already picks the best fit for people's messages. Backend `chains.ts`, limits and words in core `handoffs.ts`, the "who goes next" question in core `router.ts`. Research and agreed design: issue #115 (Grok Bot, OpenBot, MausBot, Buzz).

- **@mention = handoff.** When a turn's reply is done (`turns.finishReply` → `handOff`), every other agent it @mentions by full name (`mentionedAgents`: longest name first, not in code, not itself) gets a turn, acting for the same person (`actorId`, their permissions), triggered by that reply. It goes in the reply's thread, or a new thread under a top-level reply, so the top level stays the people's. In a channel any active agent can be handed to (it joins, as with a person's mention); in a DM only its own agents. The reply's `mentions.agentIds` records them. An agent writing a name without @ hands nothing.
- **A chain** (`agentChains`) is made at a turn's first handoff, for the person whose message started it, and counts its budget: agent turns, dispatcher hops, handoffs per pair of agents, an `epoch`. Each handed-off turn carries `agentTurns.chain`: `{ id, depth, path, epoch }` (`path`: the agents from the chain's start to it). Approval follow-ups keep their turn's chain.
- **Only a person starts one.** A turn hands off only if a person's message started it or its chain: wake turns (follow-ups, heartbeats, asks' answers), automation runs (their trigger has `automation`) and answers to asks never do. Their @mentions are text.
- **Limits** (`handoffLimit`, checked before each handoff, clearest first): a ring (the work comes back to an agent on its path through another: A → B → C → A); 2 round trips between the same two agents (4 handoffs; an ask counts 2); 10 agent turns per chain; 3 dispatcher-chosen hops; 4 agent messages in the place since a person last wrote there; asks 3 deep. **Any person writing in a place with chain turns** (`messages.send` → `resetChains`) gives its running chains a fresh budget and epoch (paths start over).
- **Paused, never dropped.** A handoff past a limit pauses the chain: a line in the place, written as the agent whose handoff was held (`chatMessages.pause`, @mentioning the chain's person so they're notified): plain words, no counts or jargon (`pauseText`): "Agents kept replying to each other, so they've paused." (too many hops or agent messages in a row), "Scout and Quill kept replying to each other, so they've paused.", "Agents kept working on this on their own…", "…kept passing this around…", "…kept asking each other…". Later handoffs while paused are held too (`agentChains.held`). `chains.decide({ messageId, action })`: **Let them continue** (a fresh budget; the held turns go ahead) or **Stop them** (they never run), only by the chain's person (the agents act for them). Agents read the line in their next turn's history, so they know why.
- **Who goes next.** In a "When relevant" channel, an agent's message in a chain that @mentions nobody schedules `router.next`: the same model setting and decision-model / language-model split as the reply router. Two questions: `next` (each other agent in the channel by key, `person`, or `done`) and `ack` (only thanks or an okay to another agent → nobody). It wakes an agent only at ≥ 0.6 (`NEXT_MIN_PROBABILITY`: Jev's `probabilities`, a language model's `confidence`), as a hop (`routed` and `dispatch` on the turn, through `agentChains.held` while paused). **A hop runs like a dispatcher pick** (it wasn't asked directly: its context line says who named it, with the same room state), and posts only if it adds something. Any turn's answer can also name the next agent itself (`to`, above). Handed work, it does it and posts the result; **if it's waiting on a person, that's theirs**: it never answers, acts or chooses for them (the hop note and the guide: "People speak for themselves"). Pip once ended "Your move on the button, Jaden!" with `to: "Companybot"` (the dealer); the hop told Companybot "it's talking to you… do it", and it posted "Jaden raises to 18", a move Jaden never made. **Handed back a result it asked for, it's done**: the person already sees it, so it never restates, sums up or confirms it, and posts only if it asked for it to do more itself (its message above says what for) (#172: Scout's "Yes, 5 × 5 = 25" got Companybot's "Confirmed: 5 × 5 = 25"). A hop that doesn't post ends the chain; a shown one's @mentions hand off as usual. Its cost is kind `router` for the chain's person. Mentions-only channels and DMs: only explicit @mentions chain.
- **Asking privately** (`chat.ask_agent({ agent, message })`, in the `chat` group so every agent with chat has it; `risk: none`: the other agent acts for the same person and asks for whatever it would): stores `@Quill <message>` as the asking agent (for the person) as a **quiet** top-level message in the asker's own chat: kept, never in the timeline, prompts or unread, like a wake's reply (the answer is an ordinary thread reply, so `chat.search` can find it). The asked agent answers in that message's thread (`agentTurns.ask`, depth + 1), told it's answering an agent for the person, with its reply and tool lines stored like any turn's; a quiet parent's thread gets no reply count, so it isn't in the sidebar's threads. No chat is made, so the sidebar gains nothing. When its turn ends, `answerAsk` wakes the asker through a `{ jobId }` wakeup (`wakeups.answer`) with the answer as `result`; that wake turn is **not quiet**: its reply, in the original place, finishes the reply the person was waiting for. The tool line is a chip ("Scout asked Quill →", tool part `opens`) that opens the thread **read-only** (`Message.ask` is set on its parent): who asked whom, the question, the answer, what the asked agent is doing now, and "To step in, reply in the chat." Anyone who can see the chat can open it, like the thread an @mention makes; the asked agent runs there with the chat's memory rules (team memories only with 2+ people). Asks from before this made a group DM; those stay as they were and can be closed. Refused in wake turns, automation runs and answers to asks, and past a limit, with the reason as the tool's error.
- **Prompt rules** (Buzz: "don't loop" isn't followable, a per-turn test is): the guide says @mention an agent only to hand it work, say what you need in one message, no bare acknowledgements or thanks to agents, and put a handed-off result in the reply itself, @mentioning whoever handed it over only if it needs the result to finish. A handed-off turn's prompt names who handed it over and says to treat it as the person asking, within what they'd want (`handoffNote`).
- **Usage:** each agent's turns count under it, for the chain's person, as usual; dispatcher calls under `router`.

## Onboarding
- **Welcome messages.** Making a workspace, or joining one by invite, has the workspace's main agent (its oldest active one: Companybot) post a fixed message (`welcomeText`, core `onboarding.ts`; backend `onboarding.ts`). No model call, so making a workspace costs nothing. The agent joins #general either way.
  - **New workspace: in #general.** The company intro is team knowledge, so everyone gains from it there. It says who the agent is, that in channels it answers when a message is for it or @mentions it, and asks for one @mention with a few lines about the company (what it does, customers, current focus), saved to team memory.
  - **Joining: in their DM with the agent.** One intro per person would bury #general. It welcomes them, says they can ask anything there and @mention it in channels, and asks their role and current work.
  - Uses the name they set, never their email. If memory is off, it promises no saving.
  - Their answer is an ordinary turn: the agent sees its welcome in the chat history and saves facts as on any turn. **Why not an interview:** a question-by-question script lived in one place's session, so a reply in a thread (a separate session) lost it, and every new workspace paid for a model call before anyone said a word.
- **Saves are never silent.** `memory.remember` and `memory.remember_for_team` label their tool line with what they saved ("Saved a personal memory: \"…\""), so everyone in a shared chat sees it, like Meta AI's "Memory updated". Only once saved: a refused save doesn't quote anything.
- **Tutorial.** People who join after this shipped get `members.tutorial` (`{ done, dismissed? }`); older members get none. Steps (`tutorialSteps`): @mention an agent, DM an agent, reply in a thread, and (only for roles with `members.manage`) invite someone. Each ticks off on the server when they do it (`completeSteps`, from `messages.send` and `workspace.invite`); a mention counts only if an agent answers it. `onboarding.tutorial` returns the steps, or null once all are done or hidden (`dismissTutorial`). The app shows all of them as a Getting started card at the bottom of the sidebar (`views/chat/Tutorial.tsx`), so it stays in view in DMs and Settings, where two steps take you; the current step says how. Its header folds it to a title line (a caret on the right; per computer) rather than dismissing: it goes away when every step is done. `dismissTutorial` stays for the API.
- **Why @mention from the first message:** it always gets an answer, in any channel (a "Mentions only" one too), so the welcome teaches it.

## Whose access
- The agent acts as **the person who triggered it** (`agentTurns.actorId`): their roles, connector connections, and what chats they can see. Re-read each call, as before.
- **Personal memories are read only in DMs with exactly one person.** Anywhere with 2+ people, agents read and change team memories only, so one person's private facts never land in a shared chat. They can still save a new personal memory there, always for the person who asked: it was already said in the chat, so nothing leaks, and it lets onboarding in #general build each person's own context.
- Chat tools (`chat.read`, `chat.search`) only see chats the actor can see. Search covers every everyone-visible public channel through one search-index query, plus up to 50 recent restricted chats (DMs, private and role-limited channels). Discovery reads activity-ordered seats and a bounded restricted-channel index, then checks live access. If discovery or search reads are capped, the result says which scope was searched; name a chat to search its history directly. Candidates are merged by exact-term/phrase relevance ahead of prefixes, with a small current-chat tie boost, rather than filling results in chat order. At most 600 candidate messages (100 public, with 500 shared across private chats) and 100 live reply checks produce 20 hits. Source tagging and private-reply masking apply to each returned hit.

## What an agent is fed each turn
Built for prompt caching: the cache matches an exact prefix, so nothing earlier in the prompt may change between turns. Same pattern as OpenClaw and Hermes Agent.

1. **System prompt** — agent instructions + platform guide (+ skills index). Nothing per-chat or per-turn, so it's byte-identical in every chat and caches across all of them. Tools in a fixed order.
2. **A session per agent per place** (`agentSessions`: agent + chat + thread), as Slack-style agents treat a thread as one conversation — append-only. **One agent runs one turn at a time in a chat** (`turns.busyElsewhere`, index `by_agent_chat`): a turn for it in another thread or the main chat waits, and starts when the running one ends (`startInChat`, its own place's queue first). Two at once answered the same conversation unaware of each other and contradicted. Each past turn replays as the model had it: the stored user message (`agentTurns.prompt`), then its tool calls and their results as real tool messages (`turnSteps`, kept per finished step by the runner, core `replay.ts`), then its answer as `assistant` (its decision's JSON, as it wrote it; with none, what its reply showed). Never notes in the agent's own words: the model took the old `[Tools you used: …]` lines for its writing and copied them into new replies. Results replay cut to 4,000 characters (it can call again for the rest); a held call replays with a "held for approval" result, since providers refuse a call without one; a stopped turn is followed by a note from Companybot. Someone else's turn replays its calls without their results (only the person it acted for sees those, as in the activity log), and without details only its widgets. Never rebuilt from current messages, so edits elsewhere can't break the cache.
3. **One new user message per turn**, appended at the end:
   - Where you are: chat, who's in it (people, then agents with their one-line role), who triggered you, memory mode. In a channel or group DM: "This is a team chat: talk to your coworkers, people and agents, by name."
   - Everything said in the place since the agent's last reply, including messages not addressed to it, each labeled `[Name time]` with its text as a JSON string. Names and topics lose brackets and line breaks, and the asker's lines are marked `(asker)`, so no message (or look-alike name) can fake a line from someone else: Anthropic's advice for untrusted text. The guide tells the agent only the asker can direct it, and compaction credits a request only to whoever's labeled line made it. A thread's first turn starts with its parent. Capped at ~50 messages; past that, a note says to use `chat.read`. Messages from the turn's person that arrive while it runs are appended later, after a step, never inserted earlier ([Steering](#when-agents-reply)): to the model's messages and to the stored prompt, so replays include them.
   - Each line ends with its reactions, Slack-style (`· 👍 Ada, Ben · 🐙 Companybot`, at most 3 names per emoji, then `+2`; core `chatLine`), built by `chatOps.reactionGroups`, the same data `chat.read` returns. Older messages reacted to since its last reply (its own reactions included: they land on a message the next turn's window doesn't hold) come first under "Reacted to since your last reply:", up to 10 (`turns.reactedSince`, reactions `by_chat`). All of it is in the new message, so the cached prefix is untouched.
   - **What it said elsewhere in this chat** since its last reply here (`turns.saidElsewhere`): its own shown replies in the main chat or other threads, the 3 newest within a day, each cut to 600 characters, under "What you said elsewhere in this chat since your last reply here… stay consistent with it". Each place keeps its own session, so this is what keeps the channel and its threads telling one story. Same privacy as the rest (`readReply`, the shared-place fit); never in a foreign run. The rest of the chat isn't pulled in: a thread turn gets its parent, and the guide says to `chat_read` the channel when it needs more (Slack's advice for agents: small context slices, fetch on demand).
   - Another agent's reply still being written shows its text so far; one with nothing to show yet (it just started over after a steer) is left out, not shown as `""` (a reply that said nothing).
   - The trigger message, marked as the one to answer. A turn queued by an approval decision gets the outcome (approved + result, failed, or denied) here instead.
   - Each message's files, after its text: name, type, size and file id (`<message id>/<n>`). If any are pictures, a line says whether they follow (the model sees pictures: the catalog's `vision` tag) or that it can't see them (so it says so when asked, rather than guessing). The newest 8 pictures under 5 MB and 8000px go after the prompt as image parts, each after its id (`buildTurnInput`'s `images`). Only that turn gets them: replays are the stored text, so the cached prefix stays the same and later turns have the agent's own reply about them.
4. **Compaction** — once the session passes ~40k tokens, older turns fold into the session's summary and a ~15k-token tail stays verbatim. One cache miss, then append-only again.
5. **Chat tools** — `chat.read` (older history or another place; lines list their files), `chat.search` (all public channels and bounded recent private history, with an explicit scope notice when limited), `chat.read_file` (a file's text by id, 20k characters a page: a PDF's pages, a Word file's paragraphs, each Excel sheet as CSV, a deck's slides in order, text as is (`core/src/file-text.ts`, readers in `office-text.ts`); `inside`, like `chat.read`). Granted like other built-ins (`chat.*`), so every agent with chat has it.

Every turn's message ends the same way: "This message from Ada came in:" and its line, then why it's here (one line: "Ada @mentioned you.", "This is a DM with Ada.", a handoff's or ask's note, or a pick's or hop's routed note above), then the answer note (`ANSWER_NOTE`); its reaction is in that answer too, there's no react tool. A **wake turn** has no trigger message: its new user message ends with a wake section instead (what woke it, the note, the record as it is now and a job's result fenced as data, repeats left), then the same answer note. A reply never shown stays a hidden (`quiet`) message for the session; replays give the model its own message, its tool lines and `[You reacted 👍]` (`replayOf`), so it sees what it did, not "(No reply.)", after a reaction.

Foreign automation runs, and wakes set in one (`wakeups.foreign`), skip session replay and summaries and see only their trigger or its own thread (a foreign wake: only its wakeup). Other history must be read through the consent-gated chat tools.

Code: `core/src/turn-input.ts` builds all of it (`systemPrompt`, `buildTurnPrompt`, `buildTurnInput`); change the strategy there. `backend/convex/turns.ts` runs the queue and reads turn context; `chatTools.ts` owns agent chat tools, using the shared channel lookup in `chatOps.ts`; `agent.ts` streams the reply.

Not a skill: chat is the platform, so every agent has it.

## Backend API (`backend/convex/chats.ts`, `messages.ts`, `files.ts`)
Queries return display-ready data (names resolved) so the app never joins tables.

**`chats.ts`**
- `list()` → `{ me, channels: ChatItem[], dms: ChatItem[], agents: AgentItem[] }`, or null before you're in a workspace. Only chats you're in, minus DMs you closed with nothing new since; `dms` includes agent DMs. `me` is your user id.
  - `ChatItem`: `{ _id, kind, name, topic, private, isDefault, title, agentId, members: Participant[], unread: boolean, mentioned: boolean, lastMessageAt, canManage: boolean, replyMode }`. `title` is `name` for channels, other participants' names for DMs. `agentId` is set for agent DMs, else null. `canManage`: a channel you can rename, delete and manage members of (`channels.edit`; #general can't be deleted); the sidebar's row menu uses it. `list` leaves `members` empty for channels (`get` has them): it reads only your own membership there, so someone marking a channel read doesn't re-run everyone's list.
  - `AgentItem`: `{ _id, name, description, dmId, unread, mentioned, lastMessageAt }` for each active agent. `dmId` is its agent DM with you, or null; the rest come from that DM.
  - `Participant`: `{ type: "user", id: Id<"users">, name } | { type: "agent", id: Id<"agents">, name }`.
  - Unread: the chat's newest main-timeline message is after your `lastReadAt`. `mentioned`: a message after your `lastReadAt`, in the main timeline or a thread, mentions you (not gated on `unread`: thread replies don't move `lastMessageAt`). Mentions are indexed in `userMentions` (one row per person mentioned in a message, removed when the message is deleted), so an old unread mention is found however many messages follow it. Opening the chat clears both; there's no per-thread read state.
  - Side chats are in `dms` with `parentId` (the DM) and `label` (the title), after the DMs and in the order they were made (so a new tab lands at the end); the DM and other chats have `parentId: null, label: null`.
- `createSideChat({ parentId })` → chatId. Under an agent DM you're in, not under another side chat. `renameChat({ chatId, title })` — side chats only.
- `activeThreads({ now })` → `{ chatId, messageId, title, lastReplyAt }[]`: threads replied to within the workspace's window (`workspaces.threadHours`: 1 hour, 1 day, 3 days, 1 week or forever (0), core `threadWindows`; default 3 days; people with `workspace.manage` set it in Settings → Workspace, "Threads in the sidebar", or agents with `workspace.settings`) in channels you're in, newest reply first (index `by_chat_lastReply`; each channel's 10 newest, 50 in all, so one busy channel can't crowd out the rest). `title` is the parent's first line. The sidebar nests them under their channel, like Discord's active threads, which leave the channel list after the server's auto-archive duration the same way. `now` is the app's clock rounded to 5 minutes (`useClock`): a Convex query re-runs when its arguments change, not as time passes, so passing the time in is what makes a quiet thread drop off on time (Convex's own pattern for time-dependent queries; a scheduled write per thread would be precise but far heavier).
- `browse()` → public channels you're not in: `{ _id, name, topic, memberCount }[]`.
- `get({ chatId })` → `ChatItem` plus `trash`, or null if you can't see it.
- `createChannel({ name, topic?, private })` → chatId. Name normalized to lowercase-dashed; refused if taken. Topics are at most 250 characters (core `TOPIC_MAX`, like Slack) for people, agents and tools alike; longer is refused, not cut. `migrations.channelTopics` cut older ones.
- `updateChannel({ chatId, name?, topic?, replyMode? })`. `replyMode`: `"mentions"` or `"relevant"` (When agents reply); `ChatItem.replyMode` is always `"mentions"` outside channels.
- `join({ chatId })` — public channels. `leave({ chatId })` — any channel you're in, except `#general`.
- `addMembers({ chatId, userIds, agentIds })` — channels only; by its members, or anyone who can manage it.
- `openDm({ userIds, agentIds })` → chatId. Finds or creates, and reopens it if you'd closed it. You're always included. The app's New message picks people and agents, so a group DM can include agents (they answer when @mentioned).
- `closeDm({ chatId })` — Close conversation: a DM or group DM out of your sidebar (`chatMembers.closedAt`), history kept. Not agent DMs, side chats or channels (leave those).
- `markRead({ chatId })` — sets your `lastReadAt` to now.
- `alerts()` → `{ workspaceId, chatId, messageId, threadId?, title, text }[]`: each chat's newest unread message meant for you (DMs and agents' replies once done, main timelines; @mentions from `userMentions`, the same rows as the sidebar's `mentioned`, main timelines and threads), filtered by your `notify` preference (`all` default, `mentions`, `off`). The app shows a desktop notification for new ones while it isn't in front (`notifications.ts`) and puts the count on the dock badge. Clicking one reopens its workspace if the window has switched since (only if you're still in it), then its chat, or the thread when `threadId` is set.
- `place({ chatId, threadId? })` → `{ summary, summarizedUpTo, compacting, costUsd }`, or null. Summaries belong to agent sessions, so only agent DMs have one (`summarizedUpTo` is a turn time); elsewhere summary is null. `costUsd` is the chat's (or thread's) running total.
- What changes with every message (the main timeline's `lastMessageAt`, the running `costUsd`) is on the chat's `chatActivity` row (chatOps `activityOf`/`setActivity`), never the chat, so a message doesn't re-run what reads only the chat (names, members, access: `browse`, `arrangements.get`, permission checks, every screen's `requireChat`). Read activity only where it's shown: unread and DM order (`list`, `get`, the workspace switcher), DM alerts, `place`. Made with the chat (`insertChat`); seats are read with `chatMembers.by_workspace`.

**`messages.ts`**
- `page({ chatId, threadId?, paginationOpts })` → the main timeline (or a thread) a page at a time, newest page first (`usePaginatedQuery`, core `MESSAGE_PAGE` = 50; the app loads older pages as you scroll up, and a thread's first page starts with its parent). Pages are cut by when each message was shown (`publishedAt`, set when it's sent, when a quiet reply is shown and when a reply moves below messages it took in; index `by_chat_shown`), so a reply shown late is on the newest page (until `migrations.messageShownAt` has reached a place, its reads use when each was made: one indexed read checks; COMPAT). Quiet rows (replies not shown yet, asks) are skipped by the index (`quiet` unset; other timeline reads use `by_chat_thread_quiet` the same way), so any number of them never makes a page slow or short; replies you can't open are in the page, masked. `list({ chatId, threadId? })` is the old one-array read (newest 200) for alpha.9 apps (COMPAT). Each page, and the app's pages put together, are in the order they were shown (chatOps `shownAt`: `publishedAt`, else `_creationTime`). A reply sits where it was made, unless it was shown later: a quiet reply when its decision posts it, or a reply that took in messages sent after it began (steering, below) moves below them (`publishedAt`), so it's always under what it read. The app sorts what it has loaded by `shownAt`, the key pages are cut by. An agent reading the chat (`chatTools.readFor`) gets the same order; DM alerts (`chats.alerts`) look back `STALE_TURN_MS` for a reply shown after you last read. Each `Message`:
  `{ _id, _creationTime, chatId, threadId, author: Participant, text, parts, status, error, stoppedBy: string | null, stats, editedAt, deleted, mine: boolean, replyCount, lastReplyAt, replyAuthors: Participant[] (up to 3), automation: { id, name } | null, reactions: { emoji, count, mine, people: Participant[] }[], pause: { status, for, by, canDecide } | null, records: RecordTagView[] }`; `text` and `parts` have tagged records as this reader reads them ([Record tags](#record-tags)). `pause` is set on a paused line ([Agents working together](#agents-working-together)); `chains.decide({ messageId, action: "continue" | "stop" })` answers it.
- `parts` includes approval cards. `replyAuthors` is stored on the parent as replies arrive (older parents fall back to reading their replies).
- `stream({ messageId })` → `{ text, parts }` while a reply streams, else null. The runner writes a streaming reply's content to its own `replyStreams` row (`turns.updateReply`, ~5×/s), and moves it onto the message in one write when it ends (`endStream`). So the flushes re-run only the streaming bubble's query, not every viewer's `messages.list`; the app's row subscribes to it while `status` is streaming, but shows nothing until the reply is done (the typing line under the composer shows the agent's steps meanwhile), unless it holds a permission card, which shows at once since the reply waits on it. Agents' prompts leave out replies still streaming.
- `send({ chatId, threadId?, text, mentions: { userIds, agentIds, recordIds?, skillIds? }, attachments? })` → messageId. `attachments`: up to 10 of your own unclaimed file uploads from this workspace (below), in order; with files, text may be empty. The app sends mention ids picked from the composer's menus; the server drops ids outside the workspace, agents in Trash, and skills not installed. `recordIds` are records the message references ([Data](data.md)), besides those tagged in its text ([Record tags](#record-tags)). `skillIds` are skills named with `/`: the trigger message's turn prompt tells the agent to load them with `skills_load` first (`PlaceMessage.skills`, from `turns.turnContext`). Schedules agent turns, and starts automations watching the channel (`message.posted`, top-level channel messages only).
- `edit({ messageId, text })`, `remove({ messageId })` — your own messages. Removing keeps the row (threads hang off it), clears text, parts and reactions, and deletes its files.
- `react({ messageId, emoji })` — toggles your reaction.
- `hidePreview({ messageId, url })` — takes down the card for one of your message's links (`requireOwn`, like `edit`; agents do it for their person with `chat.manage` `hide_preview`). The link stays in the text. The URL is matched as the card has it (fragment ignored); a link with no card is refused.

**`linkPreviews.ts`, `linkUnfurl.ts`** (link previews / unfurls)
- **Which links** (`previewLinks`, core `link-preview.ts`, pure and tested): `http(s)` only, first 3 distinct in order written, fragment dropped, none with a username or password, a dotless host (`localhost`, bracketed IPv6) or over 2,048 characters. Links inside fenced or inline code get none; `#/…` addresses and `companybot://page/…` links never match.
- **When:** `previewMessage` runs whenever a person's message text is set: `messages.send` and `messages.edit`. Never for text an agent wrote (replies, messages delivered with `chat.manage`, or its `edit` of its person's message, which keeps only the cards the message already had for links still in it): the server fetching a link a model wrote, unclicked, would let injected instructions carry data out in its query string. Not welcome messages or automation prompts either. Links already cached show at once; the rest go to `linkUnfurl.unfurl`, a Node action, in the background. An edit that drops a link drops its card.
- **Fetching:** through `fetchBody` (`webFetch.ts`), the same `safeFetch` + pinned-DNS request `web.fetch` uses, so private, loopback and metadata addresses are refused and redirects are rechecked. 5 s and 1 MB for the page, only HTML is read, decoded in the charset it names (`textOf`, core `safe-fetch.ts`). Details, first wins: Open Graph, then Twitter card, then `<title>` and `<meta name="description">`; site name defaults to the host without `www.`; title cut at 200 characters, description at 300. A page with neither title nor description gets no card.
- **Pictures are copied, never linked.** If the client loaded `og:image` itself, the page's server would learn every reader's IP address and when they read (the sender could track readers). So the action fetches it through `safeFetch` too (1 MB, 5 s), checks its bytes (`sniffImage`: PNG, JPEG, WebP, GIF; no SVG), and keeps it in Convex storage; the card's `imageUrl` is ours. No picture if it's missing, too big, or not an image by its bytes.
- **Storage:** `linkPreviews`, one row per URL per workspace (`by_workspace_url`), shared by every message that posts it. A row with details is reused for a day (and shown meanwhile; a failed refresh keeps the old card); one with nothing to show is tried again after an hour. Messages point at rows (`chatMessages.linkPreviews`: `previewId`, `hidden?`), so one message's hide never touches another's. `messages.list` returns `linkPreviews: { url, title, description, siteName, imageUrl }[]` without hidden ones, and none for a deleted message (`messages.remove` clears the pointers).
- **Late writes:** `save` (the action's write-back) drops everything, pictures included, if the message was deleted or the workspace is being deleted.
- **Not covered:** a link's own page isn't re-checked after the first read (a day later it's refetched only when another message posts it); previews of links posted in a channel stay in the workspace's cache after the channel is deleted (see [Architecture → Data lifecycle](architecture.md#data-lifecycle)).

**`files.ts`**
- Upload: `POST <site>/files/upload?workspaceId=…&name=…` with the sign-in token (`uploadEndpoint` gives the URL), the same path as pictures ([Architecture](architecture.md), Pictures): the type is read from the bytes (`sniffFile`, core `files.ts`): picture signatures, `%PDF-`, ZIPs told apart by the parts they list (`word/document.xml`, `xl/workbook.xml`, plus `[Content_Types].xml`; other ZIPs refused), else UTF-8 text with no NUL bytes that doesn't start like HTML or SVG, its kind from the extension. HTML, SVG and anything else are refused (415), so nothing a browser runs is ever stored or served. Stored with the sniffed type; the `uploads` row keeps `file` (name without folders or control characters, type, size, a picture's width and height from its header). 20 MB is Convex's HTTP body limit. The workspace must be named and theirs.
- A picture upload can't be attached and a file upload can't become a picture (`claimUpload` / `claimFiles` check `file`). Sending uses the rows up, so an id someone else learns is worthless; a refused message claims nothing.
- `discard({ file })` — drops one of your unclaimed uploads and its file (removed from the composer). Unclaimed ones also go with the hourly sweep after a day.
- `attachToReply({ turnId, storageId, name, width?, height? })` (internal) — puts a file the runner stored (`ctx.storage.store` with its real type) on the reply the running turn is writing; for agents that make files (`images.generate`, [Architecture](architecture.md)). Returns `{ attached: true, id }` (its file id, so the agent can edit it next), or `{ error }` with the file deleted if the turn stopped, its person lost the chat, the type isn't one messages take, or the reply has 10.

**`dictation.ts`**
- `transcribeAudio({ audio })` → text. `audio` is the recorded clip's bytes (webm/opus as Chromium records it). Empty clip → "".

**`typing.ts`**
- `ping({ chatId, threadId? })` — you're typing there. The app sends it on keystrokes, at most every 4s (`TYPING_PING_MS`, core `typing.ts`). Ignored in agent DMs (nobody else would see it) and for a thread that isn't one.
- `list({ chatId, threadId? })` → `{ people: (Participant & { at })[], agents: (Participant & { step: string | null, turnId, canStop: boolean, stopping: boolean })[] }`, at most 10 each, or nothing for someone who can't see the chat. People who pinged in the last 6s (`TYPING_MS`), you left out. A query doesn't re-run as time passes, so the app also expires each ping 6s after it saw it (its own clock, so a computer with the wrong time still works). `agents`: turns running there (index `agentTurns.by_chat`), minus ones stuck past `STALE_TURN_MS`, each with its current step (below) and whether you may stop it (`canStop`): the line shows Stop, then "Stopping…" ([Stop](#when-agents-reply)).
- **Steps** live on the turn (`agentTurns.step: { label, at }`), not its reply, so a run that posts nothing (a quiet heartbeat, a wakeup) still shows. The runner (`agent.ts`) sets it through `turns.setStep`: the newest tool call still running, in its tool line's words (`callLabel` + `toolLine`: "Searching records for Acme…"), else "Thinking…" (`THINKING_STEP`, core `action-words.ts`; set when the turn starts) while the model works; unset once its message starts, and cleared when the turn ends (`finishReply`, or failed as stale). Written only when it changes, before the next stream part, so it never lags the reply. Never the model's reasoning, and never a message: progress stays out of the chat.
- One `typing` row per person per place, overwritten by each ping, so one person can't grow the table. Sending a message deletes yours; an hourly cron deletes the rest (typed, never sent). Like Discord, there's no "stopped typing": a ping runs out.

## In the app
**Side chats** (`views/chat/ChatView.tsx`): an agent DM's title bar lists its conversations as plain text beside the agent's name, after a hairline (Grok and OpenBot have the same shape): Main (the DM), each side chat by title (the open one dark) with an × on hover that archives it after a neutral confirm (it's kept and can be restored), and + for a new one. Clicking the open side chat's tab opens its menu (Rename). The sidebar nests side chats under the agent with the same guide lines as threads under a channel, folds them with the agent row's chevron (synced per person and workspace), and offers New chat on the agent's row menu.

**The composer** (`views/chat/Composer.tsx`, extensions in `editor.ts`) is a one-block Tiptap editor, the same ProseMirror BlockNote uses for pages. Three triggers open a menu above the box (a fourth, for emoji, is below), keyboard-driven like Slack's (arrows, Enter or Tab to pick, Escape to close, mouse too): `@` people and agents (one space allowed, so "@Sam L" finds Sam Lee), `#` channels you're in plus public ones you aren't (agents read them with `chat_read`; the platform guide says a `#name` is a channel), `/` installed skills. A pick becomes an atomic chip (a `token` node: `kind`, `id`, `label`) that Backspace removes whole. The message is sent as plain text (`@Ada`, `#sales`, `/Proposal`) plus the ids by kind, so nothing else changes shape. A person or agent named in plain text, like a pasted `@Scout` that never became a chip, is mentioned too (`typedMentions`: the full name after `@`, longest first), since messages show it as a chip. Enter sends (or ⌘Enter, by the `sendWith` preference); Shift-Enter breaks the line. Messages show the same chips (`TokenText` in `Message.tsx`); `#channel` chips open the channel. `useDirectory` (`data.ts`) supplies all of it.

<a id="record-tags"></a>
**Record tags.** `@` also offers records: after the people and agents, a **Records** group from `records.mentionable` (the search index across the databases you can see, top 6), asked once typing pauses for 150ms (`RECORD_SEARCH_MS`) with one query in flight per pause; until it answers, the last query's records that still match stay listed, so the menu narrows as you type. Each row shows its database. A pick is a `token` of kind `record`, shown `@Summit Homes` and sent as `[@Summit Homes](record:<id>)` (core `record-mentions.ts`, `recordTag`), plus `mentions.recordIds`.
- **Stored as the id alone.** `messages.send` (and `edit`, and an agent's finished reply, `turns.tagReply`) keep a tag of a record the writer can see as `<record:<id>>` (`storeTags`), at most 20 a message (`RECORD_TAGS_MAX`); a tag of one they can't see, or a made-up id, is left as the name they wrote, as plain text. The name is never stored, so no place that reads a message's text (search, notifications, thread titles, automations, a future export) can show it to someone outside the database, and renames show everywhere.
- **Read per reader** (`recordTags` in `recordTags.ts`, one lookup per record per call). People: `messages.page`/`list`/`stream` return `text` and text parts with `@Summit Homes`, `@Private record` (a database they can't see, as link fields' locked chips), or `@Deleted record`, plus `records: { text, id, typeKey, state: "live" | "archived" | "locked" | "deleted" }[]`; locked and deleted ones have no id. The app's `splitTokens` makes those words chips (a message's own tags win over a person of the same name): live ones open the record, the rest are grayed (`recordTagButton`, `recordTagMutedClass`). Alerts, thread titles and `records.discussion` read the same. An app without chips (0.1.0-alpha.10) shows the same words as plain text. Agents (turn prompts, `chat.read`, `chat.search`, the dispatcher, `message.posted` automations): `[@Summit Homes](record:<id>)`, or "a private record"; a name read from a role-limited database counts as one of the turn's sources ([Private replies](#private-replies)).
- **Edits** (`retag`): the edit box holds the text as its writer reads it, so a record it tagged stays tagged while what they read for it (`@Summit Homes`, even `@Private record` after losing access) is still in the text, and is untagged once it's gone; a new tag as written is checked like a send. Its `recordMentions` rows follow.
- **Agents tag by choice.** The guide's Chat section says what `[@Name](record:<id>)` is and how to write one; the Databases section says to tag records a reply is about. Nothing looks for record names in what an agent writes. Tests: `recordTags.test.ts` (backend), `record-mentions.test.ts` (core), `tokens.test.ts` and `editor.test.ts` (desktop).

**Emoji.** One picker everywhere (`EmojiPanel.tsx`): search, categories, a skin tone, recents; the recents and the tone stay on this computer. The smiley button in the box opens it; a fourth trigger, `:` (at a word's start), opens it under the box driven by what you type after it (`:cat` narrows it; the arrow keys move a lit tile through the grid, named in the footer, and Enter or Tab takes it, `menuEmoji`; no match and it closes), and a finished `:smile:` turns into 😄 as you type it. A pick is the emoji itself in the text, not a chip (`emoji.ts` has the search and shortcodes, pure and tested). Reactions keep the quick row of 8 and add a + that opens the same picker. Pages' `:` opens it too. The data is `emojibase-data` (MIT), bundled so it works offline and loaded on first use as its own ~660 KB chunk (the app's start doesn't pay for it).

**Drafts.** What you've typed and not sent, chips included, is kept per person, per chat and per thread on this computer (`drafts.ts`) and comes back when you return. The composer's key is `draft:<workspace>:<chat>[:<thread>]` (`draftKey`); the text is saved under the person's id in front of it (`text:<person>:draft:…`, `textKey`), like its files (`files:<person>:draft:…`), so another account signed in here never sees it, and switching back finds yours. Until the app knows who's signed in, the composer shows and saves no draft. Drafts from before they were per person (bare `draft:` keys) are dropped once, when the sidebar starts (`sweepDrafts`), along with expired ones. Sending clears it once the message is in; a send that fails (the chat went to Trash, a file was swept) puts the text and files back. One nobody returns to expires after 30 days. A chat where you have one (or in a thread of it), or files waiting to send, shows a quiet "Draft" in the sidebar unless it's the open chat (`useDraftChats`). Not synced between computers.

**Dictation.** The mic button records a clip with `MediaRecorder` (stops by itself at 2 minutes) and the text lands at the caret. The mic is asked for one request at a time (`micOnce`): a second click while the permission prompt or the device is pending does nothing, and a mic granted after the composer closed or a recording started is turned off at once. Chrome's Web Speech API doesn't work in Electron, so the clip goes to `dictation.transcribeAudio`, which has AI Gateway transcribe it (`openai/gpt-4o-mini-transcribe`, about $0.003 a minute, billed to the same `AI_GATEWAY_API_KEY` as the agents; anyone in the workspace can use it, clips over 4 MB, under Convex's 5 MiB argument limit, are refused). Nothing is stored. Its cost goes to Usage as the person's "Dictation" (`usage.record`). The signed Mac app needs the microphone entitlement and usage text (`electron-builder.yml`, `resources/entitlements.mac.plist`).

**Sending.** Your message shows at once, dimmed, at the end of the chat or thread, with no hover actions ("Sending 2 files…" for files), until the server's list has it (`showSending` in `data.ts`, a Convex optimistic update; `useMutation` in `convex.ts` takes one). A send that fails drops it, and the composer gets the text back.

Under every composer, one line says who's typing there and what agents are doing (`TypingLine`, `views/chat/Typing.tsx`). Working agents' avatars lead it (tiny, stacked). One agent shows its step, updated as it changes (no timed rotation): "Companybot: Searching records for Acme…"; while it writes, it types like a person ("Companybot and Ada are typing…"). Several agents read "2 agents working": hover (or click) for each one's step and a link to Settings → Activity. People typing keep their place after a dot ("Companybot: Thinking… · Ada is typing…"). Like Buzz's "{Agent}: {step}" chip by the composer. Its space is always kept, so the box doesn't jump. A thread has its own line. The line is its own component, so its timer doesn't re-render the messages.

**Files** (`views/chat/Attachments.tsx`): the paperclip in the composer, pasting, or dropping files on the chat or thread attaches them. Pasting from Excel, Word or Keynote pastes the text (as plain text), not the picture of it those apps also copy; a screenshot, a copied picture, or files copied in Finder attach (`pastedFiles`, `composerFiles.ts`). Each uploads as it's added, showing a picture or icon, name, a progress bar (XMLHttpRequest; fetch can't report it) or its error, and a remove button (`files.discard`). Send waits until they're uploaded. Like the draft, a composer's files stay with its chat or thread (`composerFiles.ts`, keyed by person and the draft's key): leave and come back and they're there, and one still uploading lands where it was added. Uploaded ones are also kept on this computer under the person's id, so they come back after a restart and another account signed in here never sees them; they expire with their upload, a day after it (`UPLOAD_TTL_MS`). So nothing is stranded on the server counting against the 20 unclaimed uploads a person can have. The app checks each file's bytes before uploading (`fileError`); the backend checks again. Messages show pictures as thumbnails (click: larger, over everything) and other files as chips (icon, name, kind and size) that open the file in the browser.

**Link previews** (`views/chat/LinkPreviews.tsx`): compact cards under the message (and its files): site, title (two lines), description (two lines), a 64 px picture. The whole card is a link; the app's main process opens web links in the browser. The sender sees a × on hover (`message.mine`) that calls `hidePreview`.

**Agents working together** (`Message.tsx`): a paused line shows as a quiet divider, not a message: "Agents kept replying to each other, so they've paused." then Let them continue and Stop them for the person the agents work for (they wrap together onto their own line), "Waiting for Ada" for others, then "Continued by Ada" / "Stopped by Ada". An ask's tool line is a chip, "Scout asked Quill →", that opens the exchange in the thread panel, read-only (`ThreadPanel` with `Message.ask`): titled "Scout asked Quill", no composer, no hover actions; permission cards still work.

**Sections** (`Sidebar.tsx`, backend `sidebarSections.ts`): channels in no section sit at the top; under them come the sections people add, like Discord's categories, then Direct messages. One layout for the workspace: people with `sidebar.arrange` add one (New section in the + beside Chat), make a channel in it (its hover +), rename it in place or delete it from its ⋯ (its channels go back to the top), drag channels in, out and between sections, and drag a header to move its section. A channel is in one section at most. Anyone folds a section for themselves (`folded`); folded, it keeps the open and unread channels, like Direct messages. Each person sees only channels they're in; a drag leaves the ones they can't see where they are. Without `sidebar.arrange`, sections are read-only and an empty one isn't shown.

**Close conversation** (`Sidebar.tsx`): on a DM or group DM's ⋯ menu, beside Mark as read; closing the open one goes to Chat.

**Channel details** (`views/chat/dialogs.tsx`, click the channel name): anyone with `channels.edit` edits the name, topic and **Agents reply** (Mentions only / When relevant, with a line saying what each does) and saves them together; others see "Agents here also answer…" when it's on.

Click a name or avatar for a profile card (`views/chat/Profile.tsx`, from `workspace.team` and `chats.list`): name, email, roles, local time, Message.

## Permissions
`channels.edit` (Member starts with it): create, rename, set topic, set when agents reply, delete, and add or remove members of any channel you can see. Making a channel gives no extra rights over it.

Agent delivery and management: `chat.manage` finds the directory (people, agents, or invites, for `members.manage`), lists joined chats, opens fixed-participant DMs (the person is always in it; with nobody else it opens the agent's own DM with them, never a DM with themselves; never with another agent: agents have no DMs with each other, so `open_dm` refuses one and `messages.send` refuses an agent posting in a DM that has agents but not it, pointing to an @mention or `chat.ask_agent`. Decided 2026-11-06 after #table-1, where Companybot "dealt private hands" into Jaden's DMs with Pip, Marlowe and Roxy: no agent saw them, Jaden read them all), hides a link preview card on the person's own message (`hide_preview`) and sends to a chat id/#channel and optional thread. `channels.manage` browses public channels, pages participants, creates/renames/sets topic, adds/removes participants, joins/leaves. Shared operations serve the app and tools; `chats.removeMember` allows managers only and protects people in #general. Delivery stores `authorAgentId` and `actingFor`, displayed as “Companybot, for Dana” with both avatars (the agent's, the person's over its corner: `PairAvatar`). The author comes back as the agent plus `for` (the person); `chatOps.label` joins them for text and prompts. Each name opens its own card; the avatar's card has a “Sent for Dana” line. To the person alone (a DM with no other people) there's no `actingFor`: it's just the agent talking; it never queues turns or fires automation events. Its tool line is a chip that jumps to the message it sent (`opens` with `kind: "message"`, or the thread it went in). The stored label names chats by id (“posted in a chat”); `messages.sentLines` names the place per viewer when they can see it (“Companybot posted in #sales →”, “posted in your DM with Bob”, “sent you a DM”), else keeps the stored words. The tool's result says where it went too (`posted`: “Posted in Jaden's DM with Bob, as you for them.”; `open_dm`'s `note`), so later turns know what they sent where. Back-to-back lines that read the same show once with a count (“Opened a DM ×4”). It can send into the chat and thread it's replying in too (“post this here for me”): the result then says it's posted above its reply, so the reply doesn't repeat it. That's a post for the person; the agent's own reply and reactions only come from its answer, and `chat_manage` doesn't react. `chat.read` and `chat.search` also accept chat ids for DMs. Deleting a channel moves it to [Trash](data.md#trash), with its messages and members; #general stays. Agents ask first to delete a channel.

Search audience and seat activity fields are backfilled by `migrations.searchAudience`, `searchChats`, `moveSeatActivity`, and `discoveryChatActivity` (COMPAT(0.1.0-alpha.10)); run `migrations:runAll` after deploying. New messages set their audience immediately. Access changes reindex small histories and seats inline, continuing large histories in bounded scheduled pages; live permission/source checks remain authoritative during this refresh. Discovery activity lives on `seatActivity`, apart from `chatMembers` read state. Public messages do not update it. Agent seats have no discovery row and do not count toward the threshold. Restricted chats with at most 100 user seats update every activity row immediately on each send. Larger restricted chats set one pending marker on `chatActivity` and schedule one refresh after 60 seconds; subsequent sends only advance that hot document. The worker pages through 100 user activity rows at a time. If a send arrives during its sweep, the next pass starts no earlier than 60 seconds after the current pass began, keeping writes to about one pass per minute while discovery catches up with roughly 60 seconds of lag. Visibility changes still refresh audience flags. `seatActivity` is removed with its seat, channel, workspace or erased user; read-state changes never write discovery documents. Channel discovery reads the indexed `chatActivity` timestamps through `activityOf`/`setActivity`, rather than legacy timestamps on `chats`.

Activity reads past masked replies until it has enough visible entries or spends its 1,200-row budget. Settings shows a history-limit notice when discovery or the read budget cuts it short. The installed-client array API always returns the entries it found (possibly an empty array); `activity.recent` retains the limit flags for the current Settings screen. The cursor-based `activityPage` may return an empty page after masking: its cursor and `isDone: false` are preserved so callers can continue to older history without losing entries.
