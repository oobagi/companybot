# Data

Databases and their records: records (clients, deals, tasks, calls…), their fields, links, and history. Built so every record feature in [Product](product.md) sits on it without a rewrite. Code: `core/src/records.ts` (rules), `backend/convex/recordOps.ts` (storage), `records.ts`, `recordTypes.ts`, `fields.ts` (API).

## Model
- **Database** (`recordTypes`) — a collection of records anyone with `fields.edit` creates. New workspaces have none. Existing databases keep their stable keys, fields and links; no code catalog is needed. Its **Who can access** list (`access`; [Permissions](permissions.md#who-can-access)) rules its records, fields, views, history and record pages: `requireType`/`requireRecord` take the level needed, and reads across databases (search, `linked`, Activity, Archive, refs) drop the ones the person can't see (`typeVisible`). A link into one shows as a locked chip; linking a new record needs View in its database, and links a record already has stay when someone edits it.
- **Field** (`recordFields`) — one piece of info in a database: added by the team ("Stage", "Roof type"). Kinds: text, number, currency, date, checkbox, choice, email, phone, url, user (a teammate), link (another record). Choice, user and link can hold several (`multiple`). A field may have an `icon`: an id from core's `fieldIcons` (64 business icons; the app maps them in `icons.ts` `fieldIconSet`), checked by `fieldConfigError`; without one it shows its kind's. A choice option may have a `color`: one of `optionColors` (Notion's ten: default, gray, brown, orange, yellow, green, blue, purple, pink, red), drawn as soft tints (`--color-option-*` in styles.css). A new option without a color gets the next in turn by its position among the field's options (`autoColor`); an existing option sent without one keeps its own, so older apps (alpha.10) and agents naming options by label never wipe colors. Options from before colors have none and show as default until someone picks one. Fields themselves have no color. Every database has `name`, the record's title (always text). Every setting can change later, kind, one/several and linked database included: see Changing a field.
- **Record** (`records`) — `values`: field key → value. Keys come from the label once ("Roof type" → `roof_type`) and never change, so renames and kind changes don't touch views or agents' references. Empty values (and unchecked boxes) aren't stored. Dates are `YYYY-MM-DD`; currency is `{ minor, currency }` (see Money); choices store the option's id, so renaming an option changes nothing.
- **Index** (`recordValues`) — one row per value of a live record: text and ids in `str`, numbers in `num`, links in `ref`. Lists filter and sort through it; never read for display. Text is case-insensitive: up to 100 chars it's its own key; longer, its first 80 chars plus a hash of the whole, so sorting goes by the first 80 and exact matches are re-checked against the value.
- **History** (`recordHistory`) — every change to a record, field, database or saved view: action, each value's old → new, `userId`, and `agentId` when an agent did it for that person. Feeds a record's history and Settings → Activity (`records.activity`).
- **Saved view** (`databaseViews`) — a named filter, sort, ordered columns and layout (table, or a board grouped by a choice field) shared with the workspace. Indexed by database (`by_type`); its lifecycle is `childOf: recordTypes`, so deleting a database in a cascade deletes its views. Removing a member keeps shared views.
- **Page body** — every record has a page under its fields (notes, plans), created on first write. Same editor, history and agent tools as standalone pages: [Pages](pages.md).
- **Follow-ups** (`wakeups` with `recordId`) — an agent checking back on a record later ([Architecture](architecture.md) → Wakeups). The record screen lists pending ones, cancellable; the agent gets the record's current values when it wakes. Deleting the record (or its database) forever cancels them; one in Archive holds them until it's restored.
- **Mentions** (`recordMentions`) — a chat message that tags a record, like tagging a person: picked from the composer's @ menu, or written by an agent (`[@Name](record:<id>)`; [Chat → Record tags](chat.md#record-tags)). One row per record per message, kept in step on send, edit (`syncRecordMentions`) and delete. `records.discussion` lists the ones you can see; the record page shows them as **In chat · Tagged in N messages**.

## Money
- **Every amount carries its own currency** (ISO 4217), like Stripe and HubSpot: `{ minor: 10000, currency: "USD" }`. `minor` is a whole number of the currency's smallest unit (ISO 4217 exponent, like Stripe): $100 is 10000, ¥100 is 100, KWD 1.250 is 1250. `minorDigits(code)` gives the decimals (0 for JPY, KRW, CLP…; 3 for KWD, BHD, OMR…; 2 otherwise); `formatMoney` shows an amount in them.
- **The workspace's currency** (`workspaces.currency`, default USD; Settings → General, `workspace.manage`) is only the default for new amounts, and later for totals and reports. Changing it never touches existing amounts: $100 stays $100. The app warns first if amounts exist ("Existing amounts stay in USD. New amounts will use EUR.").
- **Input:** `1250.50`, `"$1,250.50"` or `{ amount }` use the workspace's currency; `"EUR 12.50"`, `"12.50 EUR"` or `{ amount, currency }` name their own. Rounds the exact decimal to that currency's decimals, half away from zero (JPY 99.5 → ¥100, KWD 1.2345 → 1.235); must stay within safe integers.
- **Comparing:** amounts compare only within one currency. Index rows are `str` = code, `num` = minor units, so sorting groups by currency code, then amount. A filter picks one currency: the workspace's, unless its value names another (`gte: "USD 0"`); a range mixing currencies is refused.
- History and undo store the whole value, so the currency comes back with it.
- **Later:** exchange-rate conversion (totals across currencies, "sort by value in EUR").

## Why one generic records table
Separate tables per type (Night Owl's way) means a migration for every new type or field, five copies of "who changed what", and agent tools per table. One table with type definitions gives one API, one history, one index, one set of agent tools for every type, and new types/fields are rows.
- **Convex limits:** 32 indexes per table and indexes are fixed at deploy, so custom fields can't each get an index on the record. The `recordValues` side table gives every field an index with 4 indexes total, no per-workspace schema.
- **Query speed:** lists page straight off an index (`by_type`, `by_type_updated`, or `recordValues` by field), never a table scan, and every request does a fixed amount of work. Fine at 100k+ records per workspace; see Lists.
- **Filtering and sorting:** the same path for every field.
- **Migrations:** adding a field or type writes one row; existing records just have no value yet. Deleting a field (to Trash) keeps every value (restoring brings them back); deleting it forever strips them from every record, so a new field can reuse its key. A field's key never changes. Changing its kind rewrites its values in background batches (Changing a field), never in one transaction.
- **Heavy data** (call recordings, transcripts, invoice lines) doesn't go in `values`: it goes in its own table keyed by `recordId`.
- **Size and read budgets:** a record's values are capped at 128 KB (`RECORD_MAX_BYTES`). History stores a change's old and new values together, so an entry stays under ~260 KB, far below Convex's 1 MiB document limit. Pages are capped (50 records, 20 history entries) so a page stays under the 16 MiB read limit. Names for links and people are resolved once per page, up to 200 or 4 MB of reads; the rest come back in `unresolved` for `records.refs`.

## Lists
`records.list` takes any number of filters (all must match) and one sort. Campaigns, pipelines, saved views and agent queries all sit on it.
- **Conditions:** `eq`; `in` (any of, up to 50) on choice, person and link fields; ranges (`gt`/`gte`/`lt`/`lte`) on single-valued number, amount and date fields; `empty: true/false`. Fields holding several values (tags) take `eq`, `in` and `empty` only. Up to 10 filters.
- **Plan:** one index stream *drives* the scan and sets the order; every other condition is checked on the record itself (`recordQuery.ts`). The driver is, in order:
  1. the sort field, if sorting by a field (a range on it narrows the stream). Records without a value for it come after the rest, newest first: the name rows (every live record has one) walked beside the field's rows by creation time (`by_field_at`, both in the same order), so they're found from index rows alone. A page can run from one part into the other; a filter that needs a value on the field (a range, `eq`, `empty: false`) skips the second part, and `empty: true` lists only it;
  2. `updatedAt` or `createdAt`, if sorting by one (the records' own indexes);
  3. the `eq`/`in` condition with the fewest index rows;
  4. else the range or `empty: false` condition with the fewest rows;
  5. else every record by creation time, newest first (through each live record's name row, `by_field_at`; lists of records in Trash read the records).
- **Selectivity is estimated cheaply:** the candidates share 400 index rows of counting (one filter counts up to 400, ten up to 40 each); the smallest wins, ties go to the first given. Equality always beats a range, even a smaller one, so a list's order depends only on the query, never on the data: equality rows are kept in creation order (`at` on `recordValues`), so equality-driven lists stay newest first, while a lone range lists in that field's order. To drive from a range in a known order, sort by its field.
- **"Any of"** reads one stream per value and merges them by creation time (each stream keeps what it has read until it's used), so a record holding two of the values comes once.
- **Ties:** `recordValues` indexes end in `at`, then `recordId`, so records sharing a value and creation time (imports keep creation times) page in id order like any other key. Lists read straight off `records` (records in Trash, or sorted by `updatedAt`) can't index `_id`, so a group tied on every key is read whole; one larger than a request can read (~20 big records) is refused rather than skipped.
- **Links to records in Trash** are checked against the target's index rows (one in Trash has none), not the whole record, and its database is checked once per request, so link filters stay inside the read budget. `empty` on a link field looks only at live targets, for one link or several.
- **Bounded work:** everything a request reads goes through one budget: link targets, counting, index rows and records. At most 1,000 index rows (in chunks of 100), 2,500 index ranges and 6 MB, and at most 50 records back. No record is read without room for the largest possible one (256 KB), so a request never passes the budget by more than one small read; the rest of Convex's 16 MiB and 4,096 ranges is left for resolving names (`toRows`). If the budget runs out first, it returns what it found, maybe nothing, with `isDone: false` and a cursor to go on, like Convex's own filtered pagination. **The app and agents must keep asking while `isDone` is false, even after a short or empty page.**
- **Cursors** hold a fingerprint of the query as resolved (workspace, type, in Trash or not, sort, and filters with values as stored, so `eq: 100` in USD and in EUR differ), the plan and the last key read, so pages never repeat or skip a record, even with several-value fields and records changing between pages (a record that changes moves like it would in any Convex list). Plans are fixed for the whole list. A cursor used with a different query is refused ("That page is out of date").
- **`endCursor`** (how `usePaginatedQuery` keeps pages stable) still returns at most 50 records. A page that grew past that comes back `pageStatus: "SplitRequired"` with a `splitCursor`, and the client splits it.
- **Performance:** cost is the rows the driver reads, not the size of the workspace. A selective condition (one owner, one client, a rare stage) finishes in one request. A rare *combination* of common values (status = done AND owner = Ben, 1,500 rows each, 4 records in both) takes one request per ~1,000 driver rows, mostly short pages; tested on 3,000 seeded tasks under enforced limits (`pnpm test:scale`). That's fine for a list the person scrolls, and for agents and campaigns that page in the background.
- **Not used, on purpose:**
  - *Search indexes with `filterFields`* need a text term, rank by relevance (no field sort), and cap results at 1,024: wrong for lists and campaigns. They stay for `records.search`.
  - *Precomputed combined keys* (type + status + owner) need a fixed set of fields per key, but fields are per workspace and change at runtime, so each would be a per-type setting, rewritten on every edit, for a speedup only rare combinations need. Worth adding as a purpose-built index when one hot view (a pipeline board) shows up slow, beside the generic path.
  - *Intersecting two index streams* (leapfrog) only helps when values cluster, which CRM data rarely does; checking the record is as cheap and simpler.

## Rules
- **Access:** every member reads every record. `records.edit` (Member starts with it): create, change, delete, restore, undo. `fields.edit` (Member starts with it): add, change and delete any field, and create, rename and delete databases. Making a field gives no extra rights over it. Shared views use `records.edit`.
- **Agents act as the person who asked** (`Who = { member, agentId? }`), like memory and connectors: the person's roles decide (read fresh each call), history names both. See Agent tools.
- **Edits are field-level patches:** `records.update` sets only the keys given (null clears), so two people editing different fields never clash. No version check; history holds every old value.
- **Undo** (`records.undo`) reverses one entry: delete ↔ restore, or old values back. Refused if any value it touched has changed since, or it was already undone. Old values go through the same checks as any write, against the fields as they are now: no fields, options or link targets in Trash or retired. The undo is itself a history entry (`undoes`).
- **Archive keeps content** (see Archive). A record in Trash keeps values and history but leaves lists, filters and search (its index rows are dropped, and rebuilt on restore). New links can't point at it. A database in Trash hides its records the same way (their rows stay; search, `linked` and links skip them).
- **Links to a record in Trash stay stored** (rewriting every incoming link could be thousands of writes in one mutation). Queries treat the target as gone: `refs` marks it `archived` (the app shows "(archived)", not clickable), filtering by it and `linked` return nothing. Restoring it brings everything back. Once deleted forever, links stay stored and read "Deleted record".
- **Removed options are retired, not deleted.** Records keep them (ones in Trash too), and filters still find them, but they can't be set again, by a person, an agent or an undo. Sending one back (same id or label) revives it. Restoring a record rebuilds its index from the current fields; values on retired options or fields in Trash stay, as on any live record.
- **Validation is in core** (`normalizeValue`, `fieldConfigError`), so the app, agents and future imports share it. The backend adds what needs the database: users in the workspace, link targets of the right type, choice options in use (can't be removed).
- **Automation hook:** every change goes through `logChange` (`recordOps.ts`). Record triggers ("deal moved to Won") fire from there via `fireEvent`; not wired yet.

## Changing a field
Every setting of a field can change after it's made, like Notion's Edit property, but undoable. Name and options are plain edits. Kind, holds one ↔ several, and the linked database rewrite every record's value, so they go through one path (`backend/convex/fieldChanges.ts`, rules in `core/src/field-change.ts`, shared by the server, the app's preview and agents).
- **Rules** (`convertValue`): anything → Text keeps how it reads (choice labels, names of people and linked records, "$1,234.56", "Nov 15, 2026", "Yes"). Text → Number, Amount, Date, Checkbox, Email, Phone or Website parses it, forgivingly: "1,234" and "$1,234.56" are numbers; an amount uses the workspace's currency unless the text names one ("EUR 12", "40 gbp", "€5"; "$" is the workspace's currency if it's a dollar, else USD); dates read ISO, "11/15/2026" (month first), "Nov 15, 2026", "15 November 2026"; checkboxes read yes/true/1/x/✓ (no/false/0 as unchecked). Amount ↔ Number keep the amount; Number → Checkbox is checked unless 0. → Choice makes one option per distinct value, matched in any case, up to 100 (`OPTIONS_MAX`; text over 100 characters doesn't fit); options typed in the form come first. → Person matches a teammate's name or email (one match only); → Link matches a live record's exact name in the chosen database (one only). Text becoming several splits on commas. Several → one keeps the first value; one → several wraps it. A link to another database matches by name, like Text → Link. What doesn't fit is cleared and counted. Name stays text.
- **Preview** (`fields.preview`, `previewChange`): Edit field saves a lossless change (one → several, anything → text) without a word, like Notion; it only warns, in one line, when values will be cleared or cut or a view loses a filter. The preview converts the first 500 live records with a value (≤ 4 MB read) with the real lookups and says how many convert, how many are cleared (with up to 5 examples), how many keep only part (several → one), the options → Choice will make, and which saved views lose a filter, sort or grouping. `more` says there are other records; they follow the same rules.
- **Running it** (`changeField`, `step`): the field takes its new setup at once and gets `change` (a `fieldChanges` row), which locks it: no record writes to it, no edits, no archiving and no second change until it's done. A scheduled mutation converts up to 100 records (≤ 4 MB) a run, oldest first through `records.by_type_created`, records in Archive too, rebuilds the field's `recordValues` rows for live records, saves each changed record's old and new value (`fieldChangeValues`), and schedules the next run. Records sharing the last one's creation time go in the same run, so "converted through" (`doneThrough`) is exact. The last run unlocks the field. A run that fails is started again by the 15-minute sweep (`fieldChanges.sweep`); a run commits whole, so running it again is safe. → Choice options grow as new values appear.
- **While it runs**, reads (`toRows`: the app, agents and old apps alike) show records it hasn't reached converted on the fly by the same rules, without lookups: a value needing one (a name for text, a teammate or record by name) reads empty until its batch. So every reader gets values that fit the field's kind. Lists filter and sort through the index, which fills in batch by batch: results grow as it converts. The column header and record page say "Converting…" and its cells are read-only.
- **Views:** at the start, saved views convert or drop conditions on the field, quietly, like Notion. A text "is X" becomes the option X when the field turns into a choice with that option, and a single option becomes its label going back (core `convertCondition`). Others that no longer fit are dropped (value conditions when the kind or linked database changes, ranges when it becomes several; "is empty" / "is not empty" always stay), as are a sort if it's no longer sortable and grouping if it's no longer a single choice (the board then falls back to the first choice field, or offers to add one). The field dialog lists the views that lose something before you confirm. The All tab's shared grouping is cleared the same way, and its local filters and sort are converted (`refitFilter`) or dropped (`filterFits`) by the app.
- **History and undo:** a `field.updated` entry with Kind / Holds / Links to as old → new (labels, for people), its change behind it (`fieldChanges.historyId`). Undo (Edit field, Settings → Activity, `records.undo`, agents' `records_undo`) runs the reverse change the same way: the old setup comes back (options too; renames since are kept), and each record gets its saved old value where it still holds what the change wrote; a record changed since keeps its newer value, converted back by the rules. Only the field's latest change can be undone, then the one before it. Undo takes `fields.edit` and Edit in the database, like the change.
- **How long old values are kept:** 30 days after a change finishes (`KEEP_MS`). Then the sweep deletes its saved values in batches and it can no longer be undone ("too old to undo"). Undoing deletes them at once (there's no redo). A field, database or workspace deleted forever takes its changes and their values (lifecycle `field` / `database` / `workspace`); a record deleted forever takes its saved values (`record`).
- **Permissions:** the same as editing the field: `fields.edit` and Edit in the database. Converting to a link takes seeing the target database; converting a link to something else takes seeing the database it linked to (its names get copied).
- **Agents:** `records_save_field` with `kind`, `multiple` or `linksTo` on an existing field changes it; `preview: true` returns the preview's counts without changing anything (`risk: none`). The change itself is `locked` (it rewrites every record's value for everyone) and binds the database's newest record changes, so a record changed after approval stops it. It returns the preview's counts and the change id `records_undo` takes.
- **Released apps** (COMPAT(0.1.0-alpha.10)): they keep working. They get converted values while it runs, see the new kind after, and their writes to a converting field are refused with a plain message. The history keys read "kind: Text → Number" there.

## Archive
One place for archived content: records, databases, fields, pages, folders, files ([Drive](drive.md)), channels, agents, team memories, and skills and automations (including retained library installs). Archive hides items from active work while keeping their content indefinitely. Code: `trashOps.ts` (rules), `trash.ts` (API); each kind's own ops move it in and out (`setRecordTrashed`, `setTypeTrashed`, `setFieldTrashed`, `setPageTrashed` (pages and folders), `setFileTrashed`, `setChannelTrashed`, `setAgentTrashed`, `setSkillTrashed`, `setAutomationTrashed`, `setMemoryTrashed`). A team memory in Archive is hidden from the app and agents; deleting it forever takes its versions. Personal memories skip Trash: only their owner can change them, so there is no one else's mistake to undo. An agent deleted for good takes its memories, and with them their Trash entries. Team memories are kept out of reads by index (`archived` is unset when live), so ones in Archive never crowd out live ones in lists or agent search. A team memory's History keeps what edits removed (last 20); to get rid of pasted secrets, delete the memory and have someone with `trash.manage` delete it forever.
- **Model:** the item stays where it is, `archived: true` (the stored name, kept so installed apps and indexes keep working), plus one `trash` row: kind, item id (skills and automations: their install row's), name when deleted, its database (records, fields), who (`deletedBy`, `agentId`) and when (`deletedAt`). Indexed by workspace and time, kind and time, item, database, and time alone (the sweep); a search index on the name.
- **Archive:** whoever can edit it: `records.edit` for records, `memory.team.write` (everyone) for team memories, `fields.edit` for fields and databases, `pages.edit` for pages, folders and files, `channels.edit` for channels (#general stays), `agents.manage` for agents ( the last live agent stays, since automations and chat need one), `skills.edit` for skills, and `automations.edit` for team automations (personal ones: their maker; `canEditAutomation`). A record's page goes with its record, and so do the pages inside it: their ancestor walk ends at the record's page, so they read as in Archive while the record (or its database) is, with no fan-out. Deleting the record forever deletes them through its page's cascade. Saved views are deleted outright: they're settings, not data, with their own conflict check.
- **In Archive:** an agent leaves chat (no mentions, DMs or replies) and can't be edited; its automations say it was deleted. A skill is gone from agents. An automation runs nothing (schedule, webhook 404, events; `installOf` skips it) and can't be changed; its opt-ins and Always grants wait for a restore, and calls it held can't be allowed Always.
- **Restore** puts it back where it was, links included: anyone who can delete it now, whoever deleted it (core `canTrash`, one rule per kind), as in Google Drive's shared drives, so a member's mistake doesn't wait on anyone else. It goes by current access: someone who lost the role can't restore what they deleted. Refused while its database is in Archive, or if its name was taken meanwhile (fields, databases, channels; a channel in Archive gives up its name).
- **Delete forever:** `trash.manage` (off for Member by default), never agents. Nothing in Archive expires on its own (`trash.sweep` is a no-op kept only for already-scheduled runs). Deleting forever: the entry goes first (so it can't be restored), then a cascade (`record`, `database`, `field`, `channel`, `agent` scopes in `lifecycle.ts`) deletes what belonged to it, and the item last; pages, skills and automations go at once, as before (an automation's opt-ins and grants in its `automationInstall` cascade). A record takes its values index, history, mentions and page (content and versions); a database its records (with theirs), fields, views, history and Trash entries; a field its index rows, history and its value on every record; a channel its messages (reactions, mentions), seats, agent turns and sessions; an agent its versions, memories, sessions and channel seats (what it said and did stays, shown as "Agent"). Agent activity and approvals there stay, hidden while the chat is in Archive; pending approvals cannot be decided or claimed there.
- **The app:** **Settings → Archive** lists everything newest first, with kind, name, its database, who and when; search by name and filter by kind; Restore and (with `trash.manage`) Delete forever. Records, pages, channels, agents, skills and automations open read-only from it with a banner and Restore. Archive actions ask first in a neutral confirmation that explains the content is kept and can be restored at any time. Permanent deletion asks separately with a destructive warning. Old `/trash` and `/settings/trash` URLs open Archive.
- **Agents:** archiving a page, record, field or database, forgetting memory, undoing a record change (which can archive it), and deleting a saved view require approval (`locked`).  `trash` on `records_save`, `records_save_field`, `records_save_database` and `pages_write` (false restores, finding it by name in Archive); `trashed` on `records_find` and `pages_find` lists what's in Archive. Reads say `inTrash`; links read "(deleted)". `channels_manage` with `delete` trashes a managed channel after exact-call approval; `agents_manage` `delete`, `skills_remove` and `automations_remove` trash the same way (restoring those is for a person). No tool deletes forever. `memory_forget` sends a team memory to Archive.

## API
**`recordTypes`** `list()` → databases (oldest first) with fields (`_id`, `key`, `label`, `kind`, `options`, `linkType`, `multiple`, `archived`, `canEdit`). The data model agents read. `create({ plural })` (`fields.edit`; the singular `name` is guessed by `singularOf`, and alpha.6 apps still send it), `update({ typeId, version, name?, plural? })` (`fields.edit`; a new plural alone re-guesses the singular). Public paths and Convex table names stay the same for installed apps. Databases from earlier releases delete like any other; nothing re-seeds them. Keys and routes never change; names must be nonempty, unique against live database names/plurals, and at most 120 characters. At most 32 databases per workspace, including ones in Trash.

**`databaseViews`** `list({ typeId })`, `save({ typeId, viewId?, version?, name, filters, sort?, columns, layout?, groupBy? })`, `remove({ viewId, version })`. Anyone with `records.edit` can create, update and delete shared views; all members read them. At most 50 per database; each config is at most 16,000 characters with a name up to 120 characters, up to 10 filters, sortable fields only, and live unique columns including `name`. Saves and deletes check the version; changing a stale draft is refused. Updates replace the whole config (omitting sort clears it). Filters use stored ids and field keys, validated through the list compiler. `layout` is `table` (the default, not stored, so older views read as tables) or `board`; `groupBy` is a live choice field holding one option. COMPAT(0.1.0-alpha.8): a save without `layout` (alpha.7 apps) keeps the view's layout and grouping. A database in Trash keeps records, fields, views and history, while hiding its sidebar entry and refusing view changes; deleting it forever deletes them all (Trash).

**`fields`** `create({ typeId, label, kind, icon?, options?: [{ id?, label, color? }], linkTypeId?, multiple? })` → field with its `key`. `update({ fieldId, label?, icon?: string | null, options?, position?, kind?, multiple?, linkTypeId? })` (send all options; keep `id`s to keep values; a missing `color` keeps the option's; `icon: null` goes back to the kind's; a different kind, one/several or linked database starts a change and returns `{ changeId, change }`). History records `icon` and recolored options (`colors`: "Won: green") like renames. `preview({ fieldId, kind, multiple?, linkTypeId?, options? })` → counts, examples, options, views, or `{ error }`. `changes({ fieldId })` → `{ running: { converted, undoing } | null, last: { historyId, change, at, converted, cleared, undoable } | null }`. Fields in `recordTypes.list` carry `changing: true` while they convert.

**`trash`** `list({ kind?, search?, paginationOpts })` (skills and automations add `screenId`, the "custom-…" id their screens use), `move({ kind, id })` (Delete), `restore({ kind, id })`, `purge({ id })` (`trash.manage`). Each record, page and chat `get`, and each `agents.list`, `skills.list` and `automations.list` row, returns `trash` (who, when, `canRestore`) while it's in Trash.

**`records`**
- `list({ typeId, sort?: { field, order }, filters?: [{ field, eq? | in? | gt?/gte?/lt?/lte? | empty? }], group?: { field, option }, paginationOpts })` — see Lists. `group` is one board column: a live single-option choice field and one of its option ids (removed ones too), or `null` for records without one. It's checked on its own and doesn't count toward the 10 filters, so a view with 10 filters still shows as a board. `search` finds each of its words in the title or text values, any case: one more filter, so the rest and the sort still apply (like Notion's search in a view). `sort.field` is `createdAt`, `updatedAt` or a field key (not links or several-value fields); a choice field sorts in its options' order (each option's records read in turn, so reordering needs no reindex); records without a value for it come last, newest first. A field change converts a saved view's text "is X" filter into the option labeled X (`convertCondition`) and drops only what can't convert. Currency filters are in whole units, in one currency (see Money). Pages can be short with `isDone: false`. Rows: `{ _id, typeId, title, values, archived, updatedAt, refs, unresolved }`; `refs` maps user and record ids in `values` to `{ name, archived? }`.
- `refs({ ids })` — names for up to 200 `unresolved` ids.
- `get({ recordId })` → row + `type` + live `fields`, or null.
- `linked({ recordId, fieldId?, paginationOpts })` — records linking here ("deals for this client").
- `search({ query, typeId? })` — title and text values, best match first, top 20, as list rows (values and names): for pickers. A table searches with `list`'s `search`.
- `history({ recordId, paginationOpts })`, `activity({ paginationOpts })` — newest first, names resolved.
- `discussion({ recordId })` — messages tagging it that you can see, newest first (50): `{ messageId, chatId, threadId, text, author, where, time }`, `text` with tags as you read them, `where` the channel (`#sales`), a side chat's title or "Direct message".
- `mentionable({ query })` — records to tag in a message (the composer's @ menu): `searchRecords` across the databases you can see, top 6, `{ _id, title, typeKey, typeName }`.
- `create({ typeId, values })` → id. `update({ recordId, values })`. `undo({ historyId })`. Delete and restore through `trash`.

## Sorting and filtering in the app
- Sidebar **Databases → +** (or **New database** while there are none) asks people with `fields.edit` for one name ("Projects"), then opens it. **Edit database** (in the menu under the database's title in the top bar, and in its sidebar row's ⋯) renames it, including the singular ("Project"), or deletes it.
- Above each list, tabs: **All** (columns remembered on this computer) and each shared view. Filters, sort and columns start from the open view; edits stay private until **Save for everyone**. **+** saves the current settings as a new view. The bar's **⋯** (`ViewMenu.tsx`, like Notion's view settings) holds the rest, each a page of one menu: **Layout**, **Properties** (search; shown, in order, then hidden, with Hide all / Show all; drag to reorder; a property opens its own page to rename it, show or hide it, archive it, or open its kind and options in Edit field), **Group by** on a board, then **Edit database**, and on a saved view its name (renames it), **Duplicate view** and **Delete view**. Search is temporary and not saved. Deleted records are in Trash.
- **Layout** (in **⋯**) switches between table and board. A board makes a column per option of a choice field holding one option (**Group by** in **⋯**; the first such field until one is picked), after **No <field>**. Cards show the name and the view's properties, in their order, skipping empty values and the grouped field. Filters and sort apply to every column; each column is its own `records.list` with the option as `group`, paging as it scrolls (`Board.tsx`). Without a sort, columns list in the database's manual order (`sort: { field: "manualOrder" }`, by `records.rank`, a fractional index from core `rank`: new records first by creation time, a column's New row last). Dragging a card (`records.move`, `records.edit` and Edit; a copy follows the pointer and, let go, settles into its place before the move is sent) puts it between its new neighbors and, in another column, sets the field there with its usual history; the order itself isn't history. With a sort on, like Notion, the sort decides: a card only changes column. Removed options get a column, marked "(removed)", only while records use them, and take no cards. Each column's header has a + (on hover) and its foot a **New <record>** row: the New dialog, with that option already set. Columns are the field's options, so dragging a column by its header reorders them, clicking its chip renames, recolors or removes that option (the name saves as the menu closes), and **New column** at the end adds one, all a `fields.update` (`fields.edit` and Edit, `canManage`); "No <field>" stays first and removed options last. Without a field to group by, the board says so and offers **Add a choice field** (`fields.edit`). Board isn't offered then, and the server refuses it (`NO_BOARD`, in `setDisplay` and saved views), so a database can't be switched to a layout that shows nobody any records. The All tab's layout is shared, so changing it takes `sidebar.arrange` and Edit in the database (`canSetDisplay`); alpha.9's one-time import (`migrateDisplay`) follows the same rules and skips silently what can't apply. Search narrows the board like the table.
- **All records** keeps local filters, sort, columns and layout per database on this computer. Old column preferences carry over. Shared settings use `useDraft` + `ConflictNotice` and versions, like agents and workspace settings.
- Settings → Activity shows record, field, database and view history, naming the person and any agent acting for them. Database/view changes are logged but do not use record undo.
- Wording: databases contain records; sorting, filtering and columns belong to a view. This follows [Notion's database views](https://www.notion.com/help/views-filters-and-sorts) and [Attio's shared filter and sort settings](https://attio.com/help/reference/managing-your-data/views/filter-and-sort-views).

## Agent tools
`core/src/record-tools.ts` → `ToolContext.records` → `backend/convex/recordTools.ts` (internal `*For` per turn, through `recordOps`). Granted as `records.*`; Companybot has them. All `risk: none`: internal and logged. Record changes have undo; database/view changes do not.
- `records_types` — databases with versions, fields (key, label, kind, `icon`, options, stable-id `choices` with colors, position, `inTrash`, `linksTo`); `trashed` selects databases in Trash, workspace currency.
- `records_find` — one database with filters, sort and `cursor` (`records.list` underneath), or `search` (title and text, top 20, no filters). Asks up to 5 times to fill a short page; `more` + `cursor` when there's more. Data result: rows `{ _id, _type? (search across types), …field key: display value }` (keys start with a letter, so a field called "id" can't clash), so `widgets_table` shows them by ref (`path: "rows"`).
- `records_get` — one record: values, `links` (with ids), `linkedFrom` (10), last 5 `changes` with change ids and who (person + agent).
- `records_history` — all record history by id, or workspace Activity without id; `source: agents` reads visible agent tool calls with outputs private to the acting person. Indexed pages of up to 20 (`limit`), newest first; long model results are trimmed, and `change` reads the full entry as JSON in 20,000-character chunks (`start`/`next`). continue with `continueCursor` while `isDone` is false.
- `records_save` — create, patch values, or delete/restore (`trash`, on its own). Returns the record and its `change` id.
- `records_undo` — reverses one change (`undoChange`); undoing a create deletes it (to Trash).
- `records_save_field` — add a field (`fields.edit`), rename one / set its `icon` (null resets) / set ordered options (strings or `{id,label,color?}` to preserve stored values while renaming; a string keeps the option's color), reorder fields (`position`; Name stays first), change its kind, one/several or linked database (`preview: true` first; the change is `locked`, see Changing a field), or delete/restore it (`trash`; `fields.edit`).
- `records_save_database` — create (one `name`, e.g. "Projects"; `singular` optional), rename (database key/id + version), or delete/restore (`trash`), with `fields.edit`.
- `records_views` — saved view ids, versions and complete configs for one database.
- `records_save_view` — create, patch or delete (`remove: true`) a shared view (`records.edit`); updates/deletes require its current version. Omitted settings keep their previous values; `sort: null` and `groupBy: null` clear them. `layout: "board"` with `groupBy` (field key or label) makes a board; moving a card is `records_save` of that field. Accepts field keys or labels, choice labels, teammates by name or "me", and linked records by exact name or id, like `records_find`. Saved choices use stable option ids.
- **Named like people say them:** databases by id or key, else name or plural; fields by key, else label (a name two could match is refused, listing both); teammates as "me", a name or an email; links as the record's exact name or id.
- **Link names are an exact lookup**, not a search: the target type's name field in `recordValues` (`by_field_str`, live records only), two rows to tell one from several. Lists are checked against their limits (50) first; lookups are memoized, and one call looks up at most 100 distinct names, so a call's reads stay small.
- **What the model sees is capped** (`forModel`, ~24k characters): long text is cut (300 in lists, 2,000 on one record, shorter until it fits), then rows dropped, with a `trimmed` note. The full result stays behind the ref for widgets.
- **Display:** `displayValues` (core): option labels, names, `formatMoney` in en-US so "$" is only USD, `formatDate` ("Nov 15, 2026", the same helper the record screens use). Input amounts follow Money; dates go in and filter as `YYYY-MM-DD` (the tool descriptions say so).
- **Tool lines** say what the call did, from its input and result (`ToolDef.label`, `callLabel`): "Created deal Reroof main warehouse", "Saved Acme Roofing", "Found 1 deal", "Added field Roof type to Clients", "Undid a change to Acme Roofing". Results carry the type's names for this (`typeName`, `typePlural`). A call that fails (including an `{ error }` result) is labeled from its input alone: "Couldn't create deal Reroof main warehouse", else the tool's title.
- Not exposed to agents: deleting forever.
