# Architecture

pnpm monorepo. Each folder in `src/` is a package.

| Package | What |
|---|---|
| `src/core` | Agent framework: agents, built-in tools, connectors, skills, memory rules. Pure logic, no I/O. |
| `src/backend` | Convex: database, sign-in, live updates, and the agent runner (`convex/`). |
| `src/desktop` | Electron app (electron-vite + React + Tailwind). Talks to Convex directly. |

## Concepts (`src/core`)
What each piece is. The rules for changing them: [Extending](extending.md).
- **Role** — a workspace's named set of switches (`roles` table). Owner (everything, fixed) and Member (the default) are built in; owners add their own. A person holds one or more and gets the union ([Permissions](permissions.md#roles)).
- **Who can access** — a channel's, database's or page's list of Everyone or roles at View or Edit (`place-access.ts`); not on it, the place doesn't exist for you ([Permissions](permissions.md#who-can-access)).
- **Permission** — a switch: one workspace action, with a plain label and a Member default (`permissions.ts`). Backend and app both read this table.
- **Tool** — something an agent can call. Built-ins live in code; connector tools are discovered from the connector's MCP server each turn and reach the model on demand through `connectors_search` / `connectors_call`, not up front. Ids are `group.name`.
- **Agent** — name, instructions, model, tool grants. A tool reaches the model only if granted, allowed for one of the person's roles, and (connectors) installed, allowed, and connected.
- **Connector** — a catalog entry for a remote MCP server, with a workspace or personal connection and encrypted credentials. The catalog is currently empty.
- **Skill** — installable instructions: name, a short description, and Markdown instructions (Claude's SKILL.md fields). Agents see the descriptions and load the full text on demand. Personal skills can be made by anyone; team skills need `skills.edit`, in Settings → Skills or by asking an agent (`skills_create`).
- **Automation** — a trigger (schedule, in-app event, or webhook) plus a prompt. Anyone can make their own. Each run posts the prompt in the chosen agent's DM with each person it runs for, as them, so the reply uses their permissions and connector accounts. Or, with a channel picked, once in that channel, as its maker (library ones: whoever picked the channel).
- **Wakeup** — an agent waking later in a place (chat + thread), acting for a person: **when** (a time, once or repeating, or a job finishing) plus **what** (a note: a follow-up's task; none: look around). Follow-ups agents set, heartbeats (#162) and job callbacks (#114) are all wakeups, with one path to a turn. See Backend → Wakeups.
- **Widget** — UI an agent places in a reply (table, stats, card). Each is a tool; the app renders the stored props; the model gets a short receipt, not the data back.
- **Help** — docs for the people in a workspace (what Companybot is, every setting tab, how to do things), written as Markdown strings in `core/src/help/`, one module per area. Agents read them with `help.read` (no args lists topics; `topic` reads a page; `query` searches) and link people to the screen with `#/…` addresses, which the app opens in place (`markdown.tsx`). Companybot has the tool; any agent can be granted `help.read`. Keeping them current: [Extending](extending.md#help).
- **Platform guide** — how replies render, added to every agent's prompt after its own instructions.
- **Memory** — per agent, scoped `workspace` (team) or `personal`. Agents and people follow the same rules. Team memories are wiki-style: anyone can add, fix or delete them; each keeps who saved it (`createdBy`), its last 20 versions (`memoryVersions`, restorable) and goes to Trash when deleted, so wrong changes are undone rather than prevented (Lindy, Notion and Asana do the same). Personal memories are only their owner's; no role can read them, Owner included. In chats with 2+ people, agents read and change team memories only, but can save a new personal one for the person who asked. People with `workspace.manage` can turn memory off for the workspace (`workspaces.memory`); agents then get none, and nothing is deleted.
- **Chat** — channels, DMs, threads, reactions; agents reply when mentioned (or to everything in their DM), acting as the person who asked. See [Chat](chat.md).
- **Approval** — a held tool call shown as a card in chat (`approvals.ts`). Action rules live in `action-rules.ts`, wording in `action-words.ts`. See [Permissions](permissions.md).
- **Activity** — database, saved-view, field and record changes (`records.activity`), plus every tool call an agent makes, with its input and result (`activity.ts`). Widgets and `connectors_search` aren't logged; read-only tools are marked so the app can show changes only.
- **Database** — A collection anyone with `fields.edit` creates (Member lacks it by default; an owner can turn it on). Each contains records and fields; shared saved views hold filters, sort and columns. Existing tables (`recordTypes`, `records`, `recordFields`) and public paths keep their names for installed apps. Changes enter record history; record changes can be undone. See [Data](data.md).
- **Web** — `web.search`, `web.fetch` and `web.save` (`web.ts`; save downloads a picture or file into the reply, from the same links and allowance as fetch): search through a provider, then read pages as Markdown and PDF, Word and Excel files as text. `web.fetch` opens only links the person wrote (this turn's messages, the thread's parent, the message a turn resumed after an approval started from: `turnContext`'s `asked`) or that came up in this turn's web results (pages included, and their list of linked files), so an injected instruction can't send data to a link the model made up. 5 searches and 10 pages per reply; once one is spent, that tool is taken away for the rest of the reply (`agentPrepareStep`).
- **Turn input** — what the model gets each turn (`turn-input.ts`): a fixed system prompt, the agent's session in that place replayed exactly, and one new message. Built for prompt caching.

New workspaces start with only **#general** and **Companybot**. No databases, pages, skills, automations or connectors are seeded. Companybot can help people create databases, skills and automations, as their roles allow; the table, stats and card widgets remain available.

## Backend (`src/backend/convex`)
- **Sign-in:** Convex Auth (beta) with a 6-digit email code sent through Resend. Signed out, the app opens on a one-line landing (`views/Landing.tsx`, Get started), then sign-in (`views/SignIn.tsx`). Both use the same frame (`Split`): content centered on the left half, and on the right a picture drawn in code (`views/Art.tsx`, an SVG of flat shapes with grain), so no image ships.
- **Workspaces:** a person can be in several (`members`, one row each). First sign-in joins every workspace that invited the email (`ensure`); with none, nothing is made: the app shows onboarding (`views/Onboarding.tsx`, three steps: your name, the company and its currency, emails to invite), which ends in one transaction (`setUp`: name saved first so the welcome uses it, then the workspace with its Owner and Member roles and you as Owner, with `#general`, then the invites as Member; a bad email refuses it all). The same screen comes back whenever you're in no workspace, such as after deleting your last one. **The workspace comes from each request, never from server state:** every public function is built with `functions.ts` (`query`/`mutation`/`action`), which takes `workspaceId` and puts it on ctx for `getMember`, which checks membership in that workspace (not a member → null/refused). The app's hooks (`desktop/.../convex.ts`) add the open workspace to every call; a test fails if a screen imports convex/react's hooks directly. Which workspace is open is per device (localStorage, pinned once chosen); `preferences.workspaceId` is only "last used", for a device's first launch (`workspace.mine`, `switchTo`). A row from another workspace (by id) looks like it doesn't exist: check it with `requireInWorkspace(member, row, what)` or a `require*` helper built on it (`tests/workspaces.test.ts` tries every id-taking function from the wrong workspace). A request that names no workspace acts nowhere. Anything acting for someone in a known place (turns, approvals, automations, agent tools, connectors, OAuth flows) passes that workspace to `memberOf(ctx, userId, workspaceId)`. The workspace switcher (`WorkspaceSwitcher`) is the open workspace's logo at the top of the app rail, as in Slack; its menu lists every workspace to switch (dragged into your order; ⌘1–9 follow it), invites to join or decline, New workspace (`create`: you're its owner, with the default agents, #general and a welcome, like a first sign-in's), Workspace settings, and Leave (`leave`; not the last owner). Joining or creating opens the workspace once `mine` lists it. Other workspaces show a dot when a chat is unread and a red count of chats with an unread @mention or DM (`activity`), in the menu and summed on the logo. Creating is capped at `MAX_OWNED_WORKSPACES` (10) owned. Your avatar sits at the bottom of the app rail: Account settings and Sign out.
- **Invites:** anyone with `members.manage` (only owners invite an owner; invites pick one or more roles). One per email per workspace; accepting checks the signed-in (code-verified) email, so an invite can't be used by anyone else or for another workspace. Each invite (and Resend) emails who invited them, the workspace, and the download link (GitHub Releases), through the sign-in Resend account (`invites.ts`, text in core `invite-email.ts`); local backends log it instead. Limits: 20 emails per workspace per day; one email per address per 10 minutes, however invites come and go (a resend inside it is refused; a new invite is saved without one). Names are cut to one line before they go into the subject. Removing someone (or leaving) ends access at once, then a member cascade ([Data lifecycle](#data-lifecycle)) drops their channel seats, automation opt-ins, permission rules, personal connector accounts (the workspace's own stay), personal memories and skills, unread mentions, and automations only they could see (just-them ones, which nobody else could delete); rejoining waits until it's done, so it starts strict. DMs keep them as a past participant.
- **Messages** are ordered `parts` (text, tool activity, widget) plus `text` (plain text only, for history and summaries), and up to 10 `attachments` (storage id, name, sniffed type, size, a picture's pixels; `files.ts`, [Chat](chat.md)). History shows the agent a one-line note for each widget it showed.
- **Chat:** `chats.ts` (channels, DMs, unread) and `messages.ts` (timeline, threads, reactions); shared rules and the visibility-aware channel lookup in `chatOps.ts`; agent tools in `chatTools.ts`. Public channels are readable by the workspace; private channels and DMs by members.
- **Agent turns:** `messages.send` queues an `agentTurns` row per responding agent (`turns.ts`); in a "When relevant" channel an un-mentioned message instead schedules the reply router (`router.ts`, [Chat](chat.md#when-agents-reply)), which may queue some. One runs per agent per place (chat + thread); the rest wait; one stuck over 5 minutes is failed. A running turn streams its reply into the database via `agent.respond`; the app sees it live, and the line under the composer shows its current step (`agentTurns.step`, [Chat](chat.md#backend-api-backendconvexchatsts-messagests-filests)). An agent's finished reply can queue turns for the agents it @mentions, in a chain with limits ([Chat](chat.md#agents-working-together), `chains.ts`).
- **Sessions:** `agentSessions` holds each agent's context per place. Each turn's prompt is stored (`agentTurns.prompt`) and replayed byte-identical later. Model calls send `x-session-affinity`.
- **Agents:** stored per workspace. People with `agents.manage` create, edit and delete them (to [Trash](data.md#trash); the last agent stays). Every save writes an `agentVersions` row; restoring saves an old version as the newest. Replies read the agent fresh each turn, so edits apply from the next reply.
- **Models:** an agent can run on any AI Gateway language model that uses tools. The catalog keeps the gateway's `vision` tag (`ModelInfo.vision`; the fallback models have it, GPT-6 Luna included), which decides whether a turn's pictures are sent to the model. `modelCatalog.ts` caches them in one `modelCatalog` row from the public `GET https://ai-gateway.vercel.sh/v1/models` (no key; `type: "language"` with the `tool-use` tag, plus name, context window and $/M input/output), since queries can't fetch: a daily cron, and `refreshIfStale` when an agent editor opens on a day-old copy. A failed or empty fetch keeps the old copy; with none, core's `fallbackModels` (GPT-6 Luna, Claude Sonnet/Haiku/Opus 5.5) stand in. Saves accept the catalog, the fallback list, and the agent's current model, so an agent whose model left the gateway still saves other edits (the picker shows it as unavailable). GPT-6 Luna is the recommended default (`defaultModel`) for new agents and Companybot: about 20x cheaper than Claude Sonnet 5.5, whose agents moved to it (`migrations.lunaModel`).
- **Picture models:** we offer a short, tested list, not the gateway's whole catalog (models come and go, and some it lists are dead): core `imageModels` (GPT Image 2.5 Flare, the default `defaultImageModel`, and Sunburst for precise edits; Nano Banana 2.1; FLUX 3; Recraft V4.1), each with what it's best at (`use`) and one default picture's cost (`perImage`, measured through the gateway on 2026-10-29; Recraft's is its listed price). The gateway reported a cost for every model tested, so `perImage` only shows in the picker and sizes the budget hold; the recorded cost is the gateway's. The daily catalog fetch keeps the gateway's picture models (`modelCatalog.imageModels`, `parseGatewayImageModels`: the `image-generation` tag on a `type: "image"` model, run with `generateImage`, or a `type: "language"` one, `multimodal`, run with `generateText`, pictures back in `result.files`) only to drop ours it stopped listing (`catalogImageModels`). A workspace's pick (`workspaces.imageModel`) we no longer offer falls back to the default (`workspaceImageModel`). Adding a model: one test picture, then a line in `imageModels`. Picked in Settings → General.
- **Agent pictures** (`images.generate`, `imageGen.ts`): `prepareFor` (a mutation) checks, as the turn's person now, the monthly image budget (`workspaces.imageBudgetUsd`, default $20, 0 = off, against this month's `usage` rows of kind `image`, `imageSpent`, plus what running calls hold) and that each edit file is a picture on a message they can see (`visibleFile`), under 5 MB and 8000px, then holds one picture's estimated cost (`imageHolds`: `perImage`, else `IMAGE_PRICE_UNKNOWN_USD` = $0.25) so parallel calls see it: however many run at once, they pass the budget by one picture at most. `generateFor` then calls the model through AI Gateway (edit pictures as `images` for `generateImage`, file parts for `generateText`; aspect ratio as `aspectRatio` or Google's `imageConfig`), settles the hold into the real cost (the gateway's, else `perImage` or $0.25 × pictures, so no picture is free) with `imageGen.settle`: `usage` for the turn's person and agent whether or not it attaches, the place's running cost, and the turn's `imageCostUsd` for its reply's stats. A failed call releases its hold at once; one whose action crashed is released by a release scheduled with it (`HOLD_MS`, 15 minutes, longer than an action runs). It stores each picture with the type its bytes say (`sniffImage`; anything else, like SVG, is dropped) and attaches it with `files.attachToReply`, which enforces the reply's 10-file limit. The model gets a receipt with each picture's file id, never its data. What `providerMetadata.gateway.cost` holds for picture models hasn't been checked against a live call; the listed price covers it when it's missing.
- **Dictation:** the composer's mic sends a recorded clip to `dictation.transcribeAudio`, which transcribes it through AI Gateway (`openai/gpt-4o-mini-transcribe`) with the same `AI_GATEWAY_API_KEY`. See [Chat](chat.md).
- **Three kinds of data:** shared content (chat, memory) is fully live. Shared settings (agents, database names, shared views, workspace name, currency and memory on/off) are edited as a draft and saved; each has a `version`, and a save from an old version is refused as a conflict (`checkVersion`), with a "Use theirs / Keep mine" prompt in the app. Personal preferences (`preferences` table) are per person and sync across their devices. They include `notify` (desktop notifications and the dock badge: DMs and mentions, mentions only, or off).
- **Time zones:** each person has one: the zone they picked in Your preferences, else automatic (their computer's, which the app reports on launch), else UTC (`timeZoneOf`). Agents get it in the turn prompt, chat times in prompts use it, and `clock.now` answers in it. It isn't private: `workspace.team` returns it for profiles. Automation schedules use the zone of whoever made or installed them.
- **Permissions apply at once:** every agent tool call that reaches data (memory, records, chat, skills, automations) goes through `runningTurn`, which re-reads that the turn is running, the person's membership and role, and that they can still see the chat and post in it; connector calls re-read access too. Removals, role changes and leaving a chat take effect mid-reply.
- **Connectors:** `connectorInstalls` (roles allowed) and `connectorConnections` (AES-GCM encrypted with `CONNECTIONS_KEY`, encrypted in an action). OAuth sign-ins in progress sit in `connectorOAuthFlows` (one use, 15 min) until `/oauth/callback` finishes them. The runner connects only to connectors the agent's grants reach, skips any that fail or take over 10s, and tells the agent.
- **Skills:** `skillInstalls` (one row per skill). Skills people make live on their row (`custom`: name, description, instructions, `createdBy`; versioned; id `custom-…`), have an explicit `audience` (`team` or `personal`). Team skills need `skills.edit`; personal skills have `ownerId`, are visible/editable only to that person (Archive included), and load only on their turns; deleting moves it to Archive, which never expires. Agents make them through `skills.create` → `skills.createFor`, as the person they help. `installedSkills` (`lib.ts`) filters for the turn actor. The `/` picker uses the same visible list. Confirmed Share with team needs `skills.edit` and clears `ownerId`. Member cleanup deletes personal skills and their Archive entries, like memories. `migrations.skillAudience` sets existing installs to Team; deploy, then run `migrations:runAll`. The schema permits old rows only for rollout (tagged `COMPAT(0.1.0-alpha.10)`); after production migration, make audience required. Reads fail closed until a row is migrated: no unset-means-Team path.
- **Automations:** `automations.ts` (CRUD/settings), `automationRuns.ts` (triggers and dispatch), `automationTools.ts` (agent tools), `automationOps.ts` (shared lookups). `automationInstalls` (agent, on/off, time zone, `audience`, channel, last run). Retired library installs keep their definitions on their rows. Ones people make (`automations.create`; personal ones need no switch, team ones `automations.edit`) live on their install (`custom`: name, prompt, trigger; versioned like other shared settings; id `custom-…`) and run through the same code (`definitionOf`); `automations.edit` edits team ones, and a personal one is its maker's alone (`canEditAutomation`). `audience` decides who it runs for: `creator` (only the maker; hidden from everyone else), `subscribers` (people who opted in, `automationSubscriptions`; the maker or installer is subscribed automatically), or `channel` (one post there acting as whoever picked it, falling back to an owner who can see it). DM runs post as the person in their agent DM (tagged `automation`, shown collapsed in chat). Schedules are standard 5-field cron (`{ type: "schedule", cron }`, core `schedules.ts`: croner reads them in the install's `timeZone`, cronstrue describes the ones the form can't), at most every 15 minutes (`scheduleError`: each run is a full agent turn per person). A cron (`crons.ts`, every 5 min) runs each due schedule once: its latest time at or before now, if after `lastScheduledAt` (the time it last ran for; set to now on create, on a schedule change and on resume, so nothing past is made up). Missed times run once, never as a backlog. Lists and labels use `describeTrigger` ("Weekdays at 9:00 AM and 1:00 PM"). The app's editor (`ScheduleEditor.tsx`) always shows the cron, with a Repeats form (every few hours, daily, weekly, monthly) that reads and writes it, the description and the next 3 runs; a cron the form can't show stays editable as text. Schedules from before cron (one time on some weekdays) read as their cron (`scheduleCron`) and `migrations.cronSchedules` rewrites them (COMPAT for alpha.9 apps). In-app events go through `fireEvent`: `message.posted` (from `messages.send`, top-level channel messages, optionally one channel; posting back to that channel replies in the thread) and `member.joined` (from `workspace.ensure`). "Run now" runs it for you with sample data. Agents can list, create, and opt in through `automations_list` / `automations_create` / `automations_set_mine` (`automation-tools.ts`; the guide adds a short how-to when granted).
- **Wakeups** (`wakeups.ts`, core `wakeups.ts`): one `wakeups` row per thing that will wake an agent: agent, place (chat + thread), actor (who it runs for), `createdBy`, optional `note` and `recordId` (+ `typeId`), `foreign`, status (`pending` / `fired` / `cancelled`, with a `reason`), and when: `at` (with structured `repeat` and `times`, it repeats) or `jobId` (#114). No `kind`: a note means "do this" (a follow-up), none means "look around" (#162's heartbeat).
  - **Time:** `armAt` schedules `ctx.scheduler.runAt(at, wakeups.fire, { id, at })` and stores the scheduled id. `fire` does nothing unless the row is still pending and `at` matches, so moving or cancelling one is a patch (plus a best-effort `scheduler.cancel`) and a stale call is harmless. A repeating one is re-armed by `fire` before it wakes (`nextRepeat`: steps from the stored local date-time in the zone the repeat was set in, as Google Calendar does, so "every Monday at 9" survives clock changes and the person moving zones; hours and minutes count elapsed time; missed ones are skipped), until `times` wakes (`wakes` counts them). Exact timing, no polling, durable across deploys; the 5-minute cron stays for automation schedules.
  - **`wake(ctx, id, { result? })` is the only path to a turn.** It re-checks, as of now: a live workspace; the actor is a member (else cancelled, "person left": never re-run as anyone else) who can still see the chat; the agent, chat, thread and record exist (else cancelled). If the agent, chat, record or its database is in Trash it's **held** (`held`) and logged as skipped; any restore (`takeFromTrash`) releases the workspace's held ones, which wake again. Then the gate for note-less wakeups (`lookAroundGate`, none yet: #162 adds busy/off-hours/digest/triage), then `enqueueTurn` as the actor with `wakeupId`. #114 calls `wake` with the job's result (kept on the row as `result`).
  - **Wake turns have no trigger.** No message is posted to start one: the turn's input is the wakeup (`turnContext` `wake`: note, the record's current values via `recordOut`, a job's result, repeats left; core `buildTurnPrompt`'s wake section, record values and results fenced as data). It ends with the same answer as every turn (core `postDecision`, [Chat](chat.md) → When agents reply), so its reply shows, as itself, in the place, once its message starts, like any reply; with no message it stays a hidden (`quiet`) message, kept for session replay. A wake has no trigger to react to. Held calls go to the actor's DM (from a channel, as their own card; in the DM, in the reply, which is then shown), the run goes on (`waitFor`, like an automation's run), and their cards never offer Always (there's no automation to scope it to).
  - **Activity:** every wake writes one `agentActivity` line (`tool: "wakeups.wake"`, `wake: { wakeupId, outcome, reason? }`): `fired` when it queues a turn, then `ran` (finished quietly), `notified` (its reply was shown), or `failed`; or `skipped` with why. As private as its chat.
  - **Tools** (core `wakeups.ts`, granted as `followups.*`; Companybot has them, existing ones from `migrations.companybotFollowupTools`): `followups_create({ note, at | in, every?, times?, recordId? })` (times in the actor's zone: `in: {days: 3}` keeps the local time, `at: {year, month, day}` is 9 AM; at least 1 minute and at most 2 years ahead; repeats at most hourly, in calendar units including months, up to 100 times), `followups_list({ recordId? })` (`inside`: notes can come from private chats), `followups_cancel({ id })`. Limits: 10 pending per record, 200 per agent. The guide adds a short how-to when granted.
  - **The app:** `wakeups.list({ recordId? })` (pending, soonest first; ones in chats you can't see only for `agents.manage`, without their note) and `wakeups.cancel` (its actor, its maker, or `agents.manage`). Shown under Follow-ups in Settings → Automations and on the record (`views/Wakeups.tsx`). Fired and cancelled rows go 30 days later (`forgetSettled`, hourly).
- **Webhook automations** get a secret URL: `POST <site>/automations/<token>` (`http.ts` → `automationRuns.receive`). Body `{ event?, id, person?: { email }, data? }` (`event` must match when the trigger names one, like `call.ended`; ones people make take any), max 32 KB; `id` dedupes retries (`automationEvents` holds webhook delivery ids, kept 7 days by `forgetOldWebhooks`, deleted after uninstall by its cascade, so a busy webhook can't block removal); `data` is appended to the prompt as fenced JSON. Runs in the channel if one is picked; otherwise in the DM of the member whose email is `person` (they must be subscribed, or be the maker of a just-me one), or for every subscriber if no `person`. Replies: 200 (ran, skipped, or duplicate; the reason is in `message`, which names no channel, and in the automation's last run, `lastOutcome`, whose channels each reader sees by name only if they can see them), 400 bad body, 404 unknown token, 413 too big. Sender contract: oobagi/ai-agency#1052.
- **Permissions:** `permissions.ts` stores and checks action rules and workspace locks; `connectorTools.ts` stores the reported tool metadata. Rules and invariants: [Permissions](permissions.md).
- **Activity log:** the runner writes an `agentActivity` row as each tool call finishes (input and result as JSON, cut to 4k chars; calls cut off by a failed reply are logged as errors). An entry is as private as its chat; results show only to the person the agent acted for, since they can hold things only that person may see. Owners get no extra access. The app shows it in Settings → Activity and when you click a tool line in a reply. Memories an agent changed carry `updatedByAgent` until a person edits them.
- **Approvals:** `approvals.ts` holds tool calls and queues the turn after a decision. Card, hash and replay rules: [Permissions](permissions.md#the-card).
- **Records:** `records`, `recordTypes`, `recordFields`, `recordValues` (the index for filtering and sorting any field), `recordHistory`, `recordMentions`, and `trash` for what's deleted. Databases are created by the team; existing database keys and links remain valid without any catalog. Agents use them through ten `records_*` tools (`recordTools.ts`), as the person who asked. See [Data](data.md).
- **Pages:** `pages` and `pageVersions`; content in the `prosemirrorSync` component. Standalone pages and every record's body are one thing. See [Pages](pages.md).
- **Pictures:** workspace logos (`workspaces.image`), people's photos (`preferences.image`, in every workspace), agents' pictures (`agents.image`, outside the versioned config) and page images (`pageImages`, [Pages](pages.md)) are Convex storage files (`images.ts`). The app POSTs the file, signed in (`Authorization: Bearer <token>`), to `<site>/images/upload?workspaceId=…` (`useUpload`, `upload.ts`, reusable for other uploads; `images.uploadEndpoint` gives the URL). That HTTP action reads the type from the file's first bytes (PNG, JPEG, WebP or GIF, `core/images.ts`; never the header, so SVG or HTML labeled `image/png` is refused), allows up to 10 MB (`imageMaxBytes`; generated pictures often run a few MB), stores it with the sniffed type, and adds an `uploads` row naming the uploader (and their workspace, which must be theirs; 20 unclaimed at most). `images.set({ of: "workspace" | "me" | agentId, file })` takes only the caller's own unclaimed upload and uses its row up, so an id someone else learns is worthless; `null` removes the picture. Unclaimed uploads go after a day with their files (`images.sweepUploads`, hourly). Replacing or removing a picture deletes the old file; deleting the row deletes it too (lifecycle `files`): an agent's when it's deleted forever (not in Trash), a photo with its account, the logo, agents' pictures and pending uploads with the workspace. Queries return only URLs (`imageUrl`, once per file per query via `imageUrls`). Who changes them: owners the logo (`workspace.manage`) and agents' pictures (`agents.manage`), everyone their own photo. Agents set one from a picture in the chat, or reset it to initials (`workspace.settings` / `agents.manage` `set_image`, file id or null): the runner copies the file as the person's upload first (`files.copyFor`, [Extending](extending.md#chat-files-for-agents--backendconvexfilests-copyfor)), and `setImage` claims it like any upload. Display queries use `namer(ctx, { images: true })`; what agents read never carries URLs. Files for messages go through the same path and rows (`/files/upload`, `files.ts`; up to 20 MB; `uploads.file` set, and each kind is only claimed as itself): [Chat](chat.md).
- **Usage:** each reply stores `stats` (model, tokens, time, AI Gateway's `cost`, and its pictures' `imageCostUsd` and web searches' `searchCostUsd` apart), plus its place's running total (`costUsd` on the chat or thread parent, summaries, pictures and searches included). The runner saves the reply's usage after every finished model call (`turns.saveUsage`, onto `agentTurns.usage`), recording only what's new since the last save; `finishReply` records the rest the same way. So a turn whose action dies (Convex's 10-minute action limit, a crash) keeps what its finished calls cost, never counted twice, and a turn failed as stale (`STALE_TURN_MS`) still gets its stats. The app shows them under each reply. Prompt caching is on for every model call (AI Gateway `caching: "auto"`).
- **Usage by month** (`usage` table, `usage.ts`): every paid call goes through one function, `recordUsage(ctx, { workspaceId, userId?, agentId?, kind, model?, costUsd })`, called from the mutation that saves the call's result (`saveUsage`/`finishReply`, `addSearchCost`, `finishCompaction`, `imageGen.settle`, `router.apply`). It adds to one row per workspace, month (UTC, `"2026-10"`), person, agent, kind (`usageKinds`: chat, summary, search, image, dictation, router) and model, so the Usage screen reads a few rows instead of every message. A reply counts for the person the turn acted for (`agentTurns.actorId`: who wrote the message, who an automation ran for, a channel automation's maker); a summary for the person whose reply triggered it; a reply decision (`router`) for the person whose message it decided on, with no agent. Zero costs aren't recorded. It refuses a workspace that's being deleted (late-write rule below), and the table is deleted with the workspace and kept when a person leaves or is erased: it's the workspace's bill, shown under a former member's name. `stats.counted` marks replies in the table, so the one-off `migrations.usageThisMonth` (fills this month's earlier replies; summaries from before aren't kept apart, so they're missed) can't add one twice. **Settings → Usage** (`usage.report`, `views/Usage.tsx`): the month's total and by agent, person, kind and model, with a picker for the last six months; people with `usage.view` (off for Member by default) see the whole workspace, everyone else only their own share (`scope: "mine"`, no by-person). Agents read the same through `workspace_settings` `usage`, as the acting person. A month is capped at 2,000 rows (people × agents × kinds × models).
- **Web:** search runs in the runner through `SEARCH_PROVIDER` (core `web-search.ts`): `gateway` (default; Exa through AI Gateway, billed with the models), `brave` (`BRAVE_API_KEY`) or `searxng` (a self-hosted `SEARXNG_URL` with JSON on). Gateway search only runs as a provider-executed tool inside a model call, so the adapter makes one tiny call (GPT-6 Luna, forced to call `exa_search` with the query, one step) and records its gateway cost as it finishes (`turns.addSearchCost`): kind `search`, model `exa`, out of the reply's chat row, in its `stats` as `searchCostUsd`. Pages go through `webFetch.fetchPage`, a Node action: `safeFetch` (core `safe-fetch.ts`, reused by link previews) allows http(s) only, resolves DNS and refuses private, loopback, link-local, CGNAT, multicast and metadata addresses (IPv4 and IPv6, IPv4-mapped included), connects only to the addresses it checked (no DNS rebinding), and follows up to 5 redirects by hand, checking each. 15s, 20 MB (`FILE_MAX_BYTES`, like attachments). Text is decoded like a browser does (`textOf`: byte-order mark, the header's charset, a `<meta charset>` in the first 1 KB, else UTF-8; an unknown label reads as UTF-8). HTML goes through Mozilla Readability (linkedom) and turndown to Markdown with absolute links. Readability drops download lists as clutter (a statistics office's page of spreadsheets came out empty), so the data files the page links to (PDF, Excel, Word, CSV, JSON, XML, text) that didn't make it in are listed after the text, up to 6,000 characters, as "Files linked on this page": that makes them fetchable too. PDF, Word and Excel files are told by their bytes (servers often call them `application/octet-stream`) and read by `fileText` (core `file-text.ts`, the same reader as `chat.read_file`; Excel as CSV per sheet); a file cut at the size limit is refused, since half a file can't be read. Text, JSON and XML (RSS and Atom included) pass through; other files are refused; cut at 20,000 characters, saying so. Link previews (`linkUnfurl.ts`) read a message's first links with the same `fetchBody` (5s, 1 MB), and keep their own copy of the page's picture so readers never load third-party images ([Chat → linkPreviews](chat.md)).
- **Compaction:** once a reply leaves a session's context over 40k tokens, older turns fold into the session's summary (a ~15k-token tail kept verbatim). The app still shows everything; agent DMs show a divider where the summary starts.

## Sidebar and rail arrangements
`arrangements` holds ordered id lists with structured `workspaceId`, `userId`, `list` and optional `entityId` columns. `core/arrangements.ts` defines each list's scope and entity once. Parent-page ids identify sibling levels; record-type ids identify view and column lists. Rail tabs, pins, recents, pin order, DMs, Chat sections, folds and expanded pages are personal per workspace. Workspace switcher order is account-wide (no workspace id). Channels, page siblings, databases, view tabs and columns are shared (no user id). The All tab's layout and grouping are database settings (`recordTypes.display`), not ordered ids. Moving pages between parents is unchanged.

One `arrangements.get` subscription returns the open workspace's personal/shared lists and account workspace order. The shell waits for that loaded set and the migration before mounting, so saved order/pins render immediately; databases arrive with their saved display before RecordList mounts. `useStoredIds` reads the loaded context and sends changes as one small command (`arrangements.change`): `add` (pin, fold, expand, show a column), `remove`, `visit` (recents, newest first, 12 kept) or `move(id, beforeId | null)`. The server applies it to the list it holds now (core `applyCommand`), never a list a device sent, so changes from two devices at once both land; the optimistic update applies the same command to the cached list, in the requesting workspace only. A drop on ids that were shown but never saved names them in `fill`, appended first if absent, so it lands where it looked; a database's first column change names the default columns in `seed`. Shared writes need `sidebar.arrange`: people whose role can rearrange shared sidebar lists (Member can by default). Read-only lists do not drag, and save failures appear in the app's existing notice. Nobody receives or moves an id they can't see. `get` cuts each shared list to the caller's view (`viewer`): channels to the ones they can see (each stored id read directly, never a scan of the workspace's channels: at most 2,000 per list and about 8 MiB in all, past which the rest are left out, never an error; checked against the caller's seats, one indexed read, and each channel's privacy and Who can access list). Commands and `fill` use the same resolver, databases to the ones they reach, a database's views and columns to nothing if they can't open it, and a page level to its pages they can open (at most 500 per level). Pages go through one cached reader shared by levels, their parents and every ancestor check, budgeted at 2,000 reads per call (well under 4,096 index ranges); levels past the budget are left out. Personal lists pass through. A command reads only the id it names and its anchor: each must be live, in this list and visible to the caller, and a hidden one fails just like a missing one ("Not found."). On shared lists that includes `remove`; personal lists remove any id, so stale ones can be cleaned up. A command runs against the whole stored list, hidden ids included, so someone who sees fewer items moves only theirs, anchored on a neighbor they see, and the hidden ones keep their order. `fill` is cut to the caller's view too (a view `fill`, to views of that database in this workspace); `seed` (columns) to live fields. Lists of a page or database go when it's deleted forever.

`desktop/arrangements.ts` translates old localStorage keys only during import, writes only absent lists/settings, and deletes each key after success. It is bounded (`IMPORT_IDS_MAX` 100 ids, about 8 MiB read, before database keys are resolved too): past that it saves what it has, so it always finishes and the key is cleared; order past 100 items is dropped. It's `COMPAT(0.1.0-alpha.10)` code, deleted in a later release. Recents are deleted locally and rebuild; they could belong to a previous person on a shared computer. Pins still import, so the first signed-in person claims old computer pins. Failed imports are logged and retained for next launch, while the app opens normally. Deleted entities and inaccessible workspaces are discarded. No local reading fallback remains. Sidebar width/hidden state and chat drafts stay local, as do panel sizes and other device settings.

## Data lifecycle
What happens to rows when what they belong to goes. One registry, `lifecycle.ts`, run by one runner, `cascade.ts`. **Every table must declare what happens when its owner goes**: `tests/lifecycle.test.ts` fails on a table missing from the registry (and the registry's type won't compile).
- **Scopes:** `workspace` (deleted), `reset` (a workspace reset: its `workspace` edges, minus tables marked `keepOnReset`), `member` (removed or left), `user` (account erased), `connectorInstall`, `automationInstall` (uninstalled), `page`, `record`, `database`, `field`, `channel`, `agent` (deleted forever from [Trash](data.md#trash): the entry goes first, then the cascade, and the item itself last), `role` (deleted: the row goes at once, so its id grants nothing; then the cascade scrubs it from members, invites, connector installs and channel, database and page access lists. An emptied list stays Owners only, and nobody is given a replacement role).
- **Per table, per scope:** delete an index range (`index` + `eq`, optional `where`), patch it instead (`scrub`), go with a parent row (`childOf`, one level), or `keep` with a written reason. `onDelete` runs just before each row goes (leaving each workspace for an erased account; starting an `automationInstall` cascade for a removed member's just-them automations, so others' grants go too). Every table with a `workspaceId` is reached by a `workspaceId`-first index or as a child.
- **Access ends first, in a small mutation:** the member, install or connector row goes, or the workspace is marked `deleting` (`memberOf` refuses it, so every request and agent call does). Nothing else in that transaction grows with the data. Then `startCascade` cleans up.
- **Late writes are refused:** anything an action writes back after a wait rechecks what it belongs to at save time: connector tool lists the install they were listed under, OAuth saves the membership and install (below), the turn queue, activity log, approvals, usage (`recordUsage`), webhooks, scheduled runs and wakeups (`wake`) a live workspace (`liveWorkspace`, or `memberOf` for every actor), invite emails that the invite is still there. So no row lands behind a cascade that already passed its table.
- **Bounded by bytes, not rows:** each run reads one page of one edge (Convex allows one paginated query per function), up to 100 rows or ~4 MiB, then children and `where` lookups one document at a time, stopping while there's still room for a whole 1 MiB document under an 8 MiB budget (Convex's limit is 16 MiB; up to 2,000 writes). What's done is saved (`edge`, `cursor` on its `cascades` row) and the next run is scheduled; a page that didn't fit is read again smaller (`rows`), so skipped rows are never reread forever. A workspace's own row goes last. A table whose rows hold storage files lists those fields in `files` (a storage id, or a list of `{ storageId }` like `chatMessages.attachments`); the runner deletes the files with each row, wherever a cascade deletes it.
- **Failures:** a cron (`cascade.resume`, every 15 minutes) restarts cascades untouched for 10 minutes whose last run (`run`) failed, counting `attempts` and keeping its `error`. After 3 in a row it's marked `stuck` and left alone, and logs once. To find them: the `cascades` table in the dashboard, `stuck` = true. To resume: fix the cause, deploy, then `npx convex run cascade:retry '{"id":"<cascade id>"}'`; it carries on where it stopped. **Never delete a cascade row** to unblock someone: its rows would stay, and rejoining would bring them back.
- **Rejoining and reinstalling wait** while the old cascade runs ("still being cleaned up" / "still being uninstalled"), so old seats, rules and credentials never come back. A stuck one keeps saying so until it's retried. Not a time filter: `_creationTime` isn't in commit order.
- **Connector sign-ins** (`connectorOAuthFlows`) name the membership (`memberId`) and install (`connectorInstallId`) they started under. Starting one and the final save both check those are still the rows there, so a sign-in from before a removal and rejoin, or an uninstall and reinstall, can't connect; older sign-ins without them are refused. Unfinished ones are deleted with the workspace, member, account or install.
- **Delete workspace** (`workspace.deleteWorkspace({ name })`, owners only, `workspace.delete`; the name must match): marks it `deleting` and starts the cascade, however many members it has; access ends at once (`memberOf` refuses it), and the cascade clears "last used" and deletes invites. **Erase account** (`workspace.eraseAccount`): first checks, with a few indexed reads per workspace however big, that they aren't the only owner of one with others (one already being deleted doesn't count). At once: deletes sign-in accounts so the email starts a new account, deletes sign-in rate limits and local sign-in codes (keyed by their email, which is about to go), and replaces the `users` row with `{ erasedAt }`. It's never deleted (~20 tables point at it). `authUserId` (lib.ts) treats an erased account as signed out, so a sign-in token from before can't recreate preferences, a name, a workspace or accept an invite; every account-scoped function uses it, and `nameOf` shows "Former member". `memberOf` refuses an erased account, so nothing acts as them while their memberships wait for the cascade, and an erased owner doesn't count as an owner (so the last other one can't leave meanwhile). Then the user cascade leaves every workspace (deleting ones they're alone in, a member cascade for the rest), deletes their sessions, preferences and personal connector accounts in every workspace (including ones left behind by removals before those deleted them), and clears what agents got back for them (`agentActivity.output`, `approvals.result`, shown only to them); a call that finishes after the erase is logged without them. What they said and did in team chats and history stays, as a former member's. In the app, these are under Danger zone in Settings: resetting and deleting the workspace on General (owners only), the account on Your preferences; each asks you to type the workspace's name or your email first.
- **Reset workspace** (`workspace.resetWorkspace({ name })`, owners only, `workspace.reset`; the name must match, checked on the server): puts it back to how it was when made. One small mutation marks it `resetting` and records `lastReset` (who, when; shown on General: there's no workspace audit log, and the activity log is cleared with everything else), then starts a `reset` cascade. `liveWorkspace` refuses a resetting workspace like a deleting one, so access, agent turns, wakeups, automations and late writes stop at once; `keptWorkspace` still counts it (owned-workspace cap, `mine`, erasing an account, an erased member leaving), and `mine` lists it with `resetting`, so apps that have it open show "Resetting…" instead of switching away, then reopen on #general. The cascade deletes every workspace edge except what's marked `keepOnReset`: members, `roles` (custom ones too) and who holds which, invites, the invite email limit, preferences, and `usage` (the bill: spent is spent, and it still counts toward the picture budget). Everything else goes, personal skills and Archive included; who can access each channel, database and page is stored on that place (`access`), so it goes with it. The workspace row stays as it was (name, logo, currency, models, budgets). Its last run calls `startAgain` (workspace.ts), the same seeding a new workspace gets: default agents, #general, every member in it with a fresh tutorial, the welcome. Two writes a member and no per-member reads, so that last transaction fits up to ~7,000 members.
- **Trash:** deleting moves records, databases, fields, pages, channels, agents, and skills and automations (including retained library installs) to Trash (`trash` table) for 30 days; `trash.sweep` (hourly) and "Delete forever" (`trash.manage`) start the cascades above. See [Data → Trash](data.md#trash).
- **Retired memory timestamp:** `memories.createdTs` remains optional for existing documents because no migration cleared it. New memories omit it; member cleanup uses the cascade, not timestamps.
- **Link previews:** `linkPreviews` rows (one per URL per workspace, shared by the messages that post it) and their picture copies go with the workspace (`workspace` edge, `files: ["image"]`). Member, channel and account cleanup keep them: they hold a public page's title, text and picture, and no one of those owns a row. The unfurl action's write-back (`linkPreviews.save`) rechecks the message and a live workspace, so it can't land behind the cascade; a replaced picture is deleted when its row is rewritten.
- **Message files:** deleting a message deletes its files at once (`messages.remove`); a channel in Trash keeps them until it's deleted forever (the `channel` cascade deletes its messages, and their files with them); a deleted workspace's go with its messages. Unattached uploads go with the hourly sweep after a day, or at once when removed from the composer (`files.discard`). Leaving or an erased account keeps them: they're team history, like the messages.
- **Wakeups:** one set of edges for every wakeup. A removed member's are deleted with them (nothing runs as anyone else; `wake` checks membership too). An agent, channel, record or database deleted forever cancels pending ones, saying why; in Trash they're held. Fired and cancelled rows go after 30 days (`wakeups.forgetSettled`).
- **Arrangements:** member cascades delete personal workspace rows; user cascades delete all personal rows, including account-wide workspace order; workspace cascades delete all rows in that workspace. Page and database cascades delete rows indexed by their `entityId` when deleted forever. Shared rows survive a person leaving.
- **Dead rows:** unfinished connector sign-ins are swept hourly (`forgetExpiredOAuth`); deleting a message deletes its `recordMentions`. What agents already saw of a deleted or edited message stays in their sessions (product decision pending).
