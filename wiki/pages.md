# Pages

Free-form writing, Notion's way: a **page** is a title plus blocks. Standalone pages (wiki, SOPs, meeting notes) and the body under every record's fields are the same thing; a record's body is a page with `recordId` set. Code: `backend/convex/pageOps.ts` (rules), `pages.ts` (app API), `pageSync.ts` (editor sync), `pageTools.ts` + `core/src/page-tools.ts` (agents), `pageMarkdown.ts` (Markdown); app in `desktop/…/views/Pages.tsx` and `views/pages/`.

## Model
- **Page** (`pages`) — `workspaceId`, `title` (standalone only: a record's body shows the record's name), `recordId?`, `archived` (in Trash), who made and last changed it. Optional `parentId` nests standalone pages; record bodies cannot be parents or children. `by_parent` (workspace, parent, record, archived, title) pages through one tree level. The existing index, `by_workspace` (workspace, record, archived, title), serves the sidebar (standalone, live, by title), a record's body, and the agent's exact-title lookup; `search_title` serves `pages_find`.
- **Content** lives in the [`@convex-dev/prosemirror-sync`](https://github.com/get-convex/prosemirror-sync) component, keyed by the page's id: ProseMirror **snapshots** (whole document) and **deltas** (steps). The editor is [BlockNote](https://www.blocknotejs.org) (MIT core, Mantine UI; no paid XL packages) through the component's `useBlockNoteSync`. The backend reads and writes with BlockNote's ProseMirror schema (`pageSchema`, an unmounted editor needs no DOM).
- **Versions** (`pageVersions`) — the page's history: one row per run of edits, each pointing at the component snapshot it ends at (`version`), with `userId` (who started it), `agentId` when an agent did it for that person, `others` (anyone else who edited meanwhile, up to 10), `editedAt`, `restored` (the time of the version it brought back), and `n` (counts up per page).

## History, like Notion
Notion saves a version every 10 minutes while you edit, and another 2 minutes after you stop ([help](https://www.notion.com/help/duplicate-delete-and-restore-content)). Same here (`recordVersion`):
- Each accepted batch of steps saves its canonical snapshot and history atomically on the server (`saveTransform`), as do agent writes and restores. Client snapshots are ignored: they cannot invent versions, overwrite content, or change attribution.
- Each batch extends the open version if the page's last edit was under 2 minutes ago (`IDLE_MS`) and the version started under 10 minutes ago (`VERSION_MS`), whoever made it; a new author joins its `others`. Its old snapshot is deleted. Otherwise it starts a new version. So people typing together make one version, not one per keystroke, and can't push older history past the cap.
- Shown as "Edited by Dana", "Edited by Companybot, for Dana" or "Edited by Dana, Ben" (`whoLabel`, as record history), with the time. Pick one to see it read-only.
- **Restore** puts a version's content back as a new version ("Restored by Dana · the version from …"), so nothing is lost: the version it replaced can be restored too. It's a server-side transform, so open editors update live.
- Credit is per version, not per change: a version co-edited by Dana and Ben doesn't say who typed which word. Per-step authorship would need the component to store authors (on its roadmap).

## Storage bounds
- **Per document:** a page's content is capped at 500 KB of JSON (`PAGE_MAX_BYTES`), measured in encoded bytes on the resulting document and serialized steps before every editor or agent write, so nothing nears Convex's 1 MiB document limit. Past it: "Split it into several pages."
- **Per change:** steps are stored in deltas of at most 60 KB (`DELTA_MAX_BYTES`), because the component reads up to 100 deltas at once (catching up, cleaning up) and a delete reads too: 12 MB, under Convex's 16 MiB. A bigger batch is split across deltas. One step over it (a huge paste) is refused: "That's too much to add at once." So is a top-level block over it, which keeps every version restorable: agent writes and restores go in a block per step.
- **Compaction:** the newest 100 versions per page are kept (`PAGE_VERSIONS_MAX`); older ones go with their snapshots. Merging an edit run deletes its previous snapshot. Deltas older than a day and behind the latest snapshot are deleted on every accepted edit (the component's `deleteSteps`, which never deletes past the latest snapshot), so a client that was briefly offline can still catch up. So a page holds at most ~101 snapshots plus a day of steps. The component is used unpatched: an editor more than one batch behind catches up on its own, since applying a batch fires the editor's update, which queues another sync.
- **Reads:** lists take 200 pages (sidebar) or 50 (`pages_find` list, paged) or 20 (title search, paged), history 20 per page.

## Rules
- **Access:** every member reads every page; `pages.edit` (owner, member) creates, writes, renames, deletes (to Trash) and restores. A page is read-only while it or its record is in Trash.
- **Sync API:** `useBlockNoteSync` calls `pageSync.*` with the page's id alone, so those functions find the workspace from the page and check membership there (`memberOf`), not from the request like the rest of the API (`functions.ts`).
- **Record bodies** are always an editor in the app, Notion-style, under the record's fields. The page is made when someone who can edit first opens the record (or an agent writes in it), so 100k records nobody opens don't carry 100k empty documents. Creating is idempotent. They go to Trash with their record and can't be renamed or deleted on their own.
- **App structure:** pages open from the sidebar; there's no index screen (`/pages` goes to chat, and deleting a page opens its parent, else chat). Missing pages use `NotFound` with the page icon. Trash is under Settings → Trash; the sidebar stays an expandable page tree outside Settings.
- **Nested pages:** the sidebar loads each expanded level in pages of 30, with expansion saved locally per workspace. Hover + creates inside; the row menu (⋯ or right-click, like every sidebar row) has New page inside, Move to… and Delete. Move to… lists the top level and top-level pages, and `pages.search` finds any page by title (nested ones show their path); one click moves, the current location is marked. Saved expansion ids are checked in reactive batches of 100; deleted, inherited-Trash and invalid ids are pruned even below collapsed branches. Breadcrumbs show ancestors. The server refuses foreign parents, cycles, record bodies, and nesting beyond 32 levels. Deeper moves inspect at most 1,000 descendants and refuse larger branches; shallower moves stay cheap. Move history (100 per page, person and agent attribution) lives in `pageMoves`, shown under History → Moves, separate from restorable content versions.
- **Page blocks:** `/page` creates a child and inserts a clickable link. Children created from the sidebar also appear below the editor unless already linked in the document. Page links are ordinary ProseMirror link marks (`companybot://page/<id>`), styled with a page icon and handled in-app. The visible, editable text is the title at insert time; renaming the child rewrites matching links in its parent (only where the text still equals the old title), as an edit by whoever renamed. Links elsewhere keep their text. Alpha.7 retains a normal link mark; its Electron navigation guard blocks app protocols from opening external handlers. After alpha.7 support ends, these can become inline page mentions with live titles. The unlinked-child list scans after a 300 ms pause in document changes, with pending work cancelled on unmount. Removing a link leaves the child page and its parent relation intact.
- **Subtree Trash:** only the deleted root gets an entry. “Includes sub-pages” is captured at deletion only when it took live children with it; already-trashed children do not trigger the label. Descendants inherit Trash state through their bounded ancestor chain; all editor and agent writes recheck it, so trash/restore is atomic without fan-out. Independently deleted children remain deleted. Restoring a separately deleted child whose parent is missing or in Trash puts it at the top level; an in-progress purge cannot be escaped. Purging schedules a `page` cascade per descendant through the indexed parent edges, deleting content, versions, move history and any separate Trash entries in bounded runs. Missing ancestors fail closed until cleanup finishes.
- **Images:** paste, drop or `/image` in the editor (BlockNote's `uploadFile`). The app uploads through the shared picture endpoint (`useUpload`; PNG, JPEG, WebP, GIF, 2 MB), then `pages.addImage` (needs `pages.edit`, not in Trash) claims the caller's own upload into `pageImages` and returns the file's storage URL, which the image block keeps. An image copied into another page in the workspace (paste, agent block copy, restore) gets a row there too when the write is saved (`adoptImages`, new image URLs only); other workspaces' URLs are never adopted. Files outlive the upload sweep, stay through Trash (so restore and old versions keep working), and go when the last page with a row for them is deleted, including record bodies (their record cascade runs a page cascade). Removing a block keeps the row until the page goes, since a restored version may show it. Video, audio and file blocks are off the slash menu (uploads take pictures only; the CSP loads no outside media). Agents can't upload; `pages_read` shows images as `![caption](url)`. Alpha.7 has the same block schema, so it keeps image blocks intact, but its CSP shows them as broken images.
- **Delete goes to Trash** ([Data → Trash](data.md#trash)). Deleting forever (an owner, or 30 days on) deletes its row at once, then its content (`pageSync.deleteDoc` → the component's `deleteDocument`, which deletes in batches) and a `page` cascade for its versions (`deletePage`). A record's body goes in its record's cascade.

## Agent tools
`pages_find`, `pages_read`, `pages_write` (`core/src/page-tools.ts` → `ToolContext.pages` → `pageTools.ts`, through `runningTurn` like records). Granted as `pages.*`; Companybot has them. Reads, writes, moves and restorable Trash operations are `risk: none`.
- `pages_find` — by title words, or every standalone page by title, with `cursor`. Record bodies are found through their record. Rows include `parentId`; `parent` lists a level (null for top-level), with the same pagination. Follow child ids and cursors to read the tree.
- `pages_read` — a page (id or exact title) or a record's body (`record`) as Markdown, 20,000 characters per call (`start`, `next`), plus its last 5 versions with ids. `history` pages every retained version (20 per call, `moreVersions`/`cursor`), and `version` previews a selected snapshot. `format: blocks` reads the complete structured block JSON in chunks, including colors and alignment.
- `pages_write` — create (`title`, optional `parent` and `markdown`), move (`action: "move"`, `page`, `parent`; null for top-level), append (default) or replace content, rename, delete/restore (`trash`), replace/append structured `blocks` from a completed read, or bring back a version (`restore`). `pages_find` with `trashed` lists pages in Trash. Each write is a version "Companybot, for <person>", grouped like a person's edits.
- **Sub-pages** come back beside the content, not in it: `subpages` (up to 50 direct children) and `subpagesMore`; use `pages_find` with `parent` and its cursor for the rest. Keeping them out of `markdown` means a read → edit → replace never writes the list into the page.
- **Markdown:** BlockNote converts through HTML, so `pageMarkdown.ts` runs in Node with happy-dom as its DOM (jsdom reads files at runtime and can't be bundled). The runner converts before writing and after reading, outside the mutation. Markdown is lossy: colors and alignment drop. For rich edits use `pages_read` with `format: blocks`, concatenate all chunks, then change the JSON array with `pages_write.blocks`; it uses the same schema, size limits, permissions and version writer as the editor.
- Agent edits show in Settings → Activity as tool calls ("Wrote page Roof inspection SOP"), like any agent change.

## Notion behavior and deliberate differences
Research: [Notion sub-pages](https://www.notion.com/help/create-a-subpage), [Notion deletion](https://www.notion.com/help/duplicate-delete-and-restore-content), [BlockNote custom blocks](https://www.blocknotejs.org/docs/features/custom-schemas/custom-blocks) (checked October 27, 2026).
- Like Notion: sidebar toggles and hover +, slash-created children, ancestor breadcrumbs, and restoring subtrees.
- Notion deletes a subpage when its page block is removed. Here, per the feature requirement, removing the block keeps the child. Move retains old inline links as references. Slash creation stays on the parent so the new block is visible; click it to open the child.
- Drag reorders pages within a level; like sections, channels and DMs, the order is yours and stays on this computer (see Architecture). Nesting is only through Move to… (dragging into another page would hide where it went). Nesting/deeper-move bounds above are product limits for bounded server work. Record bodies are excluded from hierarchy in this release.
- Page links use the existing link mark for alpha.7 compatibility, with a title captured at insertion and kept in step in the parent on rename (Notion shows live titles everywhere). The unlinked sub-pages list remains, with a debounced scan so typing does not walk the document on every keystroke.
