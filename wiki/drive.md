# Drive

Drive is the rail tab for the team's pages, folders and files, like Google Drive: a tree in the sidebar, a listing screen for the top level and each folder, and screens for pages ([Pages](pages.md)) and files. Code: `backend/convex/driveFiles.ts` (files: rules and app API), `driveTools.ts` + `core/src/drive-tools.ts` (agents), folders in `pageOps.ts`/`pageTree.ts`; app in `desktop/…/views/Pages.tsx` (Drive root, folders, pages), `views/Files.tsx`, `views/drive/` (listing, viewer, uploads, icons) and `views/pages/PageTree.tsx` (the sidebar tree, Move to…, access dialogs). Decided 2026-11-04 (files first; native spreadsheets, slides and sites are issues).

## Model
- **Folder** = a `pages` row with `kind: "folder"` (`kindOf`). No document, versions, images or page blocks; `requireContent` refuses the editor, sync and content tools. Everything else about pages applies unchanged: tree level (`by_parent`), nesting rules, `pageStates` access inheritance, Archive cascade, move history, sidebar order, pins, `pages.search`.
- **File** (`driveFiles`) — `workspaceId`, `parentId?` (a folder, or the top level), `name`, `type` (sniffed), `size`, a picture's `width`/`height`, `storageId`, `archived`, who made and last changed it, optional own `access`. `by_parent` (workspace, parent, archived, name) lists a level; `search_name` serves `files_find`. Names are unique nowhere: two "Invoice.pdf" in one folder are allowed, like Google Drive.
- **Rules of containment** (`parentFor(…, child)`): folders hold folders, pages and files; pages hold sub-pages only; folders and files sit in folders or at the top level. Depth and cycle limits are pages'.
- **Access:** `fileStates` builds on `pageStates`: a file's list is its own (`driveFiles.access`), else its folder's chain, else Everyone at Edit. Reads need View; `rename`, `move`, archive and restore need `pages.edit` and Edit. `keptAccess` applies to moves and restores, as for pages. A file under a folder that gets its own list is written to `replySources` with its folder ([Permissions](permissions.md#who-can-access)); reads of a restricted file record it on the reply ([Chat → Private replies](chat.md#private-replies)).
- **Archive:** `folder` and `file` kinds in `trash`, both under `pages.edit` (`trashPermission`). Archiving a folder archives everything in it (descendants inherit through `pageStates`/`fileStates`, no fan-out; "Includes its contents" when it took live children). A file restored while its folder is archived or gone lands at the top level, keeping its folder's list if that was stricter. Deleting forever: `deleteDriveFile` removes the row and its storage file; a folder's purge cascades through `lifecycle.ts` (`driveFiles` has a `page` edge).
- **Uploads** share chat's endpoint (`/files/upload`, 20 MB, sniffed types; [Chat](chat.md)): `driveFiles.add({ file, parentId? })` claims the caller's own upload like `claimFiles`, so a storage id someone else learns is worthless. Accepted kinds: pictures, PDF, Word, Excel, PowerPoint, plain text, Markdown, CSV, JSON (`FILE_ACCEPT`, `fileTypes`).

## The app
- **Sidebar** (`DriveNav`): a Home row for the top level, lit when it's open; then "All files", a section that folds (`folded`, id `files`) with + on its header (New page, New folder, Upload files), holding the tree; then the sections people add (shared, `sidebar.arrange`; wiki/architecture.md), each holding top-level pages, folders and files in its own order, each with what's under it (`sidebarSections.driveRows`), and left out of All files. New section is the + beside Drive's name, not All files' +: a section sits beside All files, and that + makes things in All files. A section's hover + makes a page or folder or uploads into it (uploads in flight show there); its ⋯ renames or deletes it (what it held goes back to All files). Folded, a section keeps the open item. Each level (`DriveLevel`) pages `pages.children` and `driveFiles.children` in 30s and shows them in one order, the level's shared `pages` arrangement (which holds file ids too; what nobody has placed yet follows it, pages then files by name); a page's level skips files. **Folders on top** (`preferences.foldersFirst`, personal, off by default; `views/drive/order.ts`): each level (`useSortable`'s `arrange`) and section shows its folders ahead of its pages and files, each keeping their order; a drop among the folders lands in the saved order where it was let go, so it shows first among the rest. **Dragging** (`sortable.ts`; the whole sidebar is one drag group, drawn as a tree, as in Notion): the row stays, faded, a copy of it follows the pointer up and down, and a line shows where it lands: between another level's rows (into an open folder, or, dragged left past the folder's rows, out among its neighbors), or at the top between All files and the sections. Anything dropped onto a folder's row (pages onto a page's) goes in, last in its order; the row lights while the pointer is over its middle; Home takes rows to the top level. A folder can't go into itself or what's in it (its box carries those rows). Only top-level rows go into a section; moving one into a folder takes it out of its section. `views/drive/move.ts` moves the row at once (optimistic, in every loaded level) and saves its place in the new level's order in the same drop (a `move` command after the move mutation; Convex runs them in order). A failed move puts the row back and shows the error. Rows drag when the person can rearrange shared lists (`sidebar.arrange`); only rows they can edit go to another level, and only into ones they can edit. Folder menu: New page inside, New folder inside, Upload here, Move to…, Who can access, Archive. File menu: Rename, Move to…, Who can access, Archive, Pin to rail. Uploads in flight show under the level, three at a time (`limiter` in `views/drive/upload.ts`, since the browser allows few connections to the backend at once and one slow file mustn't hold up the rest): Waiting, then progress, then Saving… until the server has it; a failed one says so until dismissed.
- **Screens:** `/pages` is Drive's top level (titled Drive: the listing, drop files on it); `/pages/<id>` opens a folder (its listing, rename by title, Move to…, Who can access, Archive, drop files on it) or a page (the editor); `/files/<id>` opens a file (`FileView`). Every Drive crumb trail starts at Drive. A listing's rows drag within one level (its own group, rows sliding): onto a folder to move in, folders and pages to reorder; out of the folder is the sidebar's or Move to….
- **Viewer** (`FileViewer`): pictures and PDFs straight from the storage URL (`<img>`, `<iframe>`; the CSP allows `frame-src` for Convex storage), Word through [docx-preview](https://github.com/VolodymyrBaydalka/docxjs) (loaded on demand, fonts ignored), Excel, CSV and PowerPoint through core's `office-text` readers in the renderer (the same readers agents use; 2,000 rows × 50 columns and 25 MB shown at most), Markdown rendered, text and JSON as text. Anything else, or a failed fetch, points at **Open in browser**, which opens the storage URL.
- **Move to…** (`MoveItem`): pages may go in pages or folders; folders and files in folders or the top level. Destinations: the top level, the top level's rows, or `pages.search` by title. The server checks the rest. Dragging does the same where both ends are on screen (above).
- **Who can access** (`FileAccess`, `PageAccess`): the shared `WhoCanAccess`, following "Same as its folder" / "Same as its parent" / "Same as Drive".
- **Pins:** `file:<id>` pins resolve through `driveFiles.titles`; folders pin as pages with the folder icon.

## Agent tools
`files_find`, `files_read`, `files_write` (`core/src/drive-tools.ts` → `ToolContext.files` → `driveTools.ts`); granted as `files.*`, Companybot has them (`companybotFileTools` migration adds them to existing ones). `pages_find`/`pages_read`/`pages_write` know folders: rows carry `kind`, reading a folder lists its pages and files, `kind: "folder"` creates one.
- `files_find` — by name words, or a level (`folder`, null for the top level), `trashed` for Archive; rows `{ id, name, type, size, folderId, edited }`, 50 a page.
- `files_read` — a file's text, 20,000 characters a page (`page`), through the same reader as `chat.read_file`: a PDF's pages, Word paragraphs, each Excel sheet as CSV, slides in order. Pictures are refused (they reach agents through chat).
- `files_write` — save a chat attachment into a folder (`from`: a file id from the chat; `inside`, since it can come from the person's private chats), write text (`text` with a `name` ending in .txt/.md/.csv/.json, up to 500,000 characters; the type is sniffed from the name), rename, move (`folder`, null for the top level), or archive/restore (`trash`; `locked`, asks first). Text written by an agent is stored as the person's upload (`saveText`), like a copy.
- Activity shows them as tool calls ("Saved Invoice.pdf"), like any agent change.

## Not built yet
- **Native spreadsheets and slides** (issues): a cell editor and a deck editor in Drive, with agent tools that edit cells and slides rather than whole files. Candidates: Univer (Apache-2.0) + SheetJS for sheets; slides have no mature MIT React option (Slidewise MIT/React is young; PPTist is AGPL/Vue).
- **Sites** (issue, blocked on #116 agent-built sites): a site in Drive is a folder of pages with a published copy; see the issue for the UX plan.
- Versions of a file (replace keeps the old one), previews in chat for Drive files, search inside file contents, video and audio.
