# Architecture

pnpm monorepo. Each folder in `src/` is a package.

| Package | What |
|---|---|
| `src/core` | Agent framework: agents, built-in tools, connectors, skills, memory rules. Pure logic, no I/O. |
| `src/backend` | Convex: database, sign-in, live updates, and the agent runner (`convex/`). |
| `src/desktop` | Electron app (electron-vite + React + Tailwind). Talks to Convex directly. |

## Concepts (`src/core`)
What each piece is. The rules for changing them: [Extending](extending.md).
- **Permission** — a workspace action and the roles allowed to take it (`permissions.ts`). Backend and app both read this table.
- **Tool** — something an agent can call. Built-ins live in code; connector tools are discovered from the connector's MCP server each turn and reach the model on demand through `connectors_search` / `connectors_call`, not up front. Ids are `group.name`.
- **Agent** — name, instructions, model, tool grants. A tool reaches the model only if granted, allowed for the person's role, and (connectors) installed, allowed, and connected.
- **Connector** — a catalog entry for a remote MCP server, with a workspace or personal connection and encrypted credentials. The catalog is currently empty.
- **Skill** — installable instructions: name, a short description, and Markdown instructions (Claude's SKILL.md fields). Agents see the descriptions and load the full text on demand. Made by anyone (`skills.create`), in Settings → Skills or by asking an agent (`skills_create`).
- **Automation** — a trigger (schedule, in-app event, or webhook) plus a prompt. Anyone can make their own. Each run posts the prompt in the chosen agent's DM with each person it runs for, as them, so the reply uses their permissions and connector accounts. Or, with a channel picked, once in that channel, as its maker (library ones: whoever picked the channel).
- **Widget** — UI an agent places in a reply (table, stats, card). Each is a tool; the app renders the stored props; the model gets a short receipt, not the data back.
- **Help** — docs for the people in a workspace (what Companybot is, every setting tab, how to do things), written as Markdown strings in `core/src/help/`, one module per area. Agents read them with `help.read` (no args lists topics; `topic` reads a page; `query` searches) and link people to the screen with `#/…` addresses, which the app opens in place (`markdown.tsx`). Companybot has the tool; any agent can be granted `help.read`. Keeping them current: [Extending](extending.md#help).
- **Platform guide** — how replies render, added to every agent's prompt after its own instructions.
- **Memory** — per agent, scoped `workspace` (team) or `personal`. Agents and people follow the same rules. Team memories are wiki-style: anyone can add, fix or delete them; each keeps who saved it (`createdBy`), its last 20 versions (`memoryVersions`, restorable) and goes to Trash when deleted, so wrong changes are undone rather than prevented (Lindy, Notion and Asana do the same). Personal memories are only their owner's; workspace owners can't read them either. In chats with 2+ people, agents read and change team memories only, but can save a new personal one for the person who asked. Owners can turn memory off for the workspace (`workspaces.memory`); agents then get none, and nothing is deleted.
- **Chat** — channels, DMs, threads, reactions; agents reply when mentioned (or to everything in their DM), acting as the person who asked. See [Chat](chat.md).
- **Approval** — a held tool call shown as a card in chat (`approvals.ts`). Action rules live in `action-rules.ts`, wording in `action-words.ts`. See [Permissions](permissions.md).
- **Activity** — database, saved-view, field and record changes (`records.activity`), plus every tool call an agent makes, with its input and result (`activity.ts`). Widgets and `connectors_search` aren't logged; read-only tools are marked so the app can show changes only.
- **Database** — A collection an owner creates. Each contains records and fields; shared saved views hold filters, sort and columns. Existing tables (`recordTypes`, `records`, `recordFields`) and public paths keep their names for installed apps. Changes enter record history; record changes can be undone. See [Data](data.md).
- **Web** — `web.search` and `web.fetch` (`web.ts`): search through a provider, then read pages as Markdown. `web.fetch` opens only links the person wrote (this turn's messages, the thread's parent, the message a turn resumed after an approval started from: `turnContext`'s `asked`) or that came up in this turn's web results, so an injected instruction can't send data to a link the model made up. 5 searches and 10 pages per reply.
- **Turn input** — what the model gets each turn (`turn-input.ts`): a fixed system prompt, the agent's session in that place replayed exactly, and one new message. Built for prompt caching.

New workspaces start with only **#general** and **Companybot**. No databases, pages, skills, automations or connectors are seeded. Companybot can help owners create databases and anyone create skills and automations; the table, stats and card widgets remain available.

## Backend (`src/backend/convex`)
- **Sign-in:** Convex Auth (beta) with a 6-digit email code sent through Resend. Signed out, the app opens on a one-line landing (`views/Landing.tsx`, Get started), then sign-in (`views/SignIn.tsx`). Both use the same frame (`Split`): content centered on the left half, and on the right a picture drawn in code (`views/Art.tsx`, an SVG of flat shapes with grain), so no image ships.
- **Workspaces:** a person can be in several (`members`, one row each). First sign-in joins every workspace that invited the email (`ensure`); with none, nothing is made: the app shows onboarding (`views/Onboarding.tsx`, three steps: your name, the company and its currency, emails to invite), which ends in one transaction (`setUp`: name saved first so the welcome uses it, then the workspace as owner with `#general`, then the invites as members; a bad email refuses it all). The same screen comes back whenever you're in no workspace, such as after deleting your last one. **The workspace comes from each request, never from server state:** every public function is built with `functions.ts` (`query`/`mutation`/`action`), which takes `workspaceId` and puts it on ctx for `getMember`, which checks membership in that workspace (not a member → null/refused). The app's hooks (`desktop/.../convex.ts`) add the open workspace to every call; a test fails if a screen imports convex/react's hooks directly. Which workspace is open is per device (localStorage, pinned once chosen); `preferences.workspaceId` is only "last used", for a device's first launch (`workspace.mine`, `switchTo`). A row from another workspace (by id) looks like it doesn't exist: check it with `requireInWorkspace(member, row, what)` or a `require*` helper built on it (`tests/workspaces.test.ts` tries every id-taking function from the wrong workspace). A request that names no workspace acts nowhere. The retired `legacyWorkspaces` table is emptied by a migration, then dropped (COMPAT). Anything acting for someone in a known place (turns, approvals, automations, agent tools, connectors, OAuth flows) passes that workspace to `memberOf(ctx, userId, workspaceId)`. The rail at the far left (`WorkspaceRail`, Discord-style) shows a logo per workspace to switch, invites to join or decline, and + to start one (`create`: you're its owner, with the default agents, #general and a welcome, like a first sign-in's). Joining or creating opens the workspace once `mine` lists it. Other workspaces show a dot when a chat is unread and a red count of chats with an unread @mention or DM (`activity`); ⌘1–9 switches. Creating is capped at `MAX_OWNED_WORKSPACES` (10) owned. Your avatar sits at the rail's bottom: Account settings and Sign out. The workspace menu above the sidebar opens Workspace settings or leaves (`leave`; not the last owner).
- **Invites:** owners only (`members.manage`). One per email per workspace; accepting checks the signed-in (code-verified) email, so an invite can't be used by anyone else or for another workspace. Each invite (and Resend) emails who invited them, the workspace, and the download link (GitHub Releases), through the sign-in Resend account (`invites.ts`, text in core `invite-email.ts`); local backends log it instead. Limits: 20 emails per workspace per day; one email per address per 10 minutes, however invites come and go (a resend inside it is refused; a new invite is saved without one). Names are cut to one line before they go into the subject. Removing someone (or leaving) ends access at once, then a member cascade ([Data lifecycle](#data-lifecycle)) drops their channel seats, automation opt-ins, permission rules, personal connector accounts (the workspace's own stay), personal memories, unread mentions, and automations only they could see (just-them ones, which nobody else could delete); rejoining waits until it's done, so it starts strict. DMs keep them as a past participant.
- **Messages** are ordered `parts` (text, tool activity, widget) plus `text` (plain text only, for history and summaries), and up to 10 `attachments` (storage id, name, sniffed type, size, a picture's pixels; `files.ts`, [Chat](chat.md)). History shows the agent a one-line note for each widget it showed.
- **Chat:** `chats.ts` (channels, DMs, unread) and `messages.ts` (timeline, threads, reactions); shared rules and the visibility-aware channel lookup in `chatOps.ts`; agent tools in `chatTools.ts`. Public channels are readable by the workspace; private channels and DMs by members.
- **Agent turns:** `messages.send` queues an `agentTurns` row per responding agent (`turns.ts`). One runs per agent per place (chat + thread); the rest wait; one stuck over 5 minutes is failed. A running turn streams its reply into the database via `agent.respond`; the app sees it live. Agent replies never queue turns.
- **Sessions:** `agentSessions` holds each agent's context per place. Each turn's prompt is stored (`agentTurns.prompt`) and replayed byte-identical later. Model calls send `x-session-affinity`.
- **Agents:** stored per workspace. Owners create, edit and delete them (to [Trash](data.md#trash); the last agent stays). Every save writes an `agentVersions` row; restoring saves an old version as the newest. Replies read the agent fresh each turn, so edits apply from the next reply.
- **Models:** an agent can run on any AI Gateway language model that uses tools. The catalog keeps the gateway's `vision` tag (`ModelInfo.vision`; the fallback models have it, GPT-6 Luna included), which decides whether a turn's pictures are sent to the model. `modelCatalog.ts` caches them in one `modelCatalog` row from the public `GET https://ai-gateway.vercel.sh/v1/models` (no key; `type: "language"` with the `tool-use` tag, plus name, context window and $/M input/output), since queries can't fetch: a daily cron, and `refreshIfStale` when an agent editor opens on a day-old copy. A failed or empty fetch keeps the old copy; with none, core's `fallbackModels` (GPT-6 Luna, Claude Sonnet/Haiku/Opus 5.5) stand in. Saves accept the catalog, the fallback list, and the agent's current model, so an agent whose model left the gateway still saves other edits (the picker shows it as unavailable). GPT-6 Luna is the recommended default (`defaultModel`) for new agents and Companybot: about 20x cheaper than Claude Sonnet 5.5, whose agents moved to it (`migrations.lunaModel`).
- **Picture models:** the same fetch keeps the models that make pictures (`modelCatalog.imageModels`, `parseGatewayImageModels`): the `image-generation` tag on a `type: "image"` model (Imagen, FLUX, Recraft, GPT Image; run with `generateImage`) or a `type: "language"` one (`multimodal`: Nano Banana, run with `generateText`, pictures back in `result.files`), with one picture's listed price (`perImage`: the flat `image` price, else the default size's). Token-priced models (GPT Image) and some FLUX 2 ones list none; those take a price measured through the gateway on 2026-10-29, one default picture each (`measuredImagePrices`: GPT Image 2 and 2.5 about $0.007, GPT Image 1.5 $0.142, FLUX 2 Pro $0.03), else their `fallbackImageModels` entry's (`knownImagePrice`, in `catalogImageModels`). The gateway reported a cost for every picture model tested, so these only show in the picker and size the budget hold; the recorded cost is the gateway's. A refresh listing none keeps the old ones; with none, core's `fallbackImageModels` stand in. The catalog's `modalities` aren't used to tell editing apart: they list text-only input for models that do edit (GPT Image, FLUX Kontext), so edits are always sent and the gateway refuses a model that can't. Each workspace picks one (`workspaces.imageModel`, default `defaultImageModel` = `google/gemini-nano-banana-2.1`, the newest Nano Banana), in Settings → General.
- **Agent pictures** (`images.generate`, `imageGen.ts`): `prepareFor` (a mutation) checks, as the turn's person now, the monthly image budget (`workspaces.imageBudgetUsd`, default $20, 0 = off, against this month's `usage` rows of kind `image`, `imageSpent`, plus what running calls hold) and that each edit file is a picture on a message they can see (`visibleFile`), under 5 MB and 8000px, then holds one picture's estimated cost (`imageHolds`: `perImage`, else `IMAGE_PRICE_UNKNOWN_USD` = $0.25) so parallel calls see it: however many run at once, they pass the budget by one picture at most. `generateFor` then calls the model through AI Gateway (edit pictures as `images` for `generateImage`, file parts for `generateText`; aspect ratio as `aspectRatio` or Google's `imageConfig`), settles the hold into the real cost (the gateway's, else `perImage` or $0.25 × pictures, so no picture is free) with `imageGen.settle`: `usage` for the turn's person and agent whether or not it attaches, the place's running cost, and the turn's `imageCostUsd` for its reply's stats. A failed call releases its hold at once; one whose action crashed is released by a release scheduled with it (`HOLD_MS`, 15 minutes, longer than an action runs). It stores each picture with the type its bytes say (`sniffImage`; anything else, like SVG, is dropped) and attaches it with `files.attachToReply`, which enforces the reply's 10-file limit. The model gets a receipt with each picture's file id, never its data. What `providerMetadata.gateway.cost` holds for picture models hasn't been checked against a live call; the listed price covers it when it's missing.
- **Dictation:** the composer's mic sends a recorded clip to `dictation.transcribeAudio`, which transcribes it through AI Gateway (`openai/gpt-4o-mini-transcribe`) with the same `AI_GATEWAY_API_KEY`. See [Chat](chat.md).
- **Three kinds of data:** shared content (chat, memory) is fully live. Shared settings (agents, database names, shared views, workspace name, currency and memory on/off) are edited as a draft and saved; each has a `version`, and a save from an old version is refused as a conflict (`checkVersion`), with a "Use theirs / Keep mine" prompt in the app. Personal preferences (`preferences` table) are per person and sync across their devices. They include `notify` (desktop notifications and the dock badge: DMs and mentions, mentions only, or off).
- **Time zones:** each person has one: the zone they picked in Your preferences, else automatic (their computer's, which the app reports on launch), else UTC (`timeZoneOf`). Agents get it in the turn prompt, chat times in prompts use it, and `clock.now` answers in it. It isn't private: `workspace.team` returns it for profiles. Automation schedules use the zone of whoever made or installed them.
- **Permissions apply at once:** every agent tool call that reaches data (memory, records, chat, skills, automations) goes through `runningTurn`, which re-reads that the turn is running, the person's membership and role, and that they can still see the chat; connector calls re-read access too. Removals, role changes and leaving a chat take effect mid-reply.
- **Connectors:** `connectorInstalls` (roles allowed) and `connectorConnections` (AES-GCM encrypted with `CONNECTIONS_KEY`, encrypted in an action). OAuth sign-ins in progress sit in `connectorOAuthFlows` (one use, 15 min) until `/oauth/callback` finishes them. The runner connects only to connectors the agent's grants reach, skips any that fail or take over 10s, and tells the agent.
- **Skills:** `skillInstalls` (one row per skill). Skills people make live on their row (`custom`: name, description, instructions, `createdBy`; versioned; id `custom-…`), are on for the whole workspace, and can be changed or deleted by the maker or an owner (`canEditMade`); deleting moves it to Trash for 30 days. Agents make them through `skills.create` → `skills.createFor`, as the person they help. `installedSkills` (`lib.ts`) feeds both to each turn.
- **Automations:** `automations.ts` (CRUD/settings), `automationRuns.ts` (triggers and dispatch), `automationTools.ts` (agent tools), `automationOps.ts` (shared lookups). `automationInstalls` (agent, on/off, time zone, `audience`, channel, last run). Retired library installs keep their definitions on their rows. Member-made ones (`automations.create`) live on their install (`custom`: name, prompt, trigger; versioned like other shared settings; id `custom-…`) and run through the same code (`definitionOf`); the maker or an owner can edit (`canEditMade`). `audience` decides who it runs for: `creator` (only the maker; hidden from everyone else), `subscribers` (people who opted in, `automationSubscriptions`; the maker or installer is subscribed automatically), or `channel` (one post there acting as whoever picked it, falling back to an owner who can see it). DM runs post as the person in their agent DM (tagged `automation`, shown collapsed in chat). A cron (`crons.ts`, every 5 min) runs due schedules once per local day. In-app events go through `fireEvent`: `message.posted` (from `messages.send`, top-level channel messages, optionally one channel; posting back to that channel replies in the thread) and `member.joined` (from `workspace.ensure`). "Run now" runs it for you with sample data. Agents can list, create, and opt in through `automations_list` / `automations_create` / `automations_set_mine` (`automation-tools.ts`; the guide adds a short how-to when granted).
- **Webhook automations** get a secret URL: `POST <site>/automations/<token>` (`http.ts` → `automationRuns.receive`). Body `{ event?, id, person?: { email }, data? }` (`event` must match when the trigger names one, like `call.ended`; ones people make take any), max 32 KB; `id` dedupes retries (`automationEvents` holds webhook delivery ids, kept 7 days by `forgetOldWebhooks`, deleted after uninstall by its cascade, so a busy webhook can't block removal); `data` is appended to the prompt as fenced JSON. Runs in the channel if one is picked; otherwise in the DM of the member whose email is `person` (they must be subscribed, or be the maker of a just-me one), or for every subscriber if no `person`. Replies: 200 (ran, skipped, or duplicate; the reason is in `message` and `lastResult`), 400 bad body, 404 unknown token, 413 too big. Sender contract: oobagi/ai-agency#1052.
- **Permissions:** `permissions.ts` stores and checks action rules and owner locks; `connectorTools.ts` stores the reported tool metadata. Rules and invariants: [Permissions](permissions.md).
- **Activity log:** the runner writes an `agentActivity` row as each tool call finishes (input and result as JSON, cut to 4k chars; calls cut off by a failed reply are logged as errors). An entry is as private as its chat; results show only to the person the agent acted for, since they can hold things only that person may see. Owners get no extra access. The app shows it in Settings → Activity and when you click a tool line in a reply. Memories an agent changed carry `updatedByAgent` until a person edits them.
- **Approvals:** `approvals.ts` holds tool calls and queues the turn after a decision. Card, hash and replay rules: [Permissions](permissions.md#the-card).
- **Records:** `records`, `recordTypes`, `recordFields`, `recordValues` (the index for filtering and sorting any field), `recordHistory`, `recordMentions`, and `trash` for what's deleted. Databases are created by the team; existing database keys and links remain valid without any catalog. Agents use them through ten `records_*` tools (`recordTools.ts`), as the person who asked. See [Data](data.md).
- **Pages:** `pages` and `pageVersions`; content in the `prosemirrorSync` component. Standalone pages and every record's body are one thing. See [Pages](pages.md).
- **Pictures:** workspace logos (`workspaces.image`), people's photos (`preferences.image`, in every workspace), agents' pictures (`agents.image`, outside the versioned config) and page images (`pageImages`, [Pages](pages.md)) are Convex storage files (`images.ts`). The app POSTs the file, signed in (`Authorization: Bearer <token>`), to `<site>/images/upload?workspaceId=…` (`useUpload`, `upload.ts`, reusable for other uploads; `images.uploadEndpoint` gives the URL). That HTTP action reads the type from the file's first bytes (PNG, JPEG, WebP or GIF, `core/images.ts`; never the header, so SVG or HTML labeled `image/png` is refused), allows up to 2 MB, stores it with the sniffed type, and adds an `uploads` row naming the uploader (and their workspace, which must be theirs; 20 unclaimed at most). `images.set({ of: "workspace" | "me" | agentId, file })` takes only the caller's own unclaimed upload and uses its row up, so an id someone else learns is worthless; `null` removes the picture. Unclaimed uploads go after a day with their files (`images.sweepUploads`, hourly). Replacing or removing a picture deletes the old file; deleting the row deletes it too (lifecycle `files`): an agent's when it's deleted forever (not in Trash), a photo with its account, the logo, agents' pictures and pending uploads with the workspace. Queries return only URLs (`imageUrl`, once per file per query via `imageUrls`). Who changes them: owners the logo (`workspace.manage`) and agents' pictures (`agents.manage`), everyone their own photo. Agents can't upload; they can reset one to initials (`workspace.settings` / `agents.manage` `remove_image`). Display queries use `namer(ctx, { images: true })`; what agents read never carries URLs. Files for messages go through the same path and rows (`/files/upload`, `files.ts`; up to 20 MB; `uploads.file` set, and each kind is only claimed as itself): [Chat](chat.md).
- **Usage:** each reply stores `stats` (model, tokens, time, AI Gateway's `cost`, and its pictures' `imageCostUsd` and web searches' `searchCostUsd` apart), plus its place's running total (`costUsd` on the chat or thread parent, summaries, pictures and searches included). The runner saves the reply's usage after every finished model call (`turns.saveUsage`, onto `agentTurns.usage`), recording only what's new since the last save; `finishReply` records the rest the same way. So a turn whose action dies (Convex's 10-minute action limit, a crash) keeps what its finished calls cost, never counted twice, and a turn failed as stale (`STALE_TURN_MS`) still gets its stats. The app shows them under each reply. Prompt caching is on for every model call (AI Gateway `caching: "auto"`).
- **Usage by month** (`usage` table, `usage.ts`): every paid call goes through one function, `recordUsage(ctx, { workspaceId, userId?, agentId?, kind, model?, costUsd })`, called from the mutation that saves the call's result (`saveUsage`/`finishReply`, `addSearchCost`, `finishCompaction`, `imageGen.settle`). It adds to one row per workspace, month (UTC, `"2026-10"`), person, agent, kind (`usageKinds`: chat, summary, search, image, dictation) and model, so the Usage screen reads a few rows instead of every message. A reply counts for the person the turn acted for (`agentTurns.actorId`: who wrote the message, who an automation ran for, a channel automation's maker); a summary for the person whose reply triggered it. Zero costs aren't recorded. It refuses a workspace that's being deleted (late-write rule below), and the table is deleted with the workspace and kept when a person leaves or is erased: it's the workspace's bill, shown under a former member's name. `stats.counted` marks replies in the table, so the one-off `migrations.usageThisMonth` (fills this month's earlier replies; summaries from before aren't kept apart, so they're missed) can't add one twice. **Settings → Usage** (`usage.report`, `views/Usage.tsx`): the month's total and by agent, person, kind and model, with a picker for the last six months; people with `usage.view` (owners) see the whole workspace, everyone else only their own share (`scope: "mine"`, no by-person). Agents read the same through `workspace_settings` `usage`, as the acting person. A month is capped at 2,000 rows (people × agents × kinds × models).
- **Web:** search runs in the runner through `SEARCH_PROVIDER` (core `web-search.ts`): `gateway` (default; Exa through AI Gateway, billed with the models), `brave` (`BRAVE_API_KEY`) or `searxng` (a self-hosted `SEARXNG_URL` with JSON on). Gateway search only runs as a provider-executed tool inside a model call, so the adapter makes one tiny call (GPT-6 Luna, forced to call `exa_search` with the query, one step) and records its gateway cost as it finishes (`turns.addSearchCost`): kind `search`, model `exa`, out of the reply's chat row, in its `stats` as `searchCostUsd`. Pages go through `webFetch.fetchPage`, a Node action: `safeFetch` (core `safe-fetch.ts`, reused by link previews) allows http(s) only, resolves DNS and refuses private, loopback, link-local, CGNAT, multicast and metadata addresses (IPv4 and IPv6, IPv4-mapped included), connects only to the addresses it checked (no DNS rebinding), and follows up to 5 redirects by hand, checking each. 15s, 5 MB. Text is decoded like a browser does (`textOf`: byte-order mark, the header's charset, a `<meta charset>` in the first 1 KB, else UTF-8; an unknown label reads as UTF-8). HTML goes through Mozilla Readability (linkedom) and turndown to Markdown with absolute links; text and JSON pass through; other files are refused; cut at 20,000 characters, saying so. Link previews (`linkUnfurl.ts`) read a message's first links with the same `fetchBody` (5s, 1 MB), and keep their own copy of the page's picture so readers never load third-party images ([Chat → linkPreviews](chat.md)).
- **Compaction:** once a reply leaves a session's context over 40k tokens, older turns fold into the session's summary (a ~15k-token tail kept verbatim). The app still shows everything; agent DMs show a divider where the summary starts.

## Data lifecycle
What happens to rows when what they belong to goes. One registry, `lifecycle.ts`, run by one runner, `cascade.ts`. **Every table must declare what happens when its owner goes**: `tests/lifecycle.test.ts` fails on a table missing from the registry (and the registry's type won't compile).
- **Scopes:** `workspace` (deleted), `member` (removed or left), `user` (account erased), `connectorInstall`, `automationInstall` (uninstalled), `page`, `record`, `database`, `field`, `channel`, `agent` (deleted forever from [Trash](data.md#trash): the entry goes first, then the cascade, and the item itself last).
- **Per table, per scope:** delete an index range (`index` + `eq`, optional `where`), patch it instead (`scrub`), go with a parent row (`childOf`, one level), or `keep` with a written reason. `onDelete` runs just before each row goes (leaving each workspace for an erased account; starting an `automationInstall` cascade for a removed member's just-them automations, so others' grants go too). Every table with a `workspaceId` is reached by a `workspaceId`-first index or as a child.
- **Access ends first, in a small mutation:** the member, install or connector row goes, or the workspace is marked `deleting` (`memberOf` refuses it, so every request and agent call does). Nothing else in that transaction grows with the data. Then `startCascade` cleans up.
- **Late writes are refused:** anything an action writes back after a wait rechecks what it belongs to at save time: connector tool lists the install they were listed under, OAuth saves the membership and install (below), the turn queue, activity log, approvals, usage (`recordUsage`), webhooks and scheduled runs a live workspace (`liveWorkspace`, or `memberOf` for every actor), invite emails that the invite is still there. So no row lands behind a cascade that already passed its table.
- **Bounded by bytes, not rows:** each run reads one page of one edge (Convex allows one paginated query per function), up to 100 rows or ~4 MiB, then children and `where` lookups one document at a time, stopping while there's still room for a whole 1 MiB document under an 8 MiB budget (Convex's limit is 16 MiB; up to 2,000 writes). What's done is saved (`edge`, `cursor` on its `cascades` row) and the next run is scheduled; a page that didn't fit is read again smaller (`rows`), so skipped rows are never reread forever. A workspace's own row goes last. A table whose rows hold storage files lists those fields in `files` (a storage id, or a list of `{ storageId }` like `chatMessages.attachments`); the runner deletes the files with each row, wherever a cascade deletes it.
- **Failures:** a cron (`cascade.resume`, every 15 minutes) restarts cascades untouched for 10 minutes whose last run (`run`) failed, counting `attempts` and keeping its `error`. After 3 in a row it's marked `stuck` and left alone, and logs once. To find them: the `cascades` table in the dashboard, `stuck` = true. To resume: fix the cause, deploy, then `npx convex run cascade:retry '{"id":"<cascade id>"}'`; it carries on where it stopped. **Never delete a cascade row** to unblock someone: its rows would stay, and rejoining would bring them back.
- **Rejoining and reinstalling wait** while the old cascade runs ("still being cleaned up" / "still being uninstalled"), so old seats, rules and credentials never come back. A stuck one keeps saying so until it's retried. Not a time filter: `_creationTime` isn't in commit order.
- **Connector sign-ins** (`connectorOAuthFlows`) name the membership (`memberId`) and install (`connectorInstallId`) they started under. Starting one and the final save both check those are still the rows there, so a sign-in from before a removal and rejoin, or an uninstall and reinstall, can't connect; older sign-ins without them are refused. Unfinished ones are deleted with the workspace, member, account or install.
- **Delete workspace** (`workspace.deleteWorkspace({ name })`, owners, `workspace.delete`; the name must match): marks it `deleting` and starts the cascade, however many members it has; access ends at once (`memberOf` refuses it), and the cascade clears "last used" and deletes invites. **Erase account** (`workspace.eraseAccount`): first checks, with a few indexed reads per workspace however big, that they aren't the only owner of one with others (one already being deleted doesn't count). At once: deletes sign-in accounts so the email starts a new account, deletes sign-in rate limits and local sign-in codes (keyed by their email, which is about to go), and replaces the `users` row with `{ erasedAt }`. It's never deleted (~20 tables point at it). `authUserId` (lib.ts) treats an erased account as signed out, so a sign-in token from before can't recreate preferences, a name, a workspace or accept an invite; every account-scoped function uses it, and `nameOf` shows "Former member". `memberOf` refuses an erased account, so nothing acts as them while their memberships wait for the cascade, and an erased owner doesn't count as an owner (so the last other one can't leave meanwhile). Then the user cascade leaves every workspace (deleting ones they're alone in, a member cascade for the rest), deletes their sessions, preferences and personal connector accounts in every workspace (including ones left behind by removals before those deleted them), and clears what agents got back for them (`agentActivity.output`, `approvals.result`, shown only to them); a call that finishes after the erase is logged without them. What they said and did in team chats and history stays, as a former member's. In the app, both are under Danger zone in Settings: deleting the workspace on General (owners only), the account on Your preferences; each asks you to type the workspace's name or your email first.
- **Trash:** deleting moves records, databases, fields, pages, channels, agents, and skills and automations (including retained library installs) to Trash (`trash` table) for 30 days; `trash.sweep` (hourly) and owners' "Delete forever" start the cascades above. See [Data → Trash](data.md#trash).
- **Retired memory timestamp:** `memories.createdTs` remains optional for existing documents because no migration cleared it. New memories omit it; member cleanup uses the cascade, not timestamps.
- **Link previews:** `linkPreviews` rows (one per URL per workspace, shared by the messages that post it) and their picture copies go with the workspace (`workspace` edge, `files: ["image"]`). Member, channel and account cleanup keep them: they hold a public page's title, text and picture, and no one of those owns a row. The unfurl action's write-back (`linkPreviews.save`) rechecks the message and a live workspace, so it can't land behind the cascade; a replaced picture is deleted when its row is rewritten.
- **Message files:** deleting a message deletes its files at once (`messages.remove`); a channel in Trash keeps them until it's deleted forever (the `channel` cascade deletes its messages, and their files with them); a deleted workspace's go with its messages. Unattached uploads go with the hourly sweep after a day, or at once when removed from the composer (`files.discard`). Leaving or an erased account keeps them: they're team history, like the messages.
- **Dead rows:** unfinished connector sign-ins are swept hourly (`forgetExpiredOAuth`); deleting a message deletes its `recordMentions`. What agents already saw of a deleted or edited message stays in their sessions (product decision pending).

## Clean-start upgrade
`storedSkills` and `storedAutomations` migrate existing library installs to stored `definition` snapshots. Instructions, prompts, schedules, webhook event filters, tokens, subscriptions, agent selection and provenance stay unchanged. Existing databases, records, pages and agents (including Scribe) stay untouched. Transitional definitions in `legacyCatalogs.ts` cover the deploy-to-migration window; remove them with the alpha.8 COMPAT cleanup only after both `storedSkills` and `storedAutomations` have finished in prod.

`retireNightOwl` removes only the test connector's install gate, then starts the existing `connectorInstall` cascade for credentials, OAuth flows, tools and permission settings. Reconnecting cannot undo retirement: restoring Night Owl requires restoring support in code (including its catalog entry and grant handling), then reinstalling it, reconnecting accounts and granting its tools again. Late OAuth/connection writes still require a live install. Saving or restoring agent settings drops only retired Night Owl grants; historical versions remain intact. Old desktop install endpoints remain as COMPAT refusals with a message pointing to custom creation; installed skills and automations still list and run, and owners can move them to Trash and restore them for 30 days. Snapshots include trashed installs without changing their archived flag or Trash retention date. Night Owl connectors have no Trash kind and still retire through their connector cascade. Existing Scribes, including ones in Trash, are preserved; only new-workspace seeding changes.

```
pnpm test && pnpm typecheck

```
Desktop tests cover the renderer's pure logic only (`*.test.ts`, e.g. `views/records/logic.ts`).
`pnpm dev` (`scripts/dev.mjs`, the `/dev` skill) gives each checkout its own local Convex backend and data, so worktrees never fight over the cloud dev deployment. Outside the team (no access to the Convex project) it's an anonymous local backend (`CONVEX_AGENT_MODE=anonymous`, no account), with `AI_GATEWAY_API_KEY` taken from the shell. Sign in with any email; local backends send no code (`auth.ts`). `--reset` wipes local data. Local backends have no public URL, so connector OAuth only works on cloud dev (`npx convex dev` against `exciting-guanaco-266`, `pnpm dev:desktop`).

The app's screens are hash paths (`router.ts`): `#/chat[/<chat>[/thread|message/<id>]]`, `#/clients[/<record>]` (and the other record tabs; types owners add are `#/records/<key>[/<record>]`), `#/customize/<tab>[/<item>]`, `#/settings/<tab>`. Opening an item pushes its own screen; back returns to the list.

Every screen has the same shell (`ui.tsx`): a **top bar** (`TopBar`) with where you are on the left, as a trail of links (`Agents › Scribe`; `Page`'s `crumbs`), and the screen's actions on the right (`barButton`, `barDangerButton`; a create action is always `NewButton`, "+ New page"). A screen or tab's one-line description sits next to its title, truncated, like a channel's topic. Chat uses it too. Empty and gone screens use the centered `EmptyState` (icon, title, one line, no button); filtered lists use `NoMatches`. Screens scroll in `Scroll`: the top bar (and a footer, like chat's composer) stays put and takes its own room, content scrolls under it and fades out on a scrim that shows only while something is under it (`.scrim-top`/`.scrim-bottom` in `styles.css`). Sideways overflow (board, wide tables) uses `.bleed` to scroll out to the window's edges instead of stopping at the content column. Big titles in the content (`heading`) are only for things you write in and rename there: pages and records. Settings are rows in a card (`Settings`, `Setting`): label and hint left, control right. Small panels that open from a click (profile cards, menus, a reply's cost, a tool call's details) are a `Popover` (`views/chat/common.tsx`); bigger tasks are a `Modal`. Both draw at the end of the page and stack: a click outside or Escape closes only the newest. Destructive actions ask with `useConfirm` (a red `Confirm`, never the browser's `confirm()`); create dialogs are titled "New …". Checkboxes are `Checkbox` (`controls.tsx`), never the native look. Pickers are `Select` and a few side-by-side choices are `Segmented` (`controls.tsx`), never a native `<select>`: a `Select` opens its list in a `Popover`, searchable when long. Controls come in two sizes that line up: `compactControlClass` (toolbars, settings rows; `compactButton` for Filter-style buttons beside them, `compactPrimaryButton` to submit a row) and `inputClass` (forms, in a `Modal`). The row of controls atop a screen (search and filters, or a one-line add form like Invite) is always `toolbarClass`, compact; settings-row controls are `wideControlClass`. Icons come only from `icons.ts` (Phosphor). In lists with people, agents get a **Bot** badge and square avatars. Every person, agent and workspace picture is one `Avatar` (`common.tsx`): the image, cropped with `object-cover`, or initials. In the sidebar it's `row` (22px), the size of `Item`'s icon slot (glyph icons are 18px in it), so names line up with labels. **Sidebar:** drag its right edge to resize it (160–600px, double-click for the default 240; remembered per computer like its hidden state). The thread panel resizes the same way from its left edge (`ResizeHandle` + `useStoredWidth` in `ui.tsx`). Rows with rows under them (a page with sub-pages, a channel with active threads) fold with the chevron that replaces their icon on hover, remembered per computer (`Item`'s `onToggle`). Sections (Databases, Pages, Channels, Direct messages) fold when you click their title (folded, they keep only the open and unread rows) and move when you drag it; channels, DMs, databases, the rail's workspaces and a database's view tabs drag into your own order (`sortable.ts`, saved per computer like the sidebar's hidden state). Create actions are the section header's hover +; a section shows a muted "New …" row only while empty. There's no Pages or Databases index screen: `/pages` and `/records` go to chat. `pnpm --filter @companybot/desktop preview:web` serves the UI in a browser on port 5173.
